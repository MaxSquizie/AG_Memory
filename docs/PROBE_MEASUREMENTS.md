8,4 секунды и среднего другого режима около 2,3 секунды не является измерением
ускорения на одной и той же выборке.

## Каталог и классификация ответов

Событие `probe_catalog` сохраняет точную версию каталога в начале наблюдаемого
выполнения. `registry_sha256` связывает статические контракты,
`catalog_sha256` — также версию схемы и исторические имена. Анализ TSV использует
этот снимок, а не незаметно подставляет реестр установленной сегодня версии.
Для старого TSV без снимка отсутствие метаданных остаётся видимым.

`structural_oov_reading → structural_oov_function` — сопоставление имён для
отчёта. Исходное имя сохраняется. Старое полное чтение и нынешний выбор функции
не объявляются семантически эквивалентными.

Наблюдаемые исходы разделены:

- `CHOSEN_ONE`, `CHOSEN_MULTIPLE`: валидный выбор из записанного закрытого домена;
- `NONE_FIT`: `0`, отклонение показанных вариантов;
- `INSUFFICIENT_CONTEXT`: `?`, недостаток данных;
- `MALFORMED`: полный ответ нарушает известный протокол;
- `UNKNOWN_EVIDENCE`: протокол, ответ или домен не восстановимы из экспорта;
- `TRUNCATED`: полного ответа нет;
- `PROVIDER_ERROR`: ошибка транспорта;
- `UNFINISHED`: запрос без завершения;
- `BUDGET_BLOCKED` в TSV-анализе: наблюдавшийся отказ до получения ответа.

Внешние пробелы нормализуются так же, как в штатном decoder. Проверяются
диапазон, повторные номера и запрет `0` внутри списка. Множественный выбор
сохраняет каждый выбранный ID. Ошибки HTTP, embedding-запросы без prompt,
непарные события, повторные request IDs и обрезанная карта не становятся
обычными ответами модели. У многошагового кейса учитываются все шаги.

`NOT_OBSERVED_IN_EXPORT` означает только отсутствие наблюдения. Статусы
`UNREGISTERED_OBSERVED` и `DYNAMIC_SOURCE_COLLECTION` сохраняют вызовы за пределами
статического каталога. Отсутствие вызова не присваивает языковому механизму
ни «поддерживается», ни «не поддерживается».

## Четыре разных счётчика

| Уровень | Что считается | Что не следует из числа |
| --- | --- | --- |
| `STATE_CALLS` | Начисленные попытки селектора, включая неуспешные | Что состоялся физический запрос модели |
| `EXECUTOR` | Вызовы, прошедшие его gate; длина входа; отдельная проверка времени | Что provider не отклонил вызов позднее |
| `PROVIDER` | Начисленная оценка токенов и независимые proposal-квоты | Что это точные токены tokenizer или только новые обращения |
| `backend_request_context` | Вход на границе `backend.generate` | Число внутренних HTTP retry или успех генерации |

У provider оценка равна `max(1, (len(prompt) + len(response)) // 4)`; при ошибке
учитывается имеющийся prompt. Здесь `len` — число Unicode code points Python,
system не включён. Replay тоже может расходовать этот логический бюджет.
Embedding-ранжирование имеет отдельный `request_kind=EMBEDDING_RANKING`.

`budget_configured` сохраняет действующие лимиты, единицы и исходные счётчики;
`budget_window_entered` — переход окна; `budget_charged` — before/delta/after;
`budget_reset` — реальный сброс. `budget_ref` относится к объекту-владельцу,
`budget_epoch` различает сбросы. Общий Budget родителя и исполняемых копий имеет
одну ссылку. Суммировать можно только **delta одного уровня**, сохраняя окно,
стадию и владельца. Снимки `state_field` не являются расходом.

`pipeline_stage` сохраняет стадию исполнения внутри вложенных PROVIDER/EXECUTOR
span. Она отличается от декларативного `level` семейства (`T1_T2`, `TD_T4`).
Отсутствующая атрибуция replay записывается как неизвестная, а не как новый запрос.

В коде есть defaults `ProbeLimits` и `RealBackendSelector`; конкретная политика
окна поступает из release. Нулевые оконные caps имеют значение unlimited,
но это правило нельзя переносить на все остальные лимиты. Деление бюджета на
резервы стадий этим изменением не вводится: сначала требуется текущая трасса,
показывающая реальное вытеснение поздних стадий ранними.

## Команды анализа

Из корня репозитория:

```bash
python tools/audit_formalizer_runtime.py path/to/runtime.tsv --out path/to/audit
```

Создаются `summary.json`, `probes.tsv`, `budgets.tsv`, `coverage.tsv`.
В summary есть конфигурации бюджетов, отдельные записи selection-протоколов,
неполные span и пробелы evidence. Поэтому отказ executor до provider и вызов
пользовательского селектора не исчезают из картины только из-за отсутствия
`provider_request`. Provider invocation, format repair и replay не считаются
независимыми физическими обращениями. Большие снимки IR при чтении отбрасываются.

Для прежнего progress JSONL:

```bash
python tools/audit_formalizer_probe_run.py path/to/progress.jsonl --out path/to/inventory.md --json-out path/to/inventory.json
```

Новая инвентаризация показывает числители/знаменатели и таблицу
PASS/FAIL × наличие наблюдавшегося валидного `?`, отдельно отмечая неполные
данные. Старые Markdown без raw-источников автоматически не пересчитываются.

## Независимая разметка и отрицательные контроли

Экспорт предъявленных вопросов для разметки:

```bash
python tools/audit_formalizer_probe_controls.py export path/to/runtime.tsv --out path/to/annotations.json
```

Экспорт содержит prompt, упорядоченные candidates, фактические system/role/
параметры на границе `backend.generate` и идентичность события. Ответ модели
отдельным полем не показывается разметчику. При replay контекст принимается
только из совпадающего исходного вызова в том же файле. Вызов без полного
контекста не допускается к оценке.

Разметчик заполняет `annotation` для каждого оставленного образца:

```json
{
  "reviewer": "имя или идентификатор разметчика",
  "rationale": "почему показанный вариант не соответствует исходному тексту",
  "expected_outcome": "NONE_FIT",
  "expected_selected": []
}
```

Для положительного/неоднозначного случая указываются `ONE_SELECTED` или
`MULTIPLE_ADMISSIBLE` и точный набор ID. Для недостатка данных —
`INSUFFICIENT_CONTEXT` и пустой список. Это не шкала уверенности.

```bash
python tools/audit_formalizer_probe_controls.py score path/to/runtime.tsv --annotations path/to/annotations.json --out path/to/control-score.json
```

Scorer проверяет SHA исходного TSV, адрес события, точные prompt/system/settings
и карту кандидатов. Подмена порядка вариантов, повторная разметка одного события,
неизвестный ID, неверная кардинальность или незаполненная разметка отвергаются.
Ответ проверяется штатным `SELECT_LABELS_V1` decoder. First attempt, format repair
и replay оцениваются отдельно. `?` на отрицательном контроле — абстенция,
а не правильный отказ; при нуле определённых ответов доля ошибок не определена.
Модель, эффективные параметры и фактический backend context образуют отдельные
группы: результаты разных моделей или настроек не сливаются в одну точность.

Этот инструмент **оценивает уже записанные ответы**. Для намеренно неверных
разбиений нужен отдельный контрольный запуск с соответствующими входами и
независимым gold. Нельзя отредактировать prompt прежнего вызова и оценить на нём
старый ответ. Контроли не подмешиваются в рабочую формализацию и не расходуют её
окна. Сконструированные контроли, размеченный runtime и внешний G5 — разные наборы.

## Следующий измерительный запуск

1. Зафиксировать текущие код/release/model/settings, снимок каталога и полный TSV.
2. Подготовить matched positive/negative проверки одного разбиения, случаи
   недостающего контекста и нескольких допустимых чтений. Ошибочные варианты
   должны различать роли/границы/области смысла, а не только ломать формат.
3. Считать ложное принятие, ложное отклонение, `?`, нарушения протокола и
   точное множество альтернатив. Отдельно проверить downstream результат.
4. Для T4/reference/discourse различить неприменимость, детерминированный исход,
   reuse, блокировку и недостижение стадии по положительным свидетельствам.
   Нулевой счётчик не заменяет этот аудит.
5. Создать внешний G5 с происхождением, зафиксированным отбором и независимой
   разметкой до настройки на нём. Текущие unit fixtures не являются G5.
6. Решать вопрос резервов бюджета лишь после измерения реального расхода и отказов.

языка и прохождение G5 этим изменением не заявляются.

## Связь с литературой

[Braun, 2025](https://arxiv.org/html/2509.08480v1) исследует зависимость ответов
от формулировки; работа не устанавливает систематическое «да» для нашего Qwen
и русских структурных проб. Нужны собственные отрицательные контроли.

[Kadavath et al., 2022](https://arxiv.org/html/2207.05221v4) отделяют проверку
своего ответа от обучения P(IK). Перенос калибровки на новые задачи ограничен.
Опыт с заменой варианта на NOTA не доказывает, что надо удалять уже действующий
`0`: у нас `0` отклоняет предъявленную страницу, `?` сообщает о недостатке данных.
