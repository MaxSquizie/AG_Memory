# TSV-журнал рантайма

## Текущий этап

Первый этап подключает общий TSV-журнал к формализатору. Формат рассчитан на
последующее подключение остальных подсистем. Полное покрытие всего рантайма
этим этапом не заявляется.

Журнал является внешним наблюдателем. Он не участвует в выборе кандидатов,
проверке оснований, воспроизведении ответа провайдера или записи фактов.
Идентификаторы трассы, часы и курсоры наблюдения не добавляются в
`FormalizationState`, `observation`, канонические хеши или WAL.

## Где появляется файл

| Способ запуска | TSV |
| --- | --- |
| GUI, включая `run_formalizer_lab.bat` | `paths.logs_dir/session-<timestamp>-<id>.tsv` |
| Обычный CLI `ah-agent` | `paths.logs_dir/session-<timestamp>-<id>.tsv` |
| Android через существующий `start_session` | TSV рядом с JSONL той же сессии |
| `tools/run_formalizer_v7_oracle.py --out DIR` | `DIR/runtime.tsv` |
| Прямое использование Python API | Явный `RuntimeTrace` и `use_trace`, пример ниже |

Для обычной конфигурации `paths.logs_dir` указывает на `logs/`. В изолированной
лабораторной сессии путь берётся из её `gui.toml`; журнал лежит в каталоге
`logs` этой сессии. Существующие `.jsonl`, `.log` и `progress.jsonl` сохраняются.
Новый запуск получает отдельный TSV. Существующий файл не перезаписывается.
Oracle с `--list` файл не создаёт.

```python
from ah.diagnostics.runtime_trace import RuntimeTrace, use_trace

with RuntimeTrace("my-run.tsv") as journal, use_trace(journal):
    result = formalizer.interpret(text)
```

Для прямого вызова без наблюдения применяется `with use_trace(None):`.
Он также отключает автоматический выбор журнала активной GUI-сессии в этой
области выполнения. Смена сессии закрывает предыдущий TSV writer.

## Формат `runtime-tsv-1`

Кодировка — UTF-8. Разделитель столбцов — настоящий символ табуляции.
Каждое событие занимает одну физическую строку с окончанием LF. В строковых
столбцах обратная косая черта, табуляция, CR и LF записываются соответственно
как `\\`, `\t`, `\r`, `\n`. Последний столбец — обычный компактный JSON;
к нему применяется только `json.loads`, дополнительное разэкранирование не нужно.

| Столбец | Значение |
| --- | --- |
| `schema_version` | `runtime-tsv-1` |
| `timestamp` | Время записи события в UTC |
| `sequence` | Порядковый номер записи в файле, начиная с 1 |
| `session_id` | Идентификатор файла/сессии |
| `turn_id` | Ход диалога, если он задан текущим хостом |
| `trace_id` | Конкретное выполнение; повторный самостоятельный вызов получает новую трассу |
| `span_id` | Текущая вложенная операция |
| `parent_span_id` | Родительская операция |
| `run_id` | Идентификатор интерпретации/WAL, когда он уже установлен |
| `observation_id` | Наблюдение, к которому относится выполнение |
| `interpretation_version` | Версия интерпретации наблюдения |
| `component` | Подсистема; сейчас прежде всего `formalizer`, в runner также `oracle` |
| `stage` | Реальная стадия или операция |
| `event` | Тип события |
| `status` | Фактический статус операции или решения |
| `duration_ms` | Измеренная монотонными часами длительность операции |
| `entity_id` | Адрес решения, запроса, задачи или другой наблюдаемой сущности |
| `reason` | Код или текст причины |
| `data_json` | Полные дополнительные поля события |

В начале валидации `run_id` и `observation_id` могут быть пустыми: вход ещё не
принят, идентификатор ещё не назначен. Связь с последующими событиями сохраняют
`trace_id` и `span_id`. Повторное выполнение одного durable run сохраняет
`run_id`, но различается по `trace_id`. В oracle несколько вызовов внутри одного
кейса являются дочерними операциями общей трассы `ORACLE_CASE`.

Дополнительные адреса находятся в JSON: `state_ref`, `parent_state_ref`,
`condition_ref`, `hypothesis_ref`, `parent_condition_ref`, `parent_shell_ref`,
`child_ref`, `decision_ref`, `ordinal`, `attempt`, `case_id`, `case_index`.
Они появляются там, где соответствующая сущность действительно существует.

## Подключённые участки

| Участок | Что фиксируется |
| --- | --- |
| `FormalizerAdapter.interpret` и `interpret_full` | Вход, валидация, привязка run, snapshot/replay, ранние отказы, финальный отчёт и результат хосту |
| `kernel.interpret`, `run_native` | Независимое выполнение компонента, лимиты и реальные стадии |
| Native-стадии | `T0_T1`, `T2_REGIONS`, `CONTEXT`, `T3_CANDIDATES`, `T4_RESOLUTION`, `T5_PLAN`, `T6_ADMISSION` |
| Preview | Отдельные `T0`, `SRL`, `T1`, `T2`, `TD`, seal, `T3`, `T4`; явно указан `mode=preview` |
| Состояние | Новые syntax rows, диагностики, отбрасывания, context reads; изменённые токены, фреймы, решения, source traces, ресурсы, бюджеты и поля состояния |
| Диспетчер | Существующие события выполнения, повторного использования, пересмотра, инвалидирования, зависимостей и приостановки |
| Условные ветви | Создание исполняемой копии, родительское состояние, условие, локальные события и решения до снятия условного контекста |
| Component probes | Предъявленные варианты, контекст/вопрос, input-contract rejection, provisional result, отсутствие выбора, причины, reuse и история решения |
| Selection protocol | Каждая попытка, проверка формата, format repair, валидные `0` и `?` |
| Provider / bounded executor | Точный prompt, ответ, selection audit, capability/model/params, ordinal/call ID, replay, отказы до транспорта и после получения ответа |
| C/T5/T6 | Построенный список операций и фрагментов, prechecks, подготовленный пакет, фактическая транзакция, `terminal`, `applied`, `batch_hash`, idempotent replay |
| Уточнение и пересмотр | Входы clarify/ignore/reinterpret/migration, ранние ошибки, ссылка на новую версию и вложенный обычный путь интерпретации |
| Oracle | Вход/выход реального выполнения каждого кейса и привязка runtime-событий к `case_id`; ожидаемые ответы не подаются в журнал формализатора |

Вызовы реального backend также сохраняют фактически переданные system, role
и параметры генерации. Для optional embedding ranking журнал показывает
запросы текстовых batch, размеры ответов, проверку векторов, cache/replay,
причину отказа/пропуска и используемые scores. Полные массивы embedding-векторов
и низкоуровневые HTTP-пакеты в этот этап не включены.

`span_started` всегда открывает операцию. При штатном возврате записывается
`span_finished`; при исключении — `span_failed` с типом и причиной.
`OK` у стадии означает, что её код завершился: семантический результат нужно
читать в решениях и `formalizer_result`. Аналогично `RECEIVED` означает
получение ответа, `VALID` — соответствие протоколу, `PROVISIONAL` — предварительный
выбор. Ни один из этих статусов не подменяет `RESOLVED` или `APPLIED`.

Если транзакция успела примениться, а последующая проекция результата завершилась
ошибкой, журнал содержит успешную `T6_TRANSACTION` и ошибку `HOST_INTERPRET`.
Успешный коммит не переименовывается в неуспешный.

## Как интерпретировать снимки и изменения

Runtime-события и записи из внутренней трассы имеют разные источники времени.
Вызов провайдера записывается непосредственно перед выполнением, ответ — после
получения. `syntax_trace`, `decision_updated`, `state_field` и аналогичные записи
отмечены `capture=checkpoint`: время строки — момент наблюдения уже накопленных
данных. Журнал не восстанавливает несуществующие timestamps задним числом.

Внутри одной стадии новые записи сбрасываются перед и после probe, при диагностике,
отбрасывании, событиях диспетчера и выходе из условного контекста. Полный просмотр
изменений состояния выполняется на границах стадий и исполняемых ветвей.
Поля `observation` и `generation_snapshot` сравниваются по ключам; изменение
одного значения не заставляет повторно записывать весь словарь.

`state_fork` показывает унаследованные размеры коллекций. Скопированный префикс
не выдаётся за новое вычисление. Read-only overlays проверки доказательств не
регистрируются как исполняемые ветви. Если список восстановлен из snapshot,
записывается `state_collection_reset`, а его строки имеют
`capture=restored_snapshot`. Отсутствующая в конечном root state локальная ветвь
остаётся в TSV под собственным `state_ref`.

Этот механизм фиксирует опубликованные внутренние события и изменения состояния
на указанных границах. Он не является трассировщиком каждой инструкции Python
или каждой промежуточной локальной переменной.

## Чтение и поиск

Большой `data_json` может превышать стандартный лимит поля модуля `csv`.
Предоставленный reader читает строки потоково без этого ограничения,
разэкранирует обычные столбцы и декодирует JSON в дополнительный ключ `data`:

```python
from ah.diagnostics.runtime_trace import read_events

for event in read_events("my-run.tsv"):
    if event["event"] in {"candidate_rejected", "diagnostic", "span_failed"}:
        print(event["sequence"], event["stage"], event["reason"], event["data"])
```

Для обычного `csv.DictReader` нужны `delimiter="\t"`, `quoting=csv.QUOTE_NONE`,
достаточный `csv.field_size_limit` и `unescape_scalar` для строковых столбцов.
Табличный редактор подходит для коротких полей и фильтрации; большие вложенные
снимки удобнее читать программно.

Reader явно сообщает о несовместимом заголовке, неизвестной версии схемы,
повреждённом JSON или незавершённой строке. Повреждение файла не скрывается
пропуском записей.

## Ошибки журнала и стоимость

Запись защищена lock, порядок задаётся `sequence`, каждая строка сразу
сбрасывается в файл. Это не `fsync`-WAL: гарантии durable commit принадлежат
существующему каноническому журналу. При ошибке файла наблюдение отключается
с однократным сообщением; результат или исключение интерпретатора сохраняются.
Неподдерживаемое значение или цикл получает явный `_trace_unserializable`,
а не молчаливое усечение payload.

Идентификаторы и контекст операций используют `ContextVar`; независимые потоки
и задачи не меняют друг другу run/observation/span. Для пользовательских
потоков без активной сессии `use_trace(writer)` устанавливается внутри потока.

Полные данные добавляют работу сериализации и I/O. Журнал не меняет лимиты и
правила расходования call/token бюджета. Существующий wall-clock budget
продолжает измерять реальное время, в том числе стоимость наблюдения;
тождество результата около временного лимита не обещается.

## Дальнейшее подключение рантайма

| Этап | Статус | Условия завершения |
| --- | --- | --- |
| Общий формат и формализатор | Реализован в описанных границах | Автоматический файл для основных хостов; реальные этапы, probes, условия, решения, отказы и receipt; проверки результата и хешей с TSV/без TSV |
| Запросы к памяти и вывод | Следующий | Обычные вопросы, goal/proof execution, альтернативы, причины остановки, входные premises, итог и recovery; общий run/span контекст |
| Активация и обслуживание памяти | Не подключён | Ignition, распространение, рабочая область, угасание, consolidation/GC/lifecycle, причины изменения состояния |
| Диалоговый оркестратор и агент | Не подключён полностью | Полный turn, проекция контекста, генерация ответа, repair, завершение и ошибки на всех хостах |
| Общий транспорт и остальные входы | Не подключён полностью | Политики timeout/retry/cancel и независимые background/import/export пути; сквозная проверка покрытия |

При расширении используется тот же writer и схема, а события добавляются в
централизованные реальные точки выполнения. Наличие записи о вызове подсистемы
не считается полным покрытием её внутренней работы.

## Проверки первого этапа

Новые проверки находятся в `test_runtime_trace.py`,
`test_formalizer_provider_trace.py`, `test_formalizer_runtime_trace.py`,
`test_formalizer_oracle_tsv.py`. Они проверяют физический TSV, длинные поля,
корреляцию, ошибки observer, исключения, provider replay/budgets/protocol,
native commit, private conditional branches и runner.

Сопоставление native-прогона с включённым и выключенным TSV проверяет всё
сериализованное IR, итоговый report, batch hash и ledger. Скриптовые selectors
используются для воспроизводимых проверок механики. Это не измерение качества
или скорости живой модели.
