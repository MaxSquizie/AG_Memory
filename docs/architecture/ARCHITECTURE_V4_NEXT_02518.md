# Точка продолжения построчного аудита архитектуры v4

## Что завершает v0.25.18

Последний ellipsis-прогон закрывает два неорфографических failure-класса из
живого результата 97/100. Это граница acceptance-работы по ellipsis, а не
заявление о полном покрытии всех возможных конструкций языка.

При дальнейшем проходе сознательно пропускаются:

- §18.8 `Lexical Recovery`: отложен до отдельного контура Levenshtein candidate
  generation → embedding rerank → morphology validation;
- §19.4 `Late split`: прямо помечен архитектурой как отложенный;
- §37 и явные non-goals §38: не входят в обязательный backlog, пока решение не
  будет отдельно пересмотрено.

## Первая подтверждённая частичная граница — §20.6

Нижняя часть temporal/state контура уже существует:

- `AssertionCandidate` принимает `temporal_mode=TRANSITION` и
  `transition_operator`;
- Integration передаёт переход в `StateTracker` атомарно;
- `START / STOP / CONTINUE / AGAIN / NO_LONGER` зарегистрированы и имеют
  проверяемую interval/state semantics;
- переход требует явного или разрешённого TIME-actant и при нарушении откатывает
  транзакцию.

Но обычный путь adaptive perception пока только переносит уже существующий
`transition_operator` при ellipsis-клонировании. Он не выводит этот оператор из
исходной natural-language конструкции. Исправление `SCOPED_EVENT` в v0.25.18
решает более узкую задачу: дочернее `P` не становится самостоятельным factual
premise. Оно не создаёт каноническое `START(P)` и не закрывает §20.6 end-to-end.

## Следующий вертикальный срез

Следующий срез должен закрыть source text → staging transition → atomic state
integration как один контракт:

1. выделить proposition operand и определить один из пяти операторов только по
   source evidence;
2. выставить occurrence-level `TemporalMode.TRANSITION`, не меняя глобальный `T`;
3. определить fail-closed политику TIME anchor: переход нельзя коммитить с
   выдуманным временем;
4. сохранить scope, provenance, negation и ellipsis remap дочернего подграфа;
5. доказать end-to-end результат через parser, integration, persistence и
   state-query tests;
6. проверить отрицательные случаи, где похожая surface form не лицензирует
   переход.

Распознавание не должно опираться на список конкретных фазовых глаголов,
acceptance-фразы, имена участников или номера cases. Допустима bounded
source-only semantic classification с конечным протоколом результата и строгой
runtime-валидацией. Если оператор или temporal anchor неоднозначен, система
сохраняет scope и завершает переходный путь fail-closed.

## Порядок дальнейшего аудита

После §20.6 проход продолжается последовательно от §20.7. Для каждого раздела
нужно присвоить один проверяемый статус:

- `CLOSED` — контракт реализован end-to-end и покрыт положительными и
  отрицательными тестами;
- `PARTIAL` — существует только часть пути или отсутствует обязательный oracle;
- `OPEN` — исполняемого пути нет;
- `DEFERRED` — отсрочка прямо зафиксирована архитектурой или пользователем;
- `NON_GOAL` — пункт явно исключён §38.

Открытые вопросы §36 нельзя молча считать ни выполненными, ни отложенными. Для
них нужен явный выбор политики до реализации либо сохранение обратимой runtime
опции, как уже сделано для участия `H` в association mode.

Этот файл фиксирует вход в следующий проход, но не подменяет полную матрицу
соответствия всех последующих разделов архитектуры.
