# Архитектура АГ-памяти — версия для разработки

## Полная техническая спецификация когнитивного слоя долговременной памяти для LLM

Этот документ предназначен для реализации и сопровождения кода. Он объединяет нормативную архитектуру, детальные контракты модулей, правила канонического представления, алгоритмические ограничения, runtime-состояния, диагностические требования, открытые вопросы и сознательно отложенные направления.

Документ описывает **целевое поведение системы**, а не историю её разработки. Если конкретная реализация расходится с этим документом, расхождение следует считать техническим долгом или отдельным архитектурным решением, которое должно быть явно зафиксировано.

### Статусы требований

- **ОБЯЗАТЕЛЬНО** — архитектурный инвариант; реализация не должна его нарушать.
- **РЕКОМЕНДУЕТСЯ** — предпочтительная реализация; отклонение допустимо при сохранении семантики.
- **КОНФИГУРИРУЕМО** — конкретное значение не фиксируется архитектурой.
- **ОТКРЫТО** — решение намеренно ещё не принято.
- **ОТЛОЖЕНО** — направление признано полезным, но не входит в текущий обязательный контур.
- **НЕ ВХОДИТ** — сознательная граница системы; не следует реализовывать как скрытый fallback.

### Основной принцип чтения

В документе нужно строго различать три слоя:

```text
1. Canonical AH
   долговременная структурированная память

2. Runtime cognition
   возбуждение, Workspace, proof state, bindings, временные overlays,
   staging-структуры formalization/consolidation

3. Main LLM
   внешний генератор ответа, не владелец памяти и не reasoner AH
```

Runtime-структура не должна становиться новым canonical node kind только потому, что она удобна в коде. И наоборот, canonical fact не должен храниться только в runtime-индексе.

# Часть I. Нормативная архитектура

Ниже приведено целостное описание системы. Во второй части те же решения раскрыты как контракты для реализации.


АГ-память — локальный структурированный слой, который принимает опыт, переводит его в каноническое семантическое представление, поддерживает ассоциативную активацию, выполняет формальный вывод и передаёт основной генеративной модели только актуальный контекст.

Ключевая граница системы:

```text
LLM != долговременная память
```

Основная LLM отвечает за генерацию ответа. Память, идентичность сущностей, активация, поиск, формальный вывод и управление контекстом находятся вне неё.

---

# 1. Назначение и общий контур

## 1.1. Что делает система

АГ-память должна одновременно обеспечивать:

- запись нового текстового опыта;
- каноническое представление знаний;
- долговременное хранение и забывание;
- ассоциативное распространение возбуждения;
- формирование текущего Workspace — активной области памяти;
- извлечение релевантного опыта;
- символический вывод по формализованным знаниям;
- построение компактного контекста для внешней LLM;
- хранение пережитой истории самого агента.

Чат, QA, ассистент и другие режимы являются оболочками над одним когнитивным слоем.

## 1.2. Полный поток обработки

```text
Внешний текст
    ↓
Text Sensory / распознавание S
    ↓
Детерминированный языковой разбор
    ↓
Локальные семантические пробы БЯМ
    ↓
Deterministic Integration
    ↓
AH = <S, C, P, H, L>
    ↓
Activation Seed / Reactivation
    ↓
Ignition Engine
    ↓
Workspace
    ↓
Recall + Symbolic Inference
    ↓
Context Projector
    ↓
AgentContext
    ↓
Основная LLM
    ↓
Ответ
    ↓
Запись пережитого ответа в H
```

Канонические знания хранятся в `AH`. Runtime-состояния используются для вычисления и не заменяют память.

## 1.3. Длинная история не передаётся основной LLM

Каждый вызов основной LLM рассматривается как stateless относительно прошлых вызовов. Её вход состоит из:

```text
текущий запрос
+ проекция активного Workspace
+ результаты формального вывода
+ системные инструкции
```

Предыдущие реплики не передаются как отдельное длинное history window. Если они всё ещё релевантны, их семантика остаётся возбуждённой в памяти и возвращается через Workspace.

## 1.4. Локальная и внешняя части

Локально работают:

- морфология и синтаксический анализ;
- семантические пробы БЯМ;
- Deterministic Integration;
- AH Core и Persistence;
- Ignition Engine;
- Workspace;
- Recall;
- GoalSpec и Symbolic Inference;
- Context Projector;
- lifecycle и GC;
- ассоциативный поиск.

Основная генеративная LLM может находиться вне устройства. Она не получает прямой доступ к канонической AH и не управляет памятью.

# 2. Каноническая модель памяти

## 2.1. Базовая структура

```text
AH = <S, C, P, H, L>
```

`S` — сенсорно-языковой слой.  
`C`, `P`, `H` — семантические области памяти.  
`L` — типизированные направленные связи.

Для краткости:

```text
E = C ∪ P ∪ H
```

Элемент семантической области имеет состояние:

```text
e = <q, x, f>
```

где `q` задаёт тип элемента, `x` — текущее возбуждение, `f` — его функция активации.

## 2.2. Основные типы

- `s` — устойчивый языковой символ / лексическая единица.
- `m` — самостоятельно адресуемая семантическая сущность или понятие.
- `T` — шаблон предиката и набор ролей актантов.
- `N` — конкретная реализация одного `T`, то есть отдельный факт/ситуация.
- `L` — структурное типизированное отношение между элементами.
- `g` — функциональная или логическая композиция.
- `k` — адресуемая группировка элементов.

Ссылочные формы `s*` и `m*` используются внутри составных структур как ссылки на соответствующие канонические элементы.

Только `m`, `k` и `N` структурно имеют `Pr/Mt`. Для `s`, `T`, `g` и `L` дополнительные свойства не вводятся произвольно.

## 2.3. `S`: языковые символы

Один `s` соответствует одной устойчивой лексической единице или парадигме:

```text
s_ЛОДКА
R_text = {лодка, лодки, лодке, ...}
```

Phrase-level `s` не создаётся. Многословное выражение собирается из нескольких лексических символов, а его семантика разрешается отдельно.

```text
s_ПОДВОДНЫЙ + s_ЛОДКА
→ m_ПОДВОДНАЯ_ЛОДКА
```

если выражение обозначает устойчивое единое понятие.

В композиционной конструкции новый `m` для всей фразы не обязателен:

```text
«красная лодка»
→ объект/понятие ЛОДКА
+ семантика КРАСНЫЙ(...)
```

## 2.4. `m`: семантическая identity

`m` создаётся для содержания, которому нужна собственная устойчивая идентичность и которое должно независимо участвовать в активации, отношениях и рассуждении.

```text
m = <UID, Pr, Mt>
```

Примеры:

```text
m_ИВАН
m_МОСКВА
m_ЧЕЛОВЕК
m_КРАСНЫЙ
```

Имя не является identity key. Одинаковая строка может относиться к разным `m`; один `m` может иметь несколько имён и алиасов.

## 2.5. `T`: шаблон предиката

```text
T = <UID, s*, A>
```

`A` — набор допустимых ролей актантов. Основные роли:

```text
SUBJECT
OBJECT
AUXILIARY
RECIPIENT
SOURCE
ABSENTEE
LOCATION
STATE
TIME
DURATION
CAUSE
PURPOSE
TOOL
MATERIAL
AMOUNT
HOW-TO
```

Новый естественно-языковой предикат расширяет слой `T/N`, а не создаёт новый `L.ID` автоматически.

## 2.6. `N`: конкретный факт

```text
N = <UID, w, T*, actants, Pr, Mt>
```

Один `N` — одна реализация одного `T`. Одно предложение может породить несколько `N`.

```text
N_READ
├── T*      -> T_READ
├── SUBJECT -> m_ИВАН
└── OBJECT  -> m_КНИГА
```

`N` может быть актантом другого `N`, что позволяет представлять вложенное содержание:

```text
SAY(Иван, MOVE(Маша, Париж))
```

`N.w` участвует в динамике активации и не является confidence или truth score.

## 2.7. `L`: структурная связь

```text
L = <UID, ID, w, (e1*, e2*)>
```

Ключевые структурные отношения:

```text
IS-A
FOLLOW
CAUSE
```

`L` используется для отношений, семантика которых известна движку как структурная. Обычный новый глагол или предикат остаётся `T/N`.

## 2.8. `g`: функциональная и логическая композиция

```text
g = <UID, ID, operands>
```

`g.ID` имеет зарегистрированную машинную семантику. Для каждого оператора `FunctionRegistry` определяет:

- схему операндов;
- правила выполнения;
- обработчик reasoner-а;
- человекочитаемую проекцию.

Примеры:

```text
AND(...)
OR(...)
NOT(...)
IMPLIES(...)
FORALL(...)
EXISTS(...)
FALSE(N)
```

Новый `g.ID` допустим только вместе с детерминированной семантикой.

## 2.9. `k`: адресуемая группировка

```text
k = <UID, ordered_members, Pr, Mt>
```

`k` задаёт границу и identity группы, но не создаёт отношения между её членами и не выполняет логическую функцию. Он подходит для эпизодов, иерархий, ambiguity sets и conflict sets.

# 3. Семантические области `C / P / H`

## 3.1. Назначение областей

```text
C — интерсубъективная модель мира;
P — персонализированная модель агента и известных ему объектов;
H — пережитая история агента.
```

Это не уровни достоверности.

Один и тот же тип `m/N/g/k/T` может существовать в любой из этих областей.

## 3.2. Содержание сообщения и факт коммуникации разделяются

Пользовательская реплика имеет два слоя:

```text
сообщение как пережитое событие → H
содержательная семантика       → C/P по смыслу
```

Собственный ответ агента записывается в `H`, но не подтверждает автоматически содержимое `C/P`.

```text
generation != confirmation
```

`H` хранит семантическую историю, а не execution log. Тики движка, stack trace, диагностика и telemetry находятся вне `H`.

## 3.3. FOLLOW и эпизодическая последовательность

Пережитые события могут связываться `FOLLOW`:

```text
H_EVENT_1
   ↓ FOLLOW
H_EVENT_2
   ↓ FOLLOW
H_EVENT_3
```

Это позволяет сохранять порядок опыта без превращения истории в сырые текстовые логи.

# 4. Восприятие и формализация

## 4.1. Основной принцип

Всё, что можно определить алгоритмически, определяется детерминированно. Языковая модель используется только для узкой семантической неоднозначности после предварительного сужения задачи.

```text
детерминированный анализ
→ небольшой набор допустимых кандидатов
→ bounded semantic probe при необходимости
→ deterministic validation
→ canonical integration
```

БЯМ не назначает UID, не пишет в AH напрямую и не выполняет скрытый repair памяти.

## 4.2. Два уровня формализации

### Локальная языковая формализация

На уровне предложения определяются:

- лексические единицы;
- границы клауз и именных групп;
- predicate-argument structure;
- роли актантов;
- вложенность и scope;
- явные временные, причинные и логические связи;
- кандидаты identity и coreference.

### Семантическая консолидация

После локального разбора выполняются:

- entity resolution;
- deduplication;
- merge доказанных дублей;
- coreference resolution;
- linking между фактами;
- разрешение оставшейся неоднозначности;
- проверка временного и контекстного согласования.

Для сообщения консолидация выполняется после всего сообщения. Для документа — после формализации всего документа.

## 4.3. Никаких keyword-trigger правил

Лексические маркеры помогают сузить анализ, но не определяют структуру сами по себе.

Например `если`, `при условии`, `в случае` могут указывать на условную конструкцию, но оператор `IMPLIES` строится только после анализа всей структуры. Аналогично `или` и `либо` не превращаются автоматически в OR/XOR.

## 4.4. Неоднозначность сохраняется явно

Если после детерминированного анализа и bounded probe остаётся несколько равноправных canonical-кандидатов, система не выбирает один произвольно.

Для ссылочной неоднозначности используется `k_AMBIGUOUS`. Для логических scope-вариантов сохраняются scoped alternatives.

Неоднозначность может существовать до появления нового контекста.

## 4.5. Atomic Integration

Каноническая запись выполняется только после полной проверки создаваемого подграфа:

```text
candidate validation
→ predicate/T resolution
→ actant resolution
→ identity/coreference resolution
→ domain routing
→ deduplication
→ full validation
→ atomic commit
→ activation seed
```

Полусозданные структуры не остаются в памяти.

## 4.6. Raw source и provenance

Исходный текст может храниться локально как provenance и источник для повторной обработки. Он не используется как обычная retrieval-memory и не подменяет семантическую AH.

# 5. Identity, coreference и консолидация

## 5.1. Identity resolution

Resolver использует совокупность признаков:

- имя и алиасы;
- свойства;
- известные отношения;
- факты;
- временной и дискурсивный контекст;
- текущую активацию.

Одинаковое имя не означает одинаковую сущность.

## 5.2. Canonical merge

Если две сущности доказанно являются одной identity, выполняется merge. Каноническим остаётся детерминированно выбранный UID, ссылки перепривязываются, эквивалентные `N` дедуплицируются.

Несовместимые свойства после merge не разрешаются самим merge-механизмом, а передаются общему Conflict Engine.

## 5.3. Deduplication

Эквивалентный факт внутри одного domain переиспользует существующий `N`:

```text
Equivalent(N_incoming, N_existing)
AND same_domain
→ reuse N_existing
```

Повтор увеличивает `occurrence_count` и вызывает reactivation. `occurrence_count` не равен `w`.

Разные пережитые эпизоды в `H` остаются различимыми даже при одинаковом содержании.

## 5.4. Delayed coreference в больших текстах

Antecedent местоимения может появиться намного позже первой ссылки. Поэтому во время ingestion используется временный `DiscourseRef`:

```text
DiscourseRef
├── local_id
├── sort
├── mentions
├── grammatical constraints
├── semantic constraints
└── candidate bindings
```

`DiscourseRef` не является AH-узлом. Он живёт в staging/consolidation state и может существовать через весь документ.

Если позднее появляется identity:

```text
он -> DiscourseRef d0
...
«это был Алексей»
→ d0 -> m_АЛЕКСЕЙ
```

накопленные frames перепривязываются к `m_АЛЕКСЕЙ` до окончательной canonical integration.

## 5.5. Истинно неизвестный участник

Если участник так и не идентифицирован, но несколько фактов относятся к одному и тому же неизвестному объекту:

```text
«Кто-то вошёл. Он сел.»
```

сохраняется одна existential formula:

```text
EXISTS $0:
    ENTER($0)
    AND
    SIT($0)
```

Фиктивный `m_UNKNOWN_PERSON` не создаётся.

# 6. Время и состояние

## 6.1. Представление времени

Время не требует нового канонического типа. Временная сущность представляется обычным `m` и связывается с `N` через роль `TIME`.

```text
m_TIME.Pr:
    kind = POINT | INTERVAL
    start
    end
    precision
    timezone
```

Семантическое время прикрепляется только тогда, когда оно действительно указано или необходимо для различения событий, разрешения конфликта или reasoning.

Технический timestamp сообщения остаётся provenance и не становится TIME каждого факта автоматически.

## 6.2. Relative time

Относительное время разрешается по подходящему anchor в следующем порядке:

1. явный anchor в тексте или дискурсе;
2. timestamp документа/источника;
3. timestamp текущего пережитого события;
4. unresolved, если надёжного anchor нет.

Частично заданное время остаётся частичным. `12:00` не получает выдуманную дату, `март` — выдуманный год.

## 6.3. Temporal relations

Из нормализованных точек и интервалов детерминированно выводятся отношения:

```text
BEFORE
AFTER
OVERLAP
CONTAINS
```

`FOLLOW` и физическое время различаются. `FOLLOW` задаёт порядок, но сам по себе не означает timestamp или duration.

## 6.4. Состояния и переходы

Состояние может иметь открытый интервал валидности:

```text
WORK(server)
TIME = [t_start, ?]
```

Явный переход закрывает текущий интервал и открывает следующий:

```text
WORK(server)      [t0, 15:00)
NOT(WORK(server)) [15:00, ?]
```

Для переходов используются scoped функции:

```text
START(P)
STOP(P)
CONTINUE(P)
AGAIN(P)
NO_LONGER(P)
```

Текущее состояние определяется temporal coverage, а не последним упоминанием в тексте.

`NEVER(P)` трактуется как temporal quantification, а не как обычный флаг `NOT`. В open-world semantics отсутствие найденного события не доказывает «никогда».

# 7. Активация, Workspace и пластичность

## 7.1. Возбуждение `x`

`x` — текущее возбуждение элемента. Оно определяет когнитивную доступность и участие элемента в spreading activation.

```text
activation != truth
activation != proof
```

Внешний текст сильно стимулирует распознанные `S`; после интеграции сильный seed получают соответствующие semantic structures.

## 7.2. Вес `w`

`w` у `L` и `N` — сила передачи возбуждения по данному пути.

```text
w != truth
w != reliability
w != parser confidence
w != occurrence_count
```

## 7.3. Synchronous Ignition

Динамика работает по engine ticks. Каждый tick вычисляется из одного snapshot:

```text
State_τ
  ↓
collect incoming impulses
  ↓
activation / output
  ↓
propagation
  ↓
plasticity
  ↓
decay
  ↓
lifecycle / GC decisions
  ↓
Workspace update
  ↓
simultaneous commit
  ↓
State_(τ+1)
```

Это исключает зависимость результата от порядка обхода элементов.

Новый сигнал проходит не более одного нового ребра за tick.

## 7.4. Workspace

Workspace — не отдельная память, а текущая активная область AH:

```text
Workspace_t = { e | x_e > threshold }
```

В нём естественно остаются последние релевантные события и связанные знания. Именно поэтому системе не требуется отдельное окно последних реплик.

## 7.5. Decay и reactivation

После сильного нового input начинается новый decay epoch. Слабый вход может увеличить `x`, но не обязан сбрасывать затухание. Reactivation определяется сравнением силы нового воздействия с ожидаемой потерей без него.

Численная форма `f` и decay-функции конфигурируема; архитектурно важно разделение:

```text
activation f
!=
decay
```

## 7.6. Hebbian plasticity

Положительное усиление существующей связи происходит только при новой совместной activation/reactivation обоих endpoint на одном tick:

```text
a_A(τ)=1 AND a_B(τ)=1
→ increase L.w
```

Остаточное `x > 0` не является новым Hebbian event.

Если `B` активировался только из-за propagation от `A` на следующем tick, связь автоматически не усиливается. Иначе spreading activation сам бесконечно укреплял бы собственные пути.

Если activation event есть ровно у одного endpoint, допускается слабая depression. Инактивность обоих сама по себе связь не ослабляет.

Hebbian-механизм не создаёт новые semantic relations: он изменяет вес уже существующей связи.

## 7.7. Lifecycle и забывание

Новые факты могут проходить локальный lifecycle `NEW → REINFORCED → CONSOLIDATED`. Общий GC удаляет потерянные или структурно осиротевшие элементы по правилам памяти.

Долгое отсутствие активации само по себе не является основанием удалить закреплённое знание.

Если materialized derived fact теряет все допустимые proof-supports, он теряет основание и далее обрабатывается обычным lifecycle/GC.

# 8. Recall, GoalSpec и символический вывод

## 8.1. Recall и Inference разделены

Recall отвечает на вопрос:

> Что стало релевантным из-за текущего возбуждения?

Inference отвечает:

> Что формально следует из уже представленных фактов и правил?

Ассоциативная активация определяет релевантность и порядок исследования, но не заменяет proof.

## 8.2. GoalSpec

Запрос пользователя компилируется в `GoalSpec`. Цель не только задаёт условие остановки, но и управляет вниманием.

Когнитивный цикл:

```text
prompt seed
→ propagation
→ focus
→ GoalSpec evaluation
→ узкий внутренний memory query
→ сильный query seed
→ propagation
→ новый focus
→ ...
```

Внутренний query строится только из текущей цели, bindings, активных структур и текущего подцеля. Он не является произвольным глобальным чтением всей AH.

## 8.3. Стратегия proof search

Базовая стратегия:

```text
backward goal decomposition
+
forward proof validation
```

Пример:

```text
Goal: MORTAL(Иван)

rule:
HUMAN($0) -> MORTAL($0)

backward:
нужен HUMAN(Иван)

forward validation:
HUMAN(Иван) + rule
→ MORTAL(Иван)
```

Поиск должен зависеть от глубины доказательства, релевантного branching и числа bindings, а не от общего размера AH.

## 8.4. Индексы

Допустимы технические индексы:

```text
predicate -> propositions
m -> propositions, где m является actant
rule head -> rules
S -> lexical/semantic bindings
```

Индекс ускоряет доступ, но не является второй памятью, RAG-слоем или источником истины.

## 8.5. Proof проходит через возбуждение памяти

Логический поиск не должен быть «тихим» обходом графа. Каждый подтверждённый шаг доказательства получает сильное возбуждение, после чего обычная AH-динамика может активировать связанные детали и сместить focus.

Proof trace хранится отдельно для диагностики и объяснения результата.

# 9. Логический слой

## 9.1. Формулы

Атомарный факт остаётся `N`. Составная логическая конструкция имеет корневой `g`.

```text
WORK(server)        → atomic N
NOT(WORK(server))   → g_NOT(...)
AND(A,B)            → g_AND(...)
FORALL(...)         → g_FORALL(...)
```

Нотация формул — компактное описание семантики, а не параллельная модель данных.

## 9.2. Bound variables

Переменная квантора не является AH-элементом и не получает глобальный UID.

Операнд формулы может быть:

```text
AHRef(uid)

BoundVar(
    local_id,
    sort
)
```

Пример:

```text
FORALL $0:
    HUMAN($0)
    ->
    MORTAL($0)
```

`$0` обозначает тождество placeholder внутри одного scope. Две `$0` в разных формулах — разные переменные.

В runtime reasoner создаёт временный `BindingEnvironment`:

```text
$0 -> AHRef(m_ИВАН)
```

Binding не записывается обратно в каноническую формулу, не получает возбуждение и исчезает после завершения proof scope.

## 9.3. Open-world semantics

Отсутствие доказательства не равно отрицанию.

```text
not PROVED(P)
!=
PROVED(NOT(P))
```

Для `EXISTS` требуется найденный witness. Не найденный witness означает `UNKNOWN`, а не `FALSE`.

`FORALL` не доказывается перечислением всех известных примеров и отсутствием контрпримера; требуется явное универсальное правило или формальный proof.

## 9.4. Отрицание и refutation

Объектное отрицание:

```text
NOT(P)
```

отличается от опровержения конкретной ранее сохранённой proposition:

```text
FALSE(N_old)
```

`NOT(P)` является частью содержания. `FALSE(N_old)` — meta-operation над конкретным `N` и его допустимостью как premise.

## 9.5. Scope

Порядок операторов сохраняется структурно.

```text
«Не все сотрудники пришли»
→ NOT(FORALL(... CAME ...))

«Все сотрудники не пришли»
→ FORALL(... NOT(CAME) ...)
```

Условное и hypothetical content не материализуется как обычные факты:

```text
«Если P, то Q»
→ IMPLIES(P,Q)

«Предположим P»
→ локальный hypothetical scope
```

## 9.6. OR и XOR

Inclusive OR хранится как `OR(A,B)`. Ветви не становятся отдельными asserted facts.

Exclusive OR не требует отдельного canonical оператора:

```text
XOR(A,B)
≡
AND(
    OR(A,B),
    NOT(AND(A,B))
)
```

В open-world semantics:

```text
OR(A,B) доказано, если доказана хотя бы одна ветвь.

XOR(A,B) доказано, если:
A PROVED и B FALSE
или
B PROVED и A FALSE.
```

`UNKNOWN` не заменяет `FALSE`.

Reasoner поддерживает proof by cases. Временные branch assumptions существуют только внутри локального proof scope и не записываются в canonical AH.

## 9.7. Свойства отношений

Транзитивность, симметричность и другие логические свойства задаются явно в `InferenceSchemaRegistry`, keyed by canonical `L.ID` или `T.UID`.

```text
TRANSITIVE
SYMMETRIC
ASYMMETRIC
REFLEXIVE
IRREFLEXIVE
FUNCTIONAL
INVERSE_OF(...)
```

Неизвестное отношение по умолчанию не получает специальных inference rules.

Примеры:

```text
IS-A   → TRANSITIVE
BEFORE → TRANSITIVE
PARENT_OF → not transitive
CAUSE  → not automatically transitive
```

## 9.8. Причинный поиск

Из:

```text
CAUSE(A,B)
CAUSE(B,C)
```

не создаётся обычный `CAUSE(A,C)` автоматически. Можно вернуть causal path и различить:

```text
direct cause: B
upstream / indirect cause: A
```

Обратный traversal по incoming `CAUSE` ищет уже поддержанные cause candidates, но сам по себе не доказывает новое causal relation.

## 9.9. Counterfactual reasoning

Контрфакт выполняется в локальном overlay-контексте, а не в копии всей AH:

```text
CounterfactualContext
├── assumptions
├── suppressed_supports
├── local_bindings
└── local_derived
```

Явные counterfactual assumptions локально перекрывают несовместимые facts. Несколько assumptions применяются одновременно.

Если старый derived fact зависит только от подавленной premise, этот support внутри counterfactual world считается недействительным. Независимые supports сохраняются.

Контрфактуальные выводы не материализуются в factual AH.

Архитектура моделирует логическое рассуждение при явно изменённых условиях, а не общую симуляцию причинного мира.

## 9.10. Modal и attitude scope

Конструкции вида:

```text
POSSIBLE(P)
BELIEVES(A,P)
REQUIRED(P)
PERMITTED(P)
```

нужны прежде всего для защиты памяти от ложной интеграции вложенного `P` как факта.

```text
BELIEVES(Анна,P) != P
POSSIBLE(P)      != P
REQUIRED(P)      != P
```

Полный modal reasoner не требуется. Такие propositions участвуют в proof только для соответствующей цели, например «считает ли Анна, что P?».

## 9.11. Meta-propositions

`N` является допустимым аргументом другого `N/g`:

```text
FALSE(N42)
CONTRADICTS(N42,N57)
SAID(Анна,N42)
```

Semantic proposition и конкретный акт её произнесения различаются:

```text
N → содержание
H → occurrence сообщения
```

Это позволяет отдельно исправлять содержание и конкретный акт коммуникации.

Самоссылочные truth-paradoxes не входят в reasoning scope.

## 9.12. Сравнительные отношения

Явно сообщённое сравнение можно хранить как обычную relation/proposition:

```text
TALLER_THAN(Иван, Пётр)
OLDER_THAN(Иван, Алексей)
```

Универсальная арифметика сравнений, constraint solving и автоматический расчёт разностей не являются обязанностью памяти. Производный математический вывод выполняется только при наличии явно зарегистрированного rule/schema.

# 10. Conflict Engine

## 10.1. Представление конфликта

После достаточного identity, time и context resolution взаимоисключающие expressions объединяются `k`:

```text
k_CONFLICT
Mt.TYPE = CONFLICT
members = {expr_1, expr_2, ...}
```

`k` только делает conflict set адресуемым; operational semantics выполняет Conflict Engine.

## 10.2. Условия конфликта

Для пары `P` / `NOT(P)` после корректного resolution конфликт прямой.

Для двух положительных propositions с разными значениями дополнительно требуется явно известная взаимоисключаемость или `FUNCTIONAL` semantics соответствующего slot/predicate.

Само совпадение predicate не делает два значения конфликтующими.

## 10.3. Конфликт не выбирает победителя

Ни одна версия не становится истинной только потому, что она:

- новее;
- чаще повторялась;
- сильнее возбуждена;
- имеет больший `w`.

Повтор одной стороны сам по себе конфликт не снимает.

Конфликт разрешается явной коррекцией, уточнением identity, temporal scope или другого relevant context.

## 10.4. Поведение reasoner-а

Expression из unresolved conflict не используется как безусловная premise обычного proof.

Если цель зависит от такого факта и независимого непротиворечивого пути нет, система требует clarification.

Reasoning паранепротиворечив:

```text
P
NOT(P)
```

не позволяют вывести произвольный `Q` и не блокируют независимые области памяти.

# 11. Ассоциативный режим

## 11.1. Ассоциация как пересечение представлений

Игра в ассоциации не является поиском логического следствия `A -> B`. Система независимо разворачивает связанные представления двух исходных понятий и ищет общее содержание:

```text
expand(A) ∩ expand(B) != ∅
```

Пример:

```text
ВОРОНА
→ ... → НОЖКИ

ПИСЬМЕННЫЙ СТОЛ
→ ... → НОЖКИ
```

`НОЖКИ` — основание ассоциации.

Общим узлом может быть любой полноправный элемент AH, включая `S`. Поэтому лексическое пересечение может быть значимо даже тогда, когда semantic identity двух употреблений различается.

## 11.2. Goal-driven associative search

Ассоциативный запрос получает собственный GoalSpec, например:

```text
FIND_ASSOCIATIVE_CONNECTION(A,B)
```

Оба понятия получают сильное возбуждение. GoalSpec может формировать дополнительные узкие memory queries по мере смещения focus.

Найденная связь остаётся ассоциативной и не превращается в логическое доказательство.

## 11.3. Направление связи и направление возбуждения

Логическая направленность relation и распространение возбуждения разделены.

```text
A CAUSE B
```

не означает `B CAUSE A`, но возбуждение может распространяться от `B` к `A`, потому что эффект способен напомнить о причине.

Для canonical `L` направление задаётся `(e1,e2)`, а activation engine может иметь отдельные `forward_gain` и `backward_gain`.

## 11.4. Эпизодический слой

Механизм пересечения не требует отдельного типа «ассоциация». Политика того, считать ли эпизодический `H` достаточным основанием для конкретного пользовательского режима ассоциаций, может задаваться поверх общего structural search и не меняет базовую динамику AH.

# 12. Context Projector и основная LLM

## 12.1. AgentContext

Основная LLM получает человекочитаемую проекцию активной семантики, а не внутренний DSL и не полный граф AH.

Контекст формируется детерминированно из:

- актуального Workspace;
- доказанных inference results;
- необходимых причинных, временных и логических связей;
- текущего запроса.

Обычный cognitive path не даёт основной LLM произвольного доступа к глобальной памяти.

## 12.2. История возвращается через память

Если предыдущая реплика важна, её semantic structures остаются активными и попадают в AgentContext. Если она потеряла релевантность, она не занимает контекст только потому, что была недавно.

## 12.3. Документы

Документ обрабатывается полностью, затем semantic consolidation связывает его факты, identity, coreference, temporal и causal structures.

Для пересказа исходный документ активируется по provenance/source scope, после чего в Workspace попадает связанная компактная семантика.

Основной LLM передаётся формализованное содержание, а не автоматически извлечённые raw chunks. Причинные, временные и логические отношения сохраняются в проекции, поэтому документ не превращается в неупорядоченный набор фактов.

## 12.4. Ответ агента

Ответ основной LLM локально разбирается и записывается как пережитый опыт в `H`. Он не получает автоматического статуса нового знания в `C/P`.

# 13. Persistence, индексы и границы ответственности

## 13.1. Единственный владелец canonical mutations

Все канонические изменения проходят через `AH Core`. Parser, БЯМ, reasoner, Workspace и внешняя LLM не пишут память напрямую.

Высокоуровневые операции могут использовать DSL/API, но финальная mutation выполняется каноническими операциями AH Core.

## 13.2. Runtime indexes

Индексы существуют только для ускорения доступа. Они могут быть пересозданы из canonical AH и не считаются отдельной памятью.

## 13.3. Provenance и proof-supports

Для materialized derived facts сохраняются ссылки на supports, чтобы поздняя correction/refutation могла инвалидировать только зависимые основания.

Удаление или изменение одной premise не должно уничтожать independently supported fact.

## 13.4. Диагностика

UID trace, proof trace, parser diagnostics, runtime telemetry и audit log находятся вне `H`. Они описывают работу системы, а не пережитый семантический опыт.

## 13.5. Локальная автономность памяти

Каноническая AH, reasoning, activation и semantic probes находятся локально. Во внешний генеративный сервис передаётся только временный AgentContext, необходимый для конкретного ответа.

# 14. Архитектурные инварианты

Ниже — ограничения, нарушение которых меняет смысл системы.

1. `LLM != memory`: основная LLM не владеет долговременной памятью.
2. Канонические знания существуют только в `AH`; runtime state не заменяет память.
3. `Recall != Inference`: ассоциативная релевантность не является доказательством.
4. `activation != truth`; `w != confidence`.
5. Один `N` — одна реализация одного `T`.
6. Новый естественно-языковой predicate обычно расширяет `T/N`, а не `L.ID`.
7. `g` используется только для зарегистрированной функциональной/логической семантики.
8. Только `m`, `k`, `N` имеют `Pr/Mt`.
9. Неоднозначность не разрешается произвольным угадыванием.
10. БЯМ предлагает только bounded semantic cues и не изменяет AH напрямую.
11. Вложенное reported/hypothetical/modal content не становится обычным factual premise автоматически.
12. Отсутствие доказательства не считается отрицанием.
13. Conflicted premise не используется как безусловное основание proof.
14. Counterfactual assumptions действуют только внутри локального proof context.
15. BoundVar не является AH-узлом и связывается с конкретным значением только в runtime BindingEnvironment.
16. Hebbian plasticity изменяет веса существующих путей, но не создаёт новые semantic relations.
17. Собственный ответ агента записывается в `H` и не подтверждает автоматически `C/P`.
18. Основная LLM получает только детерминированную проекцию активной семантики, а не полный граф и не длинную историю.

# Часть II. Контракты реализации

# 16. Границы модулей и владение состоянием

## 16.1. Единственный владелец canonical mutations

**ОБЯЗАТЕЛЬНО.** Создание, изменение, merge, rewiring и физическое удаление canonical AH выполняет только `AH Core` через валидированный mutation plan.

Остальные модули могут:

```text
читать AH;
создавать кандидаты;
строить runtime indexes;
возбуждать узлы;
возвращать proof/result;
предлагать mutation plan;
```

но не должны изменять canonical storage напрямую.

Рекомендуемый поток записи:

```text
CandidateIR / ConsolidationResult
    ↓
MutationPlan
    ↓
full validation
    ↓
AHCore.commit_atomic(plan)
    ↓
Persistence transaction
    ↓
activation seed / index update
```

Если commit не прошёл полностью, память должна оставаться в предшествующем согласованном состоянии.

## 16.2. Рекомендуемые логические компоненты

Названия классов не нормативны, но границы ответственности — нормативны.

- `TextSensory`: выделение `s`, нормализация текста, provenance offsets. Не принимает семантические решения.
- `DeterministicParser`: morphology, clauses, NP, predicate frames, scope candidates. Не пишет canonical AH.
- `SemanticProbeService`: узкие bounded semantic decisions. Не генерирует полный граф, UID или repair.
- `FormalizationEngine`: сборка `CandidateIR`. Не разрешает global identity произвольно.
- `SemanticConsolidator`: identity, coreference, dedup, linking, ambiguity resolution. Не выполняет общий логический вывод.
- `AHCore`: canonical ownership, UID, atomic mutations. Не вызывает Main LLM как fallback.
- `Persistence`: долговременное сохранение AH и технических индексов. Не определяет truth/relevance.
- `IgnitionEngine`: synchronous activation propagation. Не считает activation доказательством.
- `Workspace`: текущая активная область памяти. Не является отдельной truth store.
- `GoalCompiler`: перевод пользовательского запроса в `GoalSpec`. Не читает всю AH произвольным scan.
- `Reasoner`: rule-driven proof, bindings, branch/counterfactual scopes. Не подменяет proof graph reachability.
- `AssociationCoordinator`: поиск пересечения активированных областей. Не объявляет ассоциацию логическим выводом.
- `ContextProjector`: human-readable projection активной семантики. Не делает скрытый RAG по raw source.
- `LifecycleGC`: lifecycle, forgetting, physical deletion. Не использует inactivity как единственный критерий semantic depression.
- `Diagnostics`: trace, provenance, counters, snapshots. Не влияет на canonical semantics.

## 16.3. Основные runtime-контейнеры

Рекомендуется явно разделить типы runtime-состояния:

```text
FormalizationBatch
CandidateIR
ConsolidationState
DiscourseRef
DiscourseAnchor
WorkspaceState
GoalSpec
ProofContext
BindingEnvironment
CounterfactualContext
BranchContext
ProofSupport
AssociationSearchState
ProjectionBundle
```

Ни один из этих классов сам по себе не расширяет множество `q` canonical AH.

# 17. Канонический data contract

## 17.1. Дисциплина `N / T / L / g / k`

**ОБЯЗАТЕЛЬНО.** Логическая запись в документации является нотацией, а не вторым форматом памяти.

```text
atomic predicate fact
→ один N как реализация одного T

новый естественно-языковой predicate
→ T/N
→ не новый L.ID автоматически

structural engine relation
→ L с зарегистрированным L.ID

functional/logical composition
→ g с зарегистрированным g.ID

group/addressable set
→ k
```

Пример:

```text
WORK(server)
```

означает canonical `N` с `T_WORK`, а:

```text
NOT(WORK(server))
```

означает compound expression, корнем которого является зарегистрированный `g_NOT`, operand которого ссылается на `N_WORK` или шаблонную proposition в scoped formula.

## 17.2. FunctionRegistry

**ОБЯЗАТЕЛЬНО.** Новый `g.ID` допустим только если существует детерминированный контракт:

```text
FunctionRegistry[g_id] = {
    operand_schema,
    validator,
    evaluator / reasoner_handler,
    canonicalizer,
    projector,
    persistence_codec
}
```

Нельзя создавать `g` только как красивую метку без машинной семантики.

Минимально предусмотренные логические функции:

```text
NOT
AND
OR
IMPLIES
FORALL
EXISTS
```

Допустимы специализированные functional wrappers, если они реально имеют engine semantics, например temporal `START/STOP/CONTINUE` либо counterfactual scope marker. Обычный семантический глагол `BELIEVE`, `SAY`, `REQUIRE` по умолчанию остаётся `T/N` с proposition-actant, а не превращается в новый `g.ID`.

## 17.3. InferenceSchemaRegistry

`T`, `L`, `g` и `s` не получают произвольные `Pr/Mt`. Специальные логические свойства relation/predicate хранятся в детерминированном schema registry:

```text
InferenceSchemaRegistry[canonical_id] = {
    transitive?,
    symmetric?,
    asymmetric?,
    reflexive?,
    irreflexive?,
    functional?,
    inverse_of?,
    additional_rule_handlers...
}
```

Ключом может быть `L.ID` либо `T.UID`.

Если свойства нет в registry, reasoner **не должен угадывать его** по имени или surface semantics.

## 17.4. `k` не является скрытым оператором

`k` используется как адресуемая группировка:

```text
k_AMBIGUOUS
k_CONFLICT
```

Сама operational semantics ambiguity/conflict реализуется соответствующим движком. Наличие `k` не превращает группу в логическую функцию.

## 17.5. Provenance и support как метаданные поддержки

Для каждого воспринимаемого или производного знания должна быть возможность восстановить происхождение:

```text
source / batch / message / document
source span или raw-source handle
creation reason
independent supports
proof supports
```

Для materialized inference важно различать:

```text
canonical semantic identity N
и
набор supports, делающих N допустимым сейчас
```

Один и тот же `N` может иметь несколько независимых supports. Инвалидируется support, а не обязательно сразу сам `N`.

# 18. Формализация: контракт для кода

## 18.1. Последовательность обработки

Целевой pipeline:

```text
raw input
→ lexical recovery candidates (only for noisy/unknown tokens)
→ lexical/morphological analysis
→ clause segmentation
→ NP / predicate-frame extraction
→ discourse/ellipsis frame completion where structurally licensed
→ actant-role candidates
→ scope/coordination candidates
→ deterministic constraints
→ bounded semantic probes where necessary
→ CandidateIR
→ batch-level semantic consolidation
→ MutationPlan
→ atomic canonical commit
→ activation seed
```

Основная идея: модель вызывается **после** алгоритмического сужения задачи, а не вместо него.

## 18.2. Требование к bounded semantic probe

Проба должна получать минимальную задачу, например:

```text
Does the statement allow both alternatives to be true?
A. YES
B. NO
C. UNCLEAR
```

или:

```text
Which candidate is the referent of the highlighted pronoun?
A. candidate_1
B. candidate_2
C. unresolved
```

Сервисные prompts рекомендуется держать простыми и на английском языке, ответы — фиксированный protocol enum. Это снижает семантическую нагрузку на локальную SLM.

БЯМ запрещено:

```text
назначать UID;
создавать полный T/N/L graph с нуля;
писать в persistence;
чинить AH скрытым repair;
выбирать truth;
делать global memory search;
```

## 18.3. Никаких marker-word fallback

Слова и конструкции вроде:

```text
если
при условии
в зависимости от
либо
сказал
якобы
не
```

являются только cues. Нельзя строить архитектуру на таблице `keyword -> operator`.

Например `в зависимости от` может выражать условность, параметризацию, функциональную зависимость либо обычное описание. Parser должен сначала построить структурные кандидаты.

## 18.4. Максимальная формализация без спекулятивной записи

Цель — сохранить доступный смысл максимально полно, но не создавать все мыслимые interpretations как одновременно factual.

```text
однозначно разрешено
→ canonical structure

несколько живых interpretations
→ ambiguity / scoped alternatives

нет основания
→ не canonical fact
```

GC не является способом исправлять плохой parsing постфактум.

## 18.5. CandidateIR

Рекомендуется иметь промежуточное представление, которое способно хранить:

```text
candidate predicates
candidate actants
candidate semantic entities
scope tree
coordination tree
logical operators
DiscourseRef
source spans
provenance
ambiguity alternatives
confidence только технического classifier-а, если нужно для выбора probe,
но не как truth score AH
```

CandidateIR существует только до consolidation/commit.

## 18.6. Batch semantics

```text
message
→ parse entire message
→ consolidate message
→ commit

document
→ parse entire document
→ keep unresolved discourse refs
→ consolidate entire document
→ commit
```

Нельзя окончательно фиксировать identity только потому, что ближайший antecedent найден в первом абзаце, если документ ещё не обработан и дальнейший текст способен изменить resolution.

## 18.7. Atomic commit

Перед записью подграфа проверяются:

```text
T resolution
actant compatibility
scope validity
identity/coreference decisions
domain routing
UID references
dedup
registry compatibility
provenance completeness
```

Только затем весь mutation plan коммитится одной логической транзакцией.

## 18.8. Lexical Recovery для зашумлённого ввода

Lexical Recovery — отдельный preprocessing-слой перед semantic formalization. Он
не является semantic parser и не имеет права создавать факты, UID или canonical
AH-элементы.

Целевой контракт:

```text
unknown/noisy token
→ Levenshtein candidate generation
→ contextual embedding rerank
→ morphology compatibility validation
→ EXACT | CORRECTED_HIGH_CONFIDENCE | AMBIGUOUS | UNKNOWN_TOKEN
→ ordinary formalization
```

Роли компонентов разделены жёстко:

- расстояние Левенштейна используется только для генерации орфографически
  близких кандидатов;
- embeddings используются только для контекстного ранжирования уже суженного
  набора кандидатов и не доказывают lexical identity;
- морфология проверяет грамматическую совместимость кандидата с локальным
  контекстом;
- semantic commitment появляется только в обычном Formalization/Consolidation
  pipeline.

Главный safety-инвариант: ложное автоматическое исправление опаснее сохранённого
`UNKNOWN_TOKEN`, потому что ошибочная нормализация способна породить ложное
каноническое знание. Поэтому при нескольких конкурентных кандидатах система
сохраняет ambiguity/unknown и не угадывает.

## 18.9. Эллипсис и восстановление неполного frame

Эллиптическая конструкция не должна чиниться keyword-trigger подстановкой
конкретного глагола. Сначала clause segmentation обязана сохранить отдельный
peer-clause без собственного predicate frame, после чего discourse reconstruction
может использовать уже разобранный antecedent frame как ограниченный источник
семантики.

Пример:

```text
Иван купил книгу, а Мария журнал.

CL1: BUY(SUBJECT=Иван, OBJECT=книга)
CL2: predicate=?, SUBJECT=Мария, OBJECT=журнал

frame completion
→ BUY(SUBJECT=Мария, OBJECT=журнал)
```

При восстановлении допустимы только роли, уже лицензированные antecedent frame;
явно заполненные роли второй clause заменяют соответствующие antecedent fillers,
а действительно опущенные роли могут наследоваться. Это runtime reconstruction до
`CandidateIR`/canonical commit, а не новый canonical node kind.

Пропозициональные маркеры обрабатываются отдельно:

```text
Иван купил книгу, а Мария — нет.
→ BUY(Иван, книга)
→ NOT(BUY(Мария, книга))

Иван купил книгу, а Мария тоже.
→ BUY(Иван, книга)
→ BUY(Мария, книга)
```

Если antecedent сам находится в неоднозначном, modal/hypothetical или ином scope,
reconstruction обязана сохранять этот scope либо fail-closed; эллипсис не даёт
права материализовать вложенное содержание как ordinary factual premise.

# 19. Identity, лексическая композиция и coreference

## 19.1. `s` — только лексическая единица

Phrase-level `s` запрещён.

```text
«подводная лодка»
→ s_ПОДВОДНЫЙ + s_ЛОДКА
→ возможно один m_ПОДВОДНАЯ_ЛОДКА

«Алексей Петров»
→ несколько s
→ один m_PERSON

«красная лодка»
→ m_ЛОДКА + predicate/property RED
→ новый phrase-m необязателен
```

## 19.2. Identity resolver

Resolver должен комбинировать признаки, а не использовать имя как ключ:

```text
aliases / lexical mentions
properties
relations
known facts
time
source/discourse position
activation/workspace relevance
semantic type constraints
```

Активация может влиять на порядок кандидатов, но не доказывает identity.

## 19.3. Merge

Если duplicate identity доказана:

```text
survivor UID = deterministic older canonical UID
rewire all references
merge aliases/properties/supports
run N dedup
delete obsolete duplicate UID after successful rewiring
write MERGE event to external audit/session log
```

После merge эквивалентный `N` переиспользуется, `occurrence_count++`, выполняется обычная reactivation. `w` не является счётчиком повторов.

Несовместимые значения после merge направляются в Conflict Engine.

## 19.4. Late split

**ОТЛОЖЕНО.** Полноценное расщепление ошибочно объединённой старой identity назад на несколько `m` не является обязательным контуром. Архитектура не должна делать невозможным будущий split, но текущий код не обязан автоматически переигрывать всю историю зависимостей.

## 19.5. Delayed coreference

Внутри сообщения/документа unresolved mention представляется staging descriptor:

```text
DiscourseRef {
    local_id
    sort
    mentions[]
    grammatical_constraints
    semantic_constraints
    candidate_bindings[]
}
```

`DiscourseRef`:

```text
не AH node;
не имеет canonical UID;
не возбуждается;
не участвует в Hebbian;
не считается фактом.
```

Поздний antecedent может появиться через много предложений. До конца batch resolver имеет право удерживать ссылку неразрешённой.

## 19.6. Истинно неизвестный участник

Для:

```text
Кто-то вошёл. Он сел.
```

не создаётся `m_UNKNOWN_PERSON`. После consolidation допустима формула:

```text
EXISTS $0:
    ENTER($0)
    AND
    SIT($0)
```

Если позже появляется:

```text
Это был Иван.
```

identity resolution связывает existential referent с `m_ИВАН`, после чего ground predicates могут быть materialized/rewired с сохранением provenance.

## 19.7. Cross-turn discourse anchor

Незавершённая existential ссылка может переживать границу turn через runtime handle:

```text
DiscourseAnchor
→ g_EXISTS
→ BoundVar(local_id)
```

Anchor не canonical. Он восстанавливается из релевантной активной структуры. Если связь с прошлым referent уже неоднозначна — clarification, а не arbitrary global bind.

# 20. Время и state tracking

## 20.1. TIME как обычный semantic object

Новый canonical тип времени не вводится. Temporal object — обычный `m`, на который `N` ссылается через `TIME`.

Рекомендуемые данные `m_TIME.Pr`:

```text
kind = POINT | INTERVAL
start
end
precision
timezone
```

Частичное время остаётся частичным:

```text
12:00
→ time-of-day without invented date

март
→ month without invented year
```

## 20.2. Время не прикрепляется ко всему

Technical ingestion timestamp всегда может существовать в provenance, но semantic `TIME` создаётся только если время:

```text
явно сказано;
различает события/состояния;
нужно для conflict resolution;
нужно для reasoning;
нужно для identity/context resolution.
```

Приветствие не должно автоматически порождать semantic fact о точном времени только потому, что система знает timestamp сообщения.

## 20.3. Relative-time anchors

Приоритет:

```text
1. explicit anchor внутри текста/discourse
2. source/document timestamp
3. timestamp текущего H-experience
4. unresolved
```

Нельзя придумывать отсутствующую дату/год.

## 20.4. Temporal relations

Из нормализованных points/intervals deterministic temporal reasoner может выводить:

```text
BEFORE
AFTER
OVERLAP
CONTAINS
и другие зарегистрированные temporal relations
```

Они при необходимости materialize как обычные `N` с proof provenance. Новый системный `L.ID` только ради каждого temporal predicate не создаётся.

`FOLLOW` и физическое время различны. `FOLLOW` задаёт структурную/эпизодическую последовательность, а не timestamp или duration.

## 20.5. State intervals

State-like occurrence может иметь открытый интервал:

```text
WORK(server)
TIME = [t_start, ?]
```

Transition закрывает старое состояние и открывает новое:

```text
WORK(server)       [t_start, 15:00)
NOT(WORK(server))  [15:00, ?]
```

Текущее состояние определяется coverage временного интервала, а не последним textual mention.

## 20.6. START / STOP / CONTINUE / AGAIN / NO_LONGER

Поддерживаемая семантика:

```text
«начал P»       → START(P)
«перестал P»    → STOP(P)
«всё ещё P»     → CONTINUE(P)
«снова P»       → AGAIN(P)
«больше не P»   → NO_LONGER(P)
```

`AGAIN(P)` требует предыдущего периода `P`, но сам по себе не доказывает промежуточный `NOT(P)`.

`NO_LONGER(P)` содержит предыдущий `P` и текущий `NOT(P)` в transition semantics.

`никогда P`:

```text
NOT(EXISTS t in relevant_past: P@t)
```

При open-world semantics простое отсутствие эпизодов `P` не доказывает `NEVER(P)`.

**Статус реализации v0.25.25: ЧАСТИЧНО ЗАКРЫТО.** Пять фазовых операторов
`START/STOP/CONTINUE/AGAIN/NO_LONGER` проходят source formalization, canonical
wrapper и state runtime end-to-end. Отдельная семантика `никогда P` пока не
формализуется как `NOT(EXISTS t ...)`: текущий общий negation path не эквивалентен
этому temporal scope. Этот остаток вынесен в semantic-composition roadmap.

## 20.7. Temporal mode occurrence-а

Нужно различать:

```text
STATE
EVENT
PROCESS
TRANSITION
```

но не как глобальное свойство `T`. Один predicate может иметь разные temporal readings. Классификация относится к конкретному proposition/event frame и нужна только когда влияет на persistence/interval/transition reasoning.

Определение:

```text
morphology/aspect/tense
→ predicate frame
→ deterministic narrowing
→ bounded probe if needed
```

**Статус реализации v0.25.24: ЗАКРЫТО.** Классификация выполняется отдельным
pre-integration проходом только для occurrence, где TIME/DURATION делает различие
наблюдаемым. Устойчивые morphology/frame cases не вызывают модель; остаток проходит
один closed-choice semantic probe с `AMBIGUOUS` и fail-closed. Режим хранится в
metadata конкретного `N`, входит в его semantic identity и не переносится на `T`.

# 21. Activation, Workspace и пластичность

## 21.1. Activation не truth

`x` означает текущую когнитивную доступность/возбуждение. Большое `x` не означает, что proposition истиннее другой.

Аналогично `w` связи отражает динамику памяти/ассоциативную силу, а не confidence.

## 21.2. Synchronous tick

**ОБЯЗАТЕЛЬНО.** Обновление activation выполняется синхронными tick-ами. Архитектурный runtime ориентируется на тик порядка одной секунды; точная физическая частота может быть конфигурируемой при сохранении synchronous semantics.

Важна семантика «состояние на `τ` → вычисление входов → новое состояние на `τ+1`», а не порядок обхода объектов в Python-цикле.

## 21.3. Seed types

Минимально различаются конфигурируемые gain:

```text
prompt_seed_gain
goal_query_seed_gain
```

Начальное правило:

```text
goal_query_seed_gain = prompt_seed_gain
```

но параметры хранятся отдельно, чтобы их можно было независимо калибровать.

Сильное упоминание `S` в prompt должно успевать воздействовать на Workspace до формирования ответа.

## 21.4. Workspace

Workspace — не отдельная память и не фиксированный `top-N`. Это floating active-memory window, возникающее из `x`, propagation, decay и текущего focus.

Нормальная когнитивная селекция должна происходить динамически. Технический safety cap возможен для защиты интерфейса/контекстного окна, но не должен быть главным алгоритмом релевантности.

Workspace фактически выполняет роль «сцены»; отдельный canonical `SCENE`/`SCENE_START`/`SCENE_END` не вводится.

## 21.5. Decay/reactivation

Сохраняется механика v3/current runtime:

```text
sliding activation floor;
reactivation_min_input;
floor update от нового prompt/impulse;
ранняя слабая деградация;
затем более крутой спад;
```

Конкретные коэффициенты — конфигурируемые hyperparameters и должны измеряться, а не зашиваться в semantic rules.

## 21.6. Hebbian event rule

Hebbian update относится только к уже существующему `L(A,B)`.

Квалифицирующее событие усиления:

```text
a_A(τ) = 1
AND a_B(τ) = 1
AND L(A,B) exists
→ h_plus(L.w)
```

где `a_i(τ)` означает **новую activation/reactivation event на данном tick**, а не просто `x_i > 0`.

Если:

```text
A активирован на τ
B активирован только распространением от A на τ+1
```

это само по себе не усиливает `L(A,B)`. Иначе propagation стал бы бесконечно самоподкрепляться.

Hebbian rule **не создаёт новый L** и не изобретает новый relation ID. Топология создаётся perception/integration, пластичность меняет `w` существующего пути.

## 21.7. Weak/social depression

Унаследованное правило:

```text
ровно один endpoint получил activation/reactivation event на tick
→ слабое уменьшение L.w

оба inactive
→ inactivity alone не уменьшает w
```

Депрессия имеет ненулевой configurable floor и не удаляет semantic relation. Physical deletion — задача lifecycle/GC.

**Статус реализации v0.25.25: ЗАКРЫТО.** Runtime использует immutable snapshot и
simultaneous commit для каждого tick; propagation попадает только в buffer
следующего tick. `resolved_symbol` и `query_recall` имеют равное начальное значение,
но отдельные настройки. Workspace вычисляется как строгий полный набор `x > t` без
top-N. Пластичность посещает только существующие `L`, учитывает same-tick events,
игнорирует inactivity, ограничивает depression ненулевым floor и не создаёт/не
удаляет topology.

# 22. GoalSpec и generalized inference

## 22.1. GoalSpec — активный runtime-объект

GoalSpec используется не только как stop condition. Он:

```text
описывает искомое утверждение;
компилирует subgoals;
создаёт narrow internal memory queries;
проверяет достижение цели;
управляет termination;
хранит query mode: factual / proof / association / evidence retrieval и т. п.
```

## 22.2. Cognitive loop

Целевой цикл:

```text
prompt seed
→ propagation
→ focus
→ Goal evaluation
→ narrow goal-generated query
→ strong query seed
→ propagation
→ new focus
→ rule validation
→ next subgoal / success / clarification
```

Goal query может опираться на несколько активных узлов одновременно и даже на `S`. Все canonical AH nodes являются полноценными участниками memory dynamics.

## 22.3. Нет произвольного global read

Невозбуждённый граф не должен быть доступен reasoner-у через unrestricted full scan.

Разрешены технические индексы:

```text
predicate -> propositions
m -> propositions where it is actant
rule-head -> rules
S -> lexical/semantic bindings
```

но запрос к индексу должен быть выведен из текущего `GoalSpec`, focus, bindings или active structures. Index — accelerator, не вторая RAG-memory и не truth store.

## 22.4. Backward decomposition + forward proof validation

Предпочтительная стратегия:

```text
goal G
→ find admissible rule with head G
→ unify bindings
→ create premises/subgoals
→ activate/resolve premises
→ when premises are established
→ apply rule forward
→ validate G
```

Пример:

```text
Goal: MORTAL(Ivan)
Rule: HUMAN($0) -> MORTAL($0)
Binding: $0 = Ivan
Subgoal: HUMAN(Ivan)
```

После подтверждения premise rule применяется вперёд и создаёт proof step цели.

## 22.5. Proof физически проходит через Ignition

Это ключевой инвариант v4.

Нельзя выполнять «тихий» BFS/DFS по графу, а затем только нарисовать trace. Каждый подтверждённый proof step должен:

```text
получить сильную activation/focus;
пройти через обычный Ignition tick;
вызвать нормальное распространение;
сместить Workspace;
после этого открыть следующий логически допустимый шаг.
```

Побочные ассоциации могут возбуждаться и попадать в Workspace, но они не входят в proof без rule validation.

## 22.6. Совместимость с существующей relation-search эвристикой

Если в текущем коде используется reverse-distance от target для pruning/order, этот механизм можно сохранить **только как эвристику**.

```text
reverse reachability / distance
!= proof
```

Сам proof должен строиться rule-driven и подтверждаться в forward direction. Для `CAUSE` reverse traversal используется для поиска кандидатов причин, а не как новое causal доказательство.

## 22.7. Termination

Reasoner должен завершать запрос при достижении одного из явно определённых состояний:

```text
GOAL_SATISFIED
GOAL_REFUTED, если формально доказано отрицание/несовместимость по contract
UNKNOWN
CONFLICTED
CLARIFICATION_REQUIRED
BUDGET_EXHAUSTED / RESOURCE_LIMIT
```

Не следует продолжать поиск «на всякий случай» после доказанной цели, если режим запроса не требует всех альтернативных proofs.

# 23. Quantifiers, BoundVar и substitutions

## 23.1. Минимальное ядро

Поддерживаются:

```text
FORALL
EXISTS
NOT
AND
OR
IMPLIES
```

Кванторы работают в общем reasoner, а не как отдельный текстовый special-case.

## 23.2. BoundVar persistence

Переменная не является AH element и не имеет глобального UID.

Operand compound formula может быть:

```text
AHRef(uid)
или
BoundVar(local_id, sort)
```

Пример:

```text
g_FORALL
variables:
    BoundVar(0, ENTITY)
body:
    HUMAN(BoundVar(0))
    ->
    MORTAL(BoundVar(0))
```

`local_id` уникален только внутри owning scope:

```text
g_1::$0 != g_2::$0
```

## 23.3. Sort

Возможные sorts:

```text
ENTITY
PROPOSITION
TIME
VALUE
...
```

Sort — machine descriptor formula, не новый `q`.

## 23.4. Runtime BindingEnvironment

Конкретная подстановка хранится только в proof context:

```text
BindingEnvironment {
    $0 -> AHRef(m_ИВАН)
}
```

Binding:

```text
не переписывает canonical formula;
не возбуждается;
не участвует в Hebbian;
исчезает при завершении scope.
```

## 23.5. Open-world EXISTS

`EXISTS` доказан, если найден witness.

```text
не найден witness
→ UNKNOWN
```

а не FALSE.

Поиск witness начинается с наиболее селективного/relevant predicate и ограничивается текущим proof context/index query.

## 23.6. Open-world FORALL

Нельзя доказывать `FORALL` перебором всех известных объектов и отсутствием counterexample. Универсальность требует:

```text
explicit universal rule
или
formal proof соответствующего universal claim
```

## 23.7. Nested scopes

Поддерживается рекурсивная вложенность:

```text
FORALL student
    EXISTS book
        READ(student, book)
```

не эквивалентно:

```text
EXISTS book
    FORALL student
        READ(student, book)
```

Parser хранит operator tree; ambiguity находится на natural-language boundary, а не внутри уже canonical formula.

# 24. NOT, assertion scope и provenance

## 24.1. NOT против FALSE(N)

```text
«Сервер не работает»
→ NOT(WORK(server))
```

Это object-level negation.

```text
«Предыдущее утверждение было неверным»
→ FALSE(N_old)
```

Это meta-refutation конкретной proposition/support.

Эти конструкции нельзя автоматически взаимозаменять.

## 24.2. Scope дерева

```text
«Не все сотрудники пришли»
→ NOT(FORALL ... CAME)

«Все сотрудники не пришли»
→ FORALL ... NOT(CAME)
```

Отрицание не является boolean field у ближайшего `N`. Порядок операторов должен сохраняться structural tree.

## 24.3. Reported/quoted/hypothetical content

Для:

```text
Анна сказала, что сервер работает.
```

можно считать фактом событие:

```text
SAID(Анна, P)
```

но `P` остаётся embedded proposition внутри reported scope и не становится ordinary factual premise автоматически.

Аналогично:

```text
предположим P
если P, то Q
возможно P
Анна считает P
```

не должны загрязнять factual memory вложенным `P`.

## 24.4. Истина не выводится из социального механизма

AH не пытается устанавливать объективную truth по:

```text
числу свидетелей;
числу повторов;
уверенному стилю текста;
x;
w;
```

Система формализует **что утверждалось, кем и в каком scope**. Опциональная `SourcePolicy` может задаваться приложением как внешний configuration contract, но не является универсальным truth engine.

# 25. OR, XOR и branch reasoning

## 25.1. Canonical XOR

Отдельный canonical operator XOR не обязателен:

```text
XOR(A,B)
≡
AND(
    OR(A,B),
    NOT(AND(A,B))
)
```

Parser может временно использовать candidate `XOR`, затем canonicalizer разворачивает его в базовые функции.

## 25.2. Natural-language ambiguity

`или` и `либо` не гарантируют inclusive/exclusive reading. После syntax/semantic constraints при остаточной неоднозначности допускается fixed-choice probe.

## 25.3. Proof semantics

```text
OR(A,B) PROVED
если A PROVED или B PROVED
```

Для XOR:

```text
A PROVED AND B FALSE
или
B PROVED AND A FALSE
```

`UNKNOWN` не является FALSE.

## 25.4. Alternatives не становятся фактами

```text
В комнате Иван или Алексей.
```

не создаёт два ordinary factual `N`. Сохраняется scoped `OR(A,B)`.

## 25.5. Disjunctive elimination

```text
OR(A,B)
NOT(A)
→ B
```

только при admissible premises и отсутствии unresolved conflict.

## 25.6. Proof by cases

```text
OR(A,B)
A -> C
B -> C
→ C
```

Reasoner создаёт локальные `BranchContext`:

```text
branch_1 assumes A
branch_2 assumes B
```

Branch assumptions и локальные intermediate conclusions не materialize в canonical AH. Только conclusion, доказанное во всех допустимых branches, может materialize с полной provenance.

# 26. Relation properties и CAUSE

## 26.1. Conservative-by-default

Если relation property не задано в `InferenceSchemaRegistry`, reasoner не предполагает его.

```text
IS-A   → TRANSITIVE
BEFORE → TRANSITIVE, если registered для T_BEFORE
PARENT_OF → not transitive
CAUSE → not automatically transitive
```

## 26.2. CAUSE chain

Из:

```text
CAUSE(A,B)
CAUSE(B,C)
```

не материализуется ordinary `CAUSE(A,C)`.

Можно вернуть:

```text
direct cause of C: B
upstream / indirect contributor: A
causal path: A -> B -> C
```

## 26.3. Reverse causal search

Вопрос «что вызвало C?» разрешает incoming traversal:

```text
C <- A
C <- B
C <- D
```

Это retrieval already-supported causal candidates, а не proof нового обратного relation.

## 26.4. Logical vs activation direction

Canonical directed relation сохраняет logical direction. Activation engine может иметь:

```text
activation_forward_gain
activation_backward_gain
```

Поэтому `A CAUSE B` ассоциативно может возбуждать `B -> A`, но логически не становится `B CAUSE A`.

# 27. Conflict Engine

## 27.1. Conflict set

После достаточного resolution:

```text
k_CONFLICT_X
Mt.TYPE = CONFLICT
members = {expr_1, expr_2, ...}
```

Atomic expression может иметь корень `N`, compound — `g`.

## 27.2. Условия обнаружения

Проверяются:

```text
resolved identity
same predicate semantics
compatible/overlapping temporal scope
same relevant context
```

Для `P` и `NOT(P)` этого достаточно после scope resolution.

Для двух положительных разных значений дополнительно требуется schema-level взаимоисключаемость либо `FUNCTIONAL` semantics. Иначе два значения одного predicate могут быть допустимы одновременно.

## 27.3. Никакого auto-winner

Конфликт не разрешается по:

```text
новизне;
частоте;
x;
w;
порядку источников.
```

Повтор одной версии также не снимает конфликт.

## 27.4. Разрешение

Допустимые основания:

```text
explicit FALSE/refutation;
identity rewiring;
temporal clarification;
context clarification;
other formal correction.
```

## 27.5. Reasoner behavior

Expression из unresolved conflict не используется как безусловная premise обычного entailment proof.

Если goal зависит от неё и нет независимого uncontested proof path:

```text
→ CLARIFICATION_REQUIRED / CONFLICTED
```

При этом query «есть ли в памяти утверждение P?» может вернуть сохранённое `P` как stored assertion. Это отличается от «доказано ли P?».

## 27.6. Paraconsistency

```text
P
NOT(P)
```

не разрешает вывести произвольное `Q`. Conflict локализуется по зависимостям.

Независимые proofs продолжают работать.

# 28. Counterfactual proof sandbox

## 28.1. Overlay, не копия AH

Рекомендуемая runtime-структура:

```text
CounterfactualContext {
    assumptions
    suppressed_supports
    local_bindings
    local_derived
    parent_context
}
```

Canonical AH не копируется и не изменяется.

## 28.2. Local override

Явное counterfactual assumption временно подавляет только несовместимые supports в своём scope.

Определение несовместимости переиспользует Conflict Engine:

```text
same resolved entity
same predicate/slot
same temporal/context scope
incompatible value/polarity
```

## 28.3. Несколько assumptions

Все assumptions одного counterfactual clause применяются одновременно в одном world overlay. Архитектура не вводит искусственный лимит количества переменных; practical limit определяется runtime budget.

## 28.4. Derived-support invalidation

Если старый materialized conclusion поддерживался только premise, suppressed внутри overlay, этот support недопустим внутри counterfactual world.

Independent support сохраняется.

## 28.5. Граница возможностей

Поддерживается:

```text
explicit assumptions;
local overrides;
dependency-aware support filtering;
ordinary rule reasoning в изменённом context.
```

**НЕ ВХОДИТ:**

```text
Structural Causal Model;
автоматическое угадывание скрытых interventions;
вывод причинных законов из корреляций;
симуляция всех возможных изменений мира.
```

# 29. Modal/attitude scope и meta-propositions

## 29.1. Modal logic ограничена защитой памяти

```text
POSSIBLE(P)
BELIEVES(A,P)
REQUIRED(P)
PERMITTED(P)
```

не усиливают proof ordinary `P`.

Они нужны прежде всего чтобы nested content не materialize как factual premise.

Modal/attitude proposition может быть premise только если сам goal спрашивает о ней:

```text
«Считает ли Анна P?»
```

но не:

```text
«Верно ли P?»
```

Полные системы K/T/S4/S5 и probabilistic proof **НЕ ВХОДЯТ**.

## 29.2. `N` как аргумент другого `N`

Proposition — адресуемый объект:

```text
FALSE(N42)
CONTRADICTS(N42,N57)
SUPPORTS(N18,N42)
SAID(Анна,N42)
```

## 29.3. Semantic proposition vs occurrence

Canonical semantic `N` и конкретный communication occurrence в `H` различаются.

Это необходимо для фраз:

```text
«во втором сообщении я ошибся»
```

где correction направлена на occurrence, а не обязательно на semantic proposition во всех её occurrences.

## 29.4. Operational meta-relations

Обычные описательные:

```text
MENTIONS
DISCUSSES
SAID
```

System-semantic с явным handler:

```text
FALSE(N)
CONTRADICTS(N1,N2)
CORRECTS(target,replacement)
```

Operational semantics определяется registry/handler, а не именем predicate.

## 29.5. Self-reference

Truth paradox вида:

```text
N = FALSE(N)
```

не решается. Expression помечается unresolved/self-referential и исключается из ordinary proof.

# 30. Ассоциативный режим

## 30.1. Смысл ассоциации

Ассоциация в режиме игры в ассоциации — **пересечение развернутых представлений**, а не consequence chain.

```text
expand(A) ∩ expand(B) != ∅
```

Пример:

```text
ВОРОНА -> ... -> НОЖКИ
СТОЛ   -> ... -> НОЖКИ
```

`НОЖКИ` — основание ассоциации.

Это не означает `ВОРОНА -> СТОЛ` и не является proof.

## 30.2. Допустимый common node

Точка пересечения может быть любым полноценным AH-элементом:

```text
S
m
N
g
k
T
...
```

Например common `S_НОЖКА` допустим даже если semantic resolver различает биологическую ногу и мебельную ножку как разные `m`.

Не вводится обязательный hub-filter: общий `T_HAVE` тоже является пересечением, просто может быть менее содержательным для verbalized response. **Критерий существования ассоциации и качество объяснения — разные задачи.**

## 30.3. Search mechanics

Обе стороны получают seed и распространяют возбуждение по обычной AH. `AssociationSearchState` может временно хранить ancestry/provenance двух фронтов, чтобы определить convergence.

Runtime ancestry не canonical и не записывается в AH.

## 30.4. GoalSpec association

Ассоциативный запрос имеет явный goal:

```text
FIND_ASSOCIATIVE_CONNECTION(A,B)
```

Goal может создавать narrow queries и смещать focus, но result определяется пересечением активированных областей, а не entailment rule.

## 30.5. Метрика minimum facts

Для экспериментальной задачи «минимальное число фактов» считается число **входных factual assertions**, а не число созданных `s/m/T/N/g/L`.

Одна человеческая factual sentence считается одним фактом независимо от внутренней декомпозиции AH.

## 30.6. H-domain

**РЕШЕНО в v0.25.25 как runtime policy.** Пересечение через `H` не зашивается в
canonical model как единственно допустимая политика. Один запрос явно выбирает
`ALL` либо `EXCLUDE_H`, а найденный результат всегда типизирован:

```text
SEMANTIC — route не зависит от H
EPISODIC — bridge зависит от H
```

Тем самым UI/эксперимент может разрешить все реальные пересечения либо потребовать
только semantic association без изменения AH. Простая последовательная
совместная встречаемость тем сама по себе не подменяет intersection-style search.

# 31. Context Projector и server boundary

## 31.1. Main LLM input

```text
current input
+ human-readable active semantic projection
+ proved conclusions / necessary proof premises
+ runtime instructions
```

Не передаются полный AH, arbitrary raw history, activation internals или global retrieval dump.

## 31.2. Human-readable projection

По умолчанию Main LLM не получает внутренний DSL. Projector разворачивает активные факты и relations в компактный human-readable semantic context.

При этом causal/temporal ordering нельзя терять: статья не должна превращаться в unordered bag of facts.

## 31.3. Selection policy

Основной механизм selection — сама dynamics Workspace. Не рекомендуется вводить дорогой reranking/diversity layer поверх каждого запроса.

Если вся компактная active semantics помещается в context window, предпочтительно передать её целиком.

## 31.4. Document summary

Для summary ingestion source/document имеет provenance scope. По запросу summary source scope может seed все semantic structures этого документа, после чего обычный Ignition формирует Workspace.

Raw chunks не извлекаются как RAG-context.

**Статус реализации v0.25.22: ЗАКРЫТО для one-shot summary.** Все operational
chunks сначала консолидируются одним DOCUMENT batch; source scope затем проецирует
canonical semantics и связи, а Main LLM получает только frozen AgentContext.

## 31.5. Слишком необязательно существующее большое projection

**ЧАСТИЧНО ЗАКРЫТО в v0.25.25.** Для one-shot ответа существует детерминированное
relation-aware сжатие внутри source scope с явным budget/notice и без raw fallback.
Добавлен runtime `SourceProjectionCursor` и bounded source slices с переносом только
уже увиденного causal/temporal overlap. `DocumentProcessor` пока не выполняет
полный multi-slice summary/aggregation loop, поэтому end-to-end continuation
остаётся открытым.

Требования к будущему решению:

```text
не давать Main LLM arbitrary global memory access;
не превращать fallback в скрытый RAG;
сохранять source scope;
сохранять causal/temporal continuity;
иметь deterministic stop/budget semantics.
```

## 31.6. Main-LLM initiated memory request

**РЕШЕНО в v0.25.25: capability отсутствует.** На один response call Main LLM
получает один окончательный frozen `AgentContext` и не может инициировать второй
memory request. Весь recall выполняется локальными `GoalSpec`/Reasoner/Association
и Workspace до генерации. Document multi-slice orchestration, когда будет
завершена, остаётся внешним контролируемым pipeline и не выдаёт модели право читать
AH произвольно.

## 31.7. Ответ Main LLM

Ответ проходит local perception и записывается как пережитый агентом communication event в `H`.

Он не является автоматической записью нового `C/P` и не подтверждает собственные предыдущие факты агента.

# 32. Persistence, lifecycle и GC

## 32.1. Canonical persistence

Persistence хранит AH и достаточные данные для восстановления:

```text
UID graph
canonical domains
Pr/Mt там, где это разрешено formalism
provenance
proof-support dependencies
occurrence links
registered semantic references
```

Runtime caches/indices могут persisted для скорости, но должны быть rebuildable из canonical state и не становиться скрытым источником truth.

## 32.2. Lifecycle N

Допустим дополнительный lifecycle:

```text
NEW
→ REINFORCED
→ CONSOLIDATED
```

Он сосуществует с общим forgetting/GC, а не заменяет его.

## 32.3. Physical deletion и нормативный GC

Сохраняется общий механизм initial lifetime + GC. После истечения предусмотренной жизни элемент может считаться потерянным, если он лишён поддерживающей структуры: например, его входящие/исходящие связи и гиперсвязи потеряли эффективный вес либо подграф полностью отвязался от сенсорной базы `S` согласно нормативной модели памяти.

```text
initial lifetime
→ structural support check
→ lost/orphaned?
→ physical deletion
```

Физическое удаление допустимо и является нормальной частью забывания. При этом долгое отсутствие activation само по себе не означает, что закреплённое знание нужно удалить.

Deletion event остаётся во внешнем audit/session log, **не в `H`**, потому что `H` — опыт агента, а не системный execution log.

## 32.4. Derived-support invalidation

При refutation/correction/merge/counterfactual filtering движок работает с supports:

```text
support invalid
→ remove/disable support
→ if independent supports remain: N remains admissible
→ if no supports remain: N loses basis
→ lifecycle/GC can remove later
```

Если derived fact позже был независимо сообщён, этот independent support должен пережить инвалидизацию старого proof.

## 32.5. Snapshots

Для reproducible tests рекомендуется поддерживать immutable/cloneable AH snapshots и cold Workspace reset. Cold Workspace — инструмент чистоты acceptance, **не runtime requirement**. В обычной работе Workspace может быть холодным, частично или сильно активным.

# 33. Edge/local deployment

## 33.1. Локально обязательны

```text
deterministic text parser / morphology
одна локальная SLM/BYAM для semantic probes
Deterministic Integration
AH Core / Persistence
Ignition Engine
Workspace
GoalCompiler / Reasoner
Association Coordinator
Context Projector
Lifecycle / GC
```

## 33.2. Внешняя Main LLM

Main generative LLM может быть server-side. Это не нарушает локальность памяти: canonical AH остаётся на устройстве, наружу уходит временный AgentContext.

## 33.3. Один probe-model

Одна локальная модель обслуживает разные bounded probes через короткие protocol prompts. Не требуется отдельная модель на каждый тип неоднозначности.

## 33.4. Model-size agnostic

Архитектура не фиксирует 8B или конкретное семейство.

Рекомендуемый edge experiment:

```text
1B / 2B / 4B / 8B quantized variants
→ same oracle probes
→ same deterministic pipeline
→ compare exact formalization
```

Цель — найти минимальную модель, которая воспроизводит oracle-correct formalization.

## 33.5. Server fallback semantic probe запрещён

Если local probe не может выбрать вариант:

```text
AMBIGUOUS / UNCLEAR
```

а не скрытый запрос более сильной серверной LLM.

## 33.6. Offline response

Полностью offline natural-language generation не является обязательной частью memory architecture. Система памяти должна продолжать сохранять локальный canonical state даже если Main LLM временно недоступна.

# 34. Диагностика и наблюдаемость

## 34.1. Human-readable trace

Для debugging reasoner должен уметь показывать:

```text
GoalSpec
focus movement
query-generated seeds
selected rules
bindings
premises/subgoals
branch/counterfactual scopes
conflicts
proof termination reason
materialized supports
```

Trace — диагностика, а не второй канал истины.

## 34.2. Workspace inspection

Диагностика должна показывать:

```text
active nodes sorted by activation/time
human-readable representations
why node was seeded/reactivated
incoming/outgoing relevant links
current focus
final AgentContext
```

## 34.3. Activation diagnostics

Для каждого tick желательно уметь трассировать:

```text
old x
external seed input
propagated input
floor/decay contribution
new x
activation/reactivation event flag
Hebbian updates
```

Это критично для поиска self-reinforcement и ложных коэффициентов decay.

## 34.4. Formalization diagnostics

Для каждого input полезно сохранять:

```text
algorithmic candidates
probe request
probe protocol answer
validated interpretation
CandidateIR
MutationPlan
canonical UID result
ambiguities left unresolved
```

Важно иметь возможность доказать, что модель принимала только bounded decision, а не скрыто генерировала graph.

# 35. Acceptance и regression contract

## 35.1. Большой граф

Inference/recall должен работать в обычной AH с большим количеством посторонних узлов и ветвлений. Архитектурный ориентир тестов — порядка `150k+` UID.

Query должен активировать релевантную область и развивать reasoning как цепочку возбуждения. Наличие большого количества невозбуждённого шума не даёт reasoner-у права читать всё подряд.

## 35.2. Multi-hop

Обязательны цепочки различной глубины, включая смешанные relations и остановку на разных глубинах. Correctness должна проверяться не только по final answer, но и по proof/support trace.

## 35.3. SOTA-breaker suites

Архитектурно предусмотрены классы:

```text
multi-hop 3+
negation scope
temporal state tracking
multi-variable counterfactuals
mention vs assertion
UNKNOWN
quantifiers
long-text contradictions
OR/XOR
modal/attitude scope
reverse CAUSE
transitive/non-transitive relations
meta-propositions
```

General mathematical comparative reasoning отложен.

## 35.4. Article summary

Тест:

```text
ingest full article
→ remove raw article from Main LLM context
→ source-scoped AH activation
→ compact semantic projection
→ summary
```

Успех означает, что связный summary формируется из AH, а не через скрытый chunk retrieval.

## 35.5. Association game

Набор должен задавать factual assertions и проверять минимальное число **фактов**, необходимое для получения meaningful intersection. Можно добавлять distractors.

## 35.6. Edge oracles

Для SLM измеряется exact match с существующими formalization/probe oracle, а не качество свободной генерации.

Если меньшая SLM даёт тот же canonical result, что большая модель, это прямой аргумент в пользу архитектурного сужения semantic work.

## 35.7. RAG comparison — high-level contract

Детальный benchmark может развиваться отдельно, но архитектурно сравнение должно фиксировать Main LLM и corpus, а knowledge participation самой LLM исключать evidence-grounded/synthetic world.

Рекомендуемые независимые показатели:

```text
answer accuracy
evidence/proof accuracy
strict grounded success
hallucination rate
multi-hop by depth
UNKNOWN correctness
conflict correctness
context tokens
latency
peak RAM
```

Правильный случайно угаданный answer без поддерживающего evidence не считается строгим успехом.

# 36. Открытые архитектурные вопросы

## 36.1. `H` в association mode

**ЗАКРЫТО в v0.25.25.** Политика обратима и выбирается на runtime boundary:

```text
ALL       — разрешить реальные пересечения, включая H;
EXCLUDE_H — исключить H из ancestry.
```

Независимо от фильтра outcome различает `SEMANTIC` и `EPISODIC`. Выбор не меняет
canonical data model или persistence.

## 36.2. Инициативный memory request основной LLM

**ЗАКРЫТО в v0.25.25 выбором базового варианта.** Main LLM получает ровно один
готовый `AgentContext` на response call и не управляет memory search. Вторичный
protocol запроса памяти не входит в текущий контракт.

## 36.3. Fallback для слишком source-scoped + document projection

**ЧАСТИЧНО ЗАКРЫТО.** One-shot source compaction имеет deterministic selection,
stop и budget semantics. Runtime cursor/slice primitive уже существует, но его
ещё не исполняет `DocumentProcessor` как законченный multi-context summary с
детерминированным aggregation/termination contract.

Варианты для отдельного решения:

```text
итеративные source-scoped slices;
goal-driven section excitation;
deterministic continuation cursor;
hierarchical projection без новой document ontology.
```

Не допускается fallback «отдать Main LLM raw chunks как обычный RAG», если эксперимент заявляет AH-only summary.

# 37. Сознательно отложенные направления

## 37.1. Late identity split

Автоматическое разделение давно слитого `m` на несколько identities с пересборкой всей downstream истории.

## 37.2. Multimodality

Архитектура AH допускает другие sensory channels, но текущая спецификация формализации ориентирована на текст. Не следует вводить полусделанные multimodal node types в текстовое ядро.

## 37.3. Universal comparative/math reasoner

Explicit comparison можно хранить:

```text
TALLER_THAN(A,B)
OLDER_THAN(A,B)
```

Но система не обязана реализовывать:

```text
constraint graphs;
арифметику разностей;
max/min solver;
общий ordered-metric engine.
```

Если конкретная relation имеет зарегистрированные rules, reasoner может их использовать как обычные inference rules.

## 37.4. Full modal logic

Не реализуются общие системы K/T/S4/S5, probabilistic modal inference и переход `POSSIBLE(P) -> P`.

## 37.5. Full causal world simulation

Counterfactual sandbox не является Structural Causal Model и не симулирует неявные изменения всего мира.

## 37.6. Fully local generative LLM

Полностью локальный natural-language responder может быть добавлен как deployment option, но не является обязательной частью AH memory layer.

# 40. Правила эволюционного развития существующего кода

## 40.1. Не переписывать сильные механизмы без необходимости

**ОБЯЗАТЕЛЬНО ДЛЯ РАЗРАБОТКИ.** Изменения выполняются эволюционно:

```text
inspect existing mechanism
→ identify exact semantic gap
→ preserve working invariants
→ extend locally
→ add regression test
→ only then refactor common abstraction if needed
```

Новый архитектурный раздел не является основанием переписать подсистему целиком, если существующий код уже реализует её корректную часть.

Особенно это относится к:

```text
AH canonical structures;
UID/persistence;
Ignition dynamics;
existing relation indexes;
current parsing algorithms;
existing fixed-choice probe infrastructure;
GUI/diagnostic hooks used for acceptance.
```

## 40.2. Миграция M2/inference

В существующей реализации relation proof мог строиться forward traversal от source, а reverse distances от target использоваться как pruning/ordering heuristic. Это допустимо сохранить при двух условиях:

```text
reverse distance никогда не считается proof;
каждый фактический proof step проходит rule validation и activation/focus loop.
```

Нельзя ограничиться схемой:

```text
quiet BFS/DFS
→ готовый trace
→ один Ignition tick для отображения
```

Целевое поведение:

```text
proof step
→ strong focus/activation
→ Ignition tick
→ Workspace changes
→ next admissible step
```

## 40.3. Cold Workspace

Cold Workspace нужен только для acceptance cases, где требуется доказать, что answer не находился в уже активном context.

Runtime должен быть корректен при любом начальном состоянии:

```text
cold
partially active
strongly active
```

Reasoner не может полагаться на предварительно очищенный Workspace.

## 40.4. Регрессионное правило для каждой архитектурной правки

Каждая правка, затрагивающая formalization, activation или inference, должна сопровождаться как минимум:

```text
positive case;
negative case;
ambiguity/UNKNOWN case where relevant;
noise case if search semantics affected;
serialization/reload case if canonical data affected.
```

Для изменения canonical schema обязательно добавлять migration/backward-compatibility test либо явно повышать schema version.

# 41. Definition of done для архитектурного соответствия

Реализация считается соответствующей этой спецификации, если одновременно выполняются следующие условия:

1. Canonical AH остаётся единственным долговременным semantic store.
2. Main LLM не владеет памятью и не получает длинную history по умолчанию.
3. Formalization детерминированно сужает проблему до bounded semantic probes.
4. Неоднозначность может сохраняться без forced guess.
5. Identity, merge, dedup и delayed coreference не нарушают canonical UID semantics.
6. Inference demand-driven, rule-driven и проходит через activation/Workspace.
7. Unexcited global memory не читается reasoner-ом произвольно.
8. Open-world `UNKNOWN` не схлопывается в FALSE.
9. Conflict локализован и не вызывает explosion.
10. OR branches, hypothetical/counterfactual content и reported/modal content не загрязняют factual memory.
11. Derived facts имеют dependency provenance.
12. Hebbian plasticity изменяет силу существующих links, но не создаёт topology.
13. Association определяется пересечением активированных представлений, а не consequence chain.
14. Context Projector выдаёт compact human-readable semantics без hidden raw-chunk RAG.
15. Runtime overlays, variables, discourse refs и indices не становятся новыми canonical node kinds.
16. Система сохраняет работоспособность на большой AH с существенным шумом и ветвлением.

# Приложение A. Реестр ключевых архитектурных решений

## Обязательные

- **Main LLM:** stateless относительно длинной истории; consumer `AgentContext`.
- **Canonical memory:** остаётся локальной и не отдаётся Main LLM.
- **Formalization:** deterministic-first + bounded semantic probes.
- **Probe failure:** ambiguity/UNCLEAR без server fallback.
- **`s`:** одна lexical unit/paradigm; phrase-level `s` запрещён.
- **Identity:** same name не является identity key.
- **Merge:** deterministic older UID survives, затем rewiring/dedup.
- **Documents:** whole-document consolidation, без special summary ontology.
- **Raw source:** provenance/reprocessing only, не Main-LLM retrieval memory.
- **Time:** semantic TIME только когда значимо; partial time remains partial.
- **State tracking:** intervals + transitions, не last textual mention.
- **Quantifiers:** FORALL/EXISTS/NOT + nested scopes.
- **BoundVar:** scoped descriptor без AH UID; runtime `BindingEnvironment`.
- **Existential unknown:** не создавать `m_UNKNOWN`; shared existential referent.
- **Delayed coreference:** `DiscourseRef` до batch consolidation.
- **Inference:** backward goal decomposition + forward validation.
- **Search:** demand-driven; no unrestricted full-AH read.
- **Proof/activation:** proof steps физически проходят через Ignition/Workspace.
- **Goal query:** strong seed, отдельный configurable gain.
- **OR/XOR:** XOR canonicalized through OR/AND/NOT; branch reasoning.
- **Conflict:** `k_CONFLICT`, no auto-winner, paraconsistent runtime.
- **CAUSE:** не имеет автоматического transitive closure.
- **Relation properties:** explicit registry, conservative-by-default.
- **Counterfactual:** local proof overlay, no copy of AH.
- **Meta-propositions:** `N` может быть аргументом; occurrence отделён от content.
- **Association:** intersection `expand(A) ∩ expand(B)`, не consequence.
- **Association/H:** runtime `ALL|EXCLUDE_H`; outcome всегда различает semantic и episodic route.
- **Hebbian:** only existing `L`, same-tick activation events.
- **Scene:** отдельный canonical scene object не вводится.
- **Context projection:** Workspace-driven, human-readable, no hidden raw RAG.
- **Main-LLM recall:** один frozen `AgentContext`; secondary memory-request capability отсутствует.

## Ограниченные по design

- **Modal/attitude:** scope protection only; universal modal reasoner не вводится.

## Открытые

- **Oversized document projection:** cursor/slices готовы, но iterative summary/aggregation pipeline не завершён.

## Отложенные / опциональные

- **Late identity split:** автоматический split старой merge history.
- **Comparative math:** universal constraint/arithmetic engine.
- **Multimodality:** будущий sensory extension.
- **Fully local responder:** deployment option, не memory requirement.

## Не входит

- **Full causal SCM:** не является частью counterfactual sandbox.

# Приложение A.1. Краткая карта обязательных registries

```text
FunctionRegistry
    g.ID -> operand schema + machine semantics

InferenceSchemaRegistry
    L.ID/T.UID -> transitivity/symmetry/functionality/etc.

ProbeRegistry
    probe_type -> compact prompt + answer protocol + validator

ProjectionRegistry (рекомендуется)
    canonical type/function -> human-readable rendering

TemporalSchema (может быть частью InferenceSchemaRegistry)
    predicate/relation -> temporal handling rules where explicit
```

Registries не являются memory stores. Они описывают машинную семантику кода.

Архитектура допускает настройку без изменения canonical meaning:

```text

prompt_seed_gain
```

# Приложение C. Минимальные regression-примеры

## C.1. Scope

```text
Не все сотрудники пришли.
```

Ожидается:

```text
NOT(FORALL employee -> CAME)
```

а не `FORALL -> NOT(CAME)`.

## C.2. Reported content

```text
Анна сказала, что сервер работает.
```

Доказуемо:

```text
SAID(Анна, WORK(server))
```

Недостаточно для factual proof `WORK(server)`.

## C.3. UNKNOWN

```text
EXISTS x: RED(x)
```

при отсутствии найденного witness → `UNKNOWN`, а не FALSE.

## C.4. Conflict

```text
WORK(server)
NOT(WORK(server))
```

Query `IS_A(server, computer)` должен продолжать независимо работать.

## C.5. OR branch

```text
OR(A,B)
A -> C
B -> C
```

→ `C`, без materialization `A`/`B`.

## C.6. Counterfactual

Canonical:

```text
LIVES(Ivan, Moscow)
LIVES(x,Moscow) -> USES_METRO(x)
```

Counterfactual:

```text
assume LIVES(Ivan, Village)
```

старый derived support `USES_METRO(Ivan)` недопустим, если других supports нет.

## C.7. Delayed coreference

```text
Кто-то вошёл. Он сел.
```

→ один shared existential referent, без `m_UNKNOWN`.

## C.8. Association

```text
У вороны есть ножки.
У письменного стола есть ножки.
```

валидное основание intersection: `НОЖКИ`, а не consequence `ВОРОНА -> СТОЛ`.

## C.9. Temporal state

```text
10:00 сервер работает.
12:00 сервер отключился.
```

Query `13:00 WORK(server)` → отрицательное состояние после transition; более позднее нерелевантное событие не меняет результат.

## C.10. CAUSE

```text
CAUSE(A,B)
CAUSE(B,C)
```

Допустимо вернуть upstream causal path `A -> B -> C`; нельзя автоматически materialize ordinary `CAUSE(A,C)`.
