# Рекурсивные именные описания через закрытые вопросы

Нормативное дополнение V7 §3/§4.7/§7.5/§8.2/§17. Ресурсный opt-in:
`ProposalPolicy.composition.nominal_composition=QUESTION_TREE_V1`,
`nominal_host_role` — зарегистрированная ENTITY-роль, отличная от
`preposition_nominal_role` и `modifier_content_role`. Требуется BOUNDED_FOREST_V1.

## Вопросы и сборка

Программный конструктор сначала строит полные покрытия ещё не присоединённых
токенов: PREP + ADJF* + NOUN/NPRO и ADVB. Морфологические варианты сохраняются
целиком; согласование определений с головным словом проверяется до выбора.
Локальная проба при необходимости выбирает целое морфологическое чтение.
Затем для каждой PP ставится отдельный закрытый вопрос: описывает ли она
событие либо конкретного именного участника? Кандидаты включают участников
основной рамки и головные слова других PP, кроме собственного дополнения.

Выбирается непосредственный хозяин связи. Поддеревья собираются по этим
ссылкам рекурсивно. Цикл, недоступный хозяин, неоднозначная сегментация,
неразрешённый выбор или исчерпанный бюджет блокируют композицию; первый
совместимый вариант не назначается победителем. Между вопросами не создаются
AH-факты. Общая T4-проверка и T5/T6 остаются обязательными.

Два вопроса «где была ситуация?» и «о чём сообщение?» имеют разные типы цели.
Слова, предлоги и имена не зашиты в runtime: конкретные relation T появляются
через обычный open/known путь T3. Известный sense без лицензированной валентности
или TemplateMap не заменяется OPEN. Определения также становятся отдельными
лексическими рамками описания, сохраняющими своё головное слово.

Все квалифицирующие связи одного участника — неупорядоченные структурные
описания этого участника. Они не становятся цепочкой областей над событием.
Модификаторы самого события продолжают прежний перебор порядков scope.

## Типизированная запись: UsageLink.kind=NOMINAL

ENTITY-слот основного узла по-прежнему содержит Ref(M). Его описание — отдельный
N с лексическим T, ENTITY-актантом хозяина и, для PP, ENTITY-дополнением.
Например, структурное описание «об искусстве» связывает M_сообщение и
M_искусство; определения «австрийское» и «инженерное» описывают M_искусство.
Никакого превращения M в proposition, семантики принадлежности по умолчанию
или alias по сходству текста нет.

`UsageLink{kind=NOMINAL, node_ref:Ref(N), parent_ref:Ref(N), position,
host_ref:Ref(M), host_role, source_tag, root_support_ref, attitude=UNKNOWN,
status=LIVE}`. `position` — ENTITY-роль родителя; `host_role` — роль того же M
в описании. Write boundary проверяет обе стороны, тип M и привязку к ROOT-опоре
того же source_tag. ID = H(node_ref, parent_ref, position, NOMINAL, host_ref,
source_tag, root_support_ref). Это отдельный вариант tagged union UsageLink;
ограничение пропозициональных слотов для OPERATOR не меняется.

Описание доступно структурно, если родитель S-accessible, link LIVE и именно
root_support_ref имеет живой proof path. Чужая опора общего STATE-узла не может
поддержать описание утратившего опору источника. Рекурсивная S-access достигает
определений через родительское именное описание. AddRootSupport на описания
не пишется: самостоятельные истинностные утверждения из них не выводятся.

C/T5 создаёт рамки и полный fragment closure. T6 записывает все M/N, основную
ROOT-опору и NOMINAL-links в одной транзакции с маркером/COMMIT_DECISION.
NOMINAL-links следуют после ROOT-опоры внутри транзакции; доступного частичного
состояния нет. Отказ фрагмента исключает весь его набор описаний. Повтор
использует стабильные ID; recovery читает те же durable операции.

Отзыв source_tag SUPERSEDE'ит NOMINAL-link, как per-observation ATTITUDE-link.
Потеря proof path без отзыва делает описание неэффективным без переписывания
link. Прямой RetractUsageLink разрешён для NOMINAL; OPERATOR остаётся запрещён.
GoalExecutor не получает новых прав записи описаний.

## Границы реализации

Этот этап запускается после построения базовой рамки. Без дополнительного
CONSTRAINT_TREE_V1 build_clause останавливается при более чем трёх именных
кандидатах (COMPONENT_SEARCH_INCOMPLETE). С этим opt-in раннее сужение зависимостей
предшествует роли предиката: см. [COMPONENT_DEPENDENCY_REDUCTION.md](COMPONENT_DEPENDENCY_REDUCTION.md).

Этот этап покрывает рекурсивное присоединение PP к именным головам и
согласованные атрибутивные ADJF. Голый генитив и приложения требуют отдельного
CONSTRAINT_TREE_V1; многословные предлоги и вложенные именные координации
не объявлены покрытыми. Полнота списка
проверяется до закрытого выбора; непокрытый токен не исчезает.

Существующий query compiler ещё не умеет проверять такие квалифицирующие
ограничения. Запрос с ними получает QUERY_NOMINAL_SCOPE_UNSUPPORTED, а не
упрощается до более широкого вопроса без описания. Независимый запрос к
самому S-only описанию не получает YES из отсутствующей truth-support.
Runtime-проекция не выдаёт описания за самостоятельные legacy assertions.

Словарь диагностического запуска остаётся TEST_ONLY. Короткие ответы
изолированного исполнителя не являются тестированием локальной модели.

Постноминальные относительные и причастные области, раздельные границы контекста
и владения токенами, а также проверяемый host_path для scoped-описания определены
в [COMPONENT_REFINEMENT.md](COMPONENT_REFINEMENT.md). Прямые NOMINAL-links
сохраняют прежнюю схему и ключ; path добавляется только при вложенном хозяине.
