# Архитектура MVP агента на АГ-памяти

**Статус:** единая рабочая спецификация v0.37  
**Целевой уровень:** Senior / «Воспламенение»  
**Область:** текстовый LLM-агент  
**Назначение:** руководство к реализации: какие данные существуют, какой модуль ими владеет, в каком порядке идёт обработка и где проходят границы ответственности.

## Обозначения

- **[M]** — следует из формализма АГ-памяти Р. В. Душкина.
- **[H]** — требуется постановкой хакатона.
- **[P]** — принятое проектное решение.
- **[D]** — прямое уточнение механики Р. В. Душкиным, переданное в ходе проектирования.
- **[DEFER]** — сознательно не входит в MVP.

Секция «Рекомендуемая структура кода» — инженерная декомпозиция, выведенная из принятых архитектурных границ; она не добавляет новых семантических типов АГ-памяти.

Главное правило документа: ниже описана одна актуальная архитектура. Старые варианты решений и уже отвергнутые ветки не сохраняются.

# 1. Архитектура верхнего уровня

## 1.1. Что строим

**[P]** АГ-память — долговременная структурированная когнитивная память LLM-агента. Она должна одновременно поддерживать:

```text
1. запись нового текстового опыта;
2. каноническое представление знаний;
3. ассоциативное распространение возбуждения;
4. формирование текущего фокуса внимания;
5. символический вывод;
6. передачу активной семантики в LLM;
7. запись собственной пережитой истории агента.
```

QA — один из режимов использования памяти, а не её основное назначение.

## 1.2. Полный поток

```text
External Text
      ↓
Text Sensory / S Recognition
      ↓
LLM Perception
      ↓
PerceptionResult
      ↓
Deterministic Integration
      ↓
AH = <S,C,P,H,L>
      ↓
Activation Seed / Reactivation
      ↓
Ignition Engine
      ↓
Workspace
      ↓
Recall + Symbolic Inference
      ↓
Deterministic Context Projection
      ↓
AgentContext
      ↓
LLM Agent
      ↓
Response / Decision / Action
      ↓
H-only Experience Integration
      ↓
AH updated with experienced response
```

Параллельно вход пользователя всегда фиксируется как пережитый опыт в `H`, а его семантическое содержание может дополнительно попасть в `C` и `P`.

## 1.3. Постоянное состояние

```text
State_t = <AH_t, Context_t>
```

`AH_t` — состояние памяти.

`Context_t` — runtime-контекст текущего взаимодействия: текущий turn, дейктические якоря, собеседники, время, conversation/episode context и собранный для LLM контекст.

**[P]** Канонические знания живут в `AH`. Runtime-объекты используются для вычисления и не заменяют память.

## 1.4. Recall и Inference — разные механизмы

```text
Recall != Inference
```

Recall отвечает:

> Что стало релевантным из-за текущего возбуждения памяти?

Inference отвечает:

> Что логически следует из формализованных фактов и отношений?

Поэтому:

```text
Ignition + Workspace
→ ассоциативный контекст

Symbolic Inference
→ логические выводы
```

Активация влияет на релевантность и порядок поиска, но не делает утверждение истинным.

# 2. Модульная схема

Код должен быть разделён по ответственности.

```text
┌──────────────────────────────┐
│ Interaction / Orchestrator   │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ Text Sensory + S Recognition │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ LLM Perception               │
│ candidate extraction only    │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ Deterministic Integration    │
│ validation / resolution      │
│ canonical construction       │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ AH Core / Store              │
│ <S,C,P,H,L>                  │
│ canonical operations         │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ Ignition Engine              │
│ x / f / g / h / t / ν        │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ Workspace                    │
│ refs with x > t              │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ Symbolic Inference           │
│ role / IS-A / FOLLOW / CAUSE │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ Context Projector            │
│ deterministic serialization  │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ LLM Agent                    │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐

```

Поддерживающие компоненты:

```text

Persistence
Lifecycle / GC
DSL
Diagnostics / UID Trace
Evaluation
RAG baseline
```

Ни один внешний модуль не пишет канонические структуры в обход `AH Core`.

# 3. Каноническая модель данных

## 3.1. `AH`

**[M]**

```text
AH = <S, C, P, H, L>
```

Для краткости:

```text
E = C ∪ P ∪ H
```

`E` — обозначение, а не отдельный раздел памяти.

## 3.2. `S` — абстрактные символы первого порядка

**[M]**

```text
s = <UID, R>
```

Для текстового агента:

```text
R = R_text
```

**[P]** Один `s` соответствует устойчивой лексической единице / парадигме. `R_text` содержит формы, по которым она распознаётся.

Критический инвариант для омографии:

```text
wordform -> set[s]
```

а не:

```text
wordform -> one s
```

Одинаковая наблюдаемая словоформа может легально входить в `R_text` нескольких
разных `s`, если это разные лексические единицы/парадигмы. Совпадение surface form
никогда само по себе не является основанием для merge `s`.

```text
known unambiguous wordform
→ reuse existing s

known homographic wordform
→ retrieve all matching s as lexical candidates

new wordform of known lexeme
→ extend R_text only after lexical identity is resolved

new lexical unit
→ create new s only after lexical identity is resolved
```

Пример:

```text
s_APPLE
└── R_text
    ├── яблоко
    ├── яблока
    ├── яблоку
    └── ...
```

Критическое различие:

```text
s_APPLE != m_APPLE
```

`s` — языковой символ.  
`m` — семантическое понятие или сущность.

Отдельные `lemma` / `canonical_form` в каноническую структуру не вводятся: самим каноническим языковым символом является `s`; словоформы нужны для распознавания, а LLM выбирает форму при генерации.

## 3.3. Элемент `C/P/H`

**[M]**

```text
e = <q, x, f>

q ∈ {
    s*,
    m,
    m*,
    g,
    k,
    T,
    N
}
```

где:

```text
x — текущий уровень возбуждения;
f — функция активации элемента.
```

## 3.4. `m` — самостоятельно адресуемая семантическая сущность

**[M]**

```text
m = <UID, Pr, Mt>
```

**[P]** `m` создаётся, когда содержание обладает собственной устойчивой идентичностью и должно независимо участвовать в:

```text
активации;
ассоциациях;
отношениях;
ролях актантов;
рассуждении.
```

Примеры:

```text
m_IVAN
m_APPLE
m_RED
m_MOSCOW
m_PERSON
m_SELF
m_USER_01
```

Класс и экземпляр — оба `m`:

```text
m_IVAN --IS-A--> m_PERSON
```

UID — каноническая машинная идентичность.

Имя не является identity key.

```text
IdentityProfile(m)
≈ properties + relations + facts + history + current context
```

`IdentityProfile` — принцип resolution, а не новый канонический тип.

## 3.5. `Pr` и `Mt`

**[M]** Поля `Pr/Mt` структурно есть только у:

```text
m
k
N
```

У `s`, `T`, `g`, `L` этих полей нет.

Свойство:

```text
p = <name, value, type, unit>
```

`Pr` — свойства без обязательной специальной семантики для кода.

`Mt` — мета-свойства, которые интерпретируются программно.

Пример:

```text
m_IVAN.Pr:
  name = Иван
  age = 32
  eye_color = карий
```

Правило выбора:

```text
локальная характеристика владельца
→ Pr

самостоятельное содержание,
которому нужна собственная активация /
ассоциация / relation / reasoning
→ отдельная AH-структура

машинный служебный атрибут
→ Mt
```

Не нужно прятать самостоятельный факт в property:

```text
Pr.moved_to = "Париж"     # плохо, если это отдельное событие
```

вместо:

```text
N_MOVE(...)
```

## 3.6. `T` — шаблон модели управления предикатного символа

**[M]**

```text
T = <UID, s*, A>
Q = |A|
```

`s*` указывает на языковой предикат.

`A` задаёт роли актантов.

Канонический классификатор:

```text
SUBJECT
OBJECT
AUXILLIARY
RECIPIENT
SOURCE
ABSENTEE
LOCATION
STATE
TIME
DURATION
CAUSE
PURPOSE
TOOL
MATERIAL
AMOUNT
HOW-TO
```

Не все роли конкретного `N` обязаны быть заполнены.

### Динамическое создание `T`

**[P]** Набор шаблонов не закрыт.

```text
unknown predicate
      ↓
Perception TemplateCandidate
(explicit roles from current semantic act)
      ↓
deterministic validation
      ↓
resolve/create predicate s
      ↓
create canonical T
      ↓
register T in index
      ↓
resume original assertion integration
```

Perception (включая LLM-интерпретацию естественного языка) предлагает предикат и явные роли текущего semantic act, но:

```text
не назначает canonical UID;
не пишет T напрямую в AH;
не создаёт inference rule автоматически.
```

Новый `T` означает только, что агент теперь умеет представлять новый тип предикатной ситуации.

### Контролируемое монотонное расширение `T`

**[P]** Первое употребление предиката не обязано раскрывать полную модель управления. Канонический `T` может расширяться позднее, когда новый turn содержит валидированную **явную** семантическую роль.

```text
Roles(T_old) ⊆ Roles(T_new)
UID(T_new) = UID(T_old)
```

Допустимое evidence для расширения:

```text
assertion: роль реально заполнена в PerceptionResult;
query: роль явно заполнена или requested_role явно запрошена;
command: роль явно присутствует в семантическом акте.
```

Не является основанием для canonical expansion:

```text
LLM предполагает, что у глагола обычно есть ещё одна незаполненная роль;
морфология/словарная валентность угадывает отсутствующий актант;
отсутствие роли в одном употреблении трактуется как доказательство её отсутствия в T.
```

Старые `N` не переписываются: уже существующий конкретный факт остаётся корректным, потому что не все роли `T` обязаны быть заполнены в каждом `N`.

Если для одного `s` уже существует несколько несовместимых `T` и новый evidence не позволяет детерминированно выбрать один из них, Integration обязана fail-closed; это уже задача lexical sense resolution, а не простое расширение валентности.

## 3.7. `N` — гиперсвязь / конкретный факт

**[M]**

```text
N =
<UID,
 w,
 T*,
 {s_i* | e_i*}[1..Q],
 Pr,
 Mt>
```

Один `N` — одна конкретная реализация одного `T`.

```text
one N = one predicate realization
one sentence may produce multiple N
N may be actant of another N
```

Пример:

```text
N_READ
├── T* -> T_READ
├── SUBJECT -> m_IVAN
└── OBJECT  -> m_BOOK
```

Вложенный факт:

```text
N_MOVE
├── SUBJECT  -> m_MASHA
└── LOCATION -> m_PARIS

N_SAY
├── SUBJECT -> m_IVAN
└── OBJECT  -> N_MOVE
```

Роли задаёт `T`; `N` хранит заполнение этих позиций.

### Scoped proposition `N`

**[P]** Канонический `N` может использоваться не только как самостоятельно утверждённый факт, но и как **содержимое семантического оператора**. В таком случае `N` получает явный machine-owned scope marker, например:

```text
Mt.semantic_scope = CONDITIONAL
```

Такой `N` означает «эта пропозиция присутствует как операнд конструкции», а не «эта пропозиция истинна в мире сама по себе». Поэтому:

```text
ordinary N
→ доступен обычному EXISTS / ROLE_FILL как asserted fact

N[semantic_scope=CONDITIONAL]
→ canonical proposition content
→ НЕ удовлетворяет ordinary EXISTS / ROLE_FILL самостоятельно
→ интерпретируется только через содержащий semantic operator
```

Scope участвует в domain-local canonical signature `N`: условное содержание и позднее независимо утверждённый такой же факт не дедуплицируются в один UID только из-за совпадения `T` и актантов. Это сохраняет различие между «если Иван придёт» и «Иван пришёл».

`N.w` — вес гиперсвязи в активационной динамике. Это не truth/confidence.

## 3.8. `L` — типизированная направленная связь

**[M]**

```text
L = <UID, ID, w, (e1*, e2*)>
```

Направление:

```text
e1 --ID,w--> e2
```

Ключевые `ID` MVP:

```text
IS-A
FOLLOW
CAUSE
```

Разделение ответственности:

```text
N → предикатный факт
L → структурное типизированное отношение
g → функциональная композиция
k → идентифицированная группировка
```

Новый естественно-языковой глагол создаёт/использует `T/N`, а не новый `L.ID`.

## 3.9. `g` — функциональная конструкция

**[M]**

```text
g = <UID, ID, {e_i*}>
```

MVP использует в том числе:

```text
AND(...)
OR(...)
FALSE(...)
IF(antecedent, consequent)
```

### Каноническая условная семантика

**[P]** Естественно-языковое условие хранится как функциональная конструкция, а не как набор попарных `L.CONDITION`:

```text
Если A, то B
→ IF(A_scoped, B_scoped)

Если A и B, то C
→ IF(AND(A_scoped, B_scoped), C_scoped)

Если A, то B и C
→ IF(A_scoped, AND(B_scoped, C_scoped))
```

Это принципиально: два отдельных link-а `A CONDITION C` и `B CONDITION C` ошибочно утверждали бы, что каждого antecedent достаточно отдельно. `AND` сохраняет исходную логическую структуру branch-set.

Branch propositions создаются как scoped `N` и не становятся самостоятельными world facts. Сам `IF` — каноническое semantic content, которое может быть привязано к H-опыту turn-а и маршрутизируется в `C/P` по обычному provenance/domain rule.

`IF` имеет фиксированную arity 2 в `FunctionRegistry`. Исполняемый modus-ponens для `IF` является отдельным inference rule: наличие канонического `IF` не разрешает движку считать antecedent или consequent уже доказанными.

`g.ID` имеет машинную семантику. Поэтому код содержит детерминированный:

```text
FunctionRegistry
```

Для каждого `g.ID` registry определяет:

```text
functional semantics;
operand schema / arity;
canonical semantic projection for LLM;
explicit inference behavior: executable handler/rule либо явно non-executing status.
```

Пример:

```text
AH:
g_FALSE_17
  ID = FALSE
  operands = [N8]

Projection:
"отрицание факта: Иван находится в Москве"
```

LLM не должна самостоятельно угадывать семантику opaque enum.

Новый `g.ID` добавляется только вместе с программной семантикой/validation и projection. Если `g.ID` должен участвовать в символическом выводе, его inference rule/handler добавляется явно; отсутствие такого rule не даёт движку права имплицитно выводить операнды или результат.

## 3.10. `k` — идентифицированная группировка / мета-объект

**[M]**

```text
k = <UID, ordered_members, Pr, Mt>
```

`k` превращает выбранный набор / подграф в отдельный адресуемый объект.

Он нужен для:

```text
hierarchy;
heterarchy;
episode;
object model;
ambiguity set;
turn/dialogue content grouping.
```

`k`:

```text
не создаёт отношения между членами;
не заменяет N;
не заменяет L;
не выполняет логическую функцию.
```

Его задача — дать целому:

```text
UID;
границу состава;
порядок непосредственных членов;
Pr/Mt;
возможность быть actant/member другого объекта.
```

## 3.11. Неоднозначная ссылка через `k`

**[P]**

Если deterministic resolution оставляет несколько равноправных кандидатов:

```text
k_AMBIGUOUS
├── m_1
├── m_2
└── ...

Mt.TYPE = AMBIGUOUS_REFERENCE
```

Семантика:

```text
Ref(k) = m_1 OR m_2 OR ... OR m_n
```

а не утверждение о всех кандидатах сразу.

После уточнения ссылка в факте заменяется на конкретный `m`.

# 4. Семантические области `C / P / H`

## 4.1. Определения

**[P]**

```text
C — интерсубъективная модель мира.

P — персонализированная модель агента
    и конкретных известных ему объектов.

H — пережитая история агента.
```

Это не уровни достоверности.

## 4.2. Одинаковая внутренняя природа

`C`, `P`, `H` используют один и тот же набор AH-типов:

```text
s*
m
m*
g
k
T
N
```

`H` не является логом движка. Тики, stack trace, UID trace, вызовы функций и telemetry туда не пишутся.

## 4.3. Семантика может дублироваться между доменами

Один смысл допустимо представить отдельными каноническими элементами в нескольких доменах.

```text
C:
  N_C = "Иван — человек"

P:
  N_P = "Иван — человек"

H:
  N_H = "Иван — человек"
```

Эти элементы имеют разные UID.

Следствие:

```text
deduplication scope = one target domain
```

Эквивалентный `N` в другом домене не блокирует создание локального `N`.

Глубокое копирование всех актантов не требуется: H/P/C-элементы могут ссылаться на уже существующие семантические сущности из других доменов, если identity должна быть общей.

## 4.4. Домен определяется смыслом

```text
"Яблоки бывают красными"
→ C

"Мне нравятся красные яблоки"
→ P
```

Источник сообщения не определяет домен содержательного факта.

## 4.5. Каждая коммуникация дополнительно является `H`

Пользовательское сообщение создаёт два слоя:

```text
User message
      ↓
┌──────────────────────┬──────────────────────┐
↓                      ↓
пережитый turn → H     semantic facts
                       ├── C
                       └── P
```

Собственный ответ агента:

```text
Agent response
→ H
→ no automatic C/P integration
```

Это фундаментальная защита от self-reinforcement:

```text
generation != learning
utterance != confirmation
```

# 5. Диалог как пережитый опыт в `H`

## 5.1. Никакого отдельного типа «dialogue memory»

**[P]** Реплики пользователя и агента записываются в `H` теми же каноническими типами `m/g/k/T/N`, что используются в `C` и `P`.

То есть код не должен вводить специальный log-record, который существует вне АГ-формализма.

```text
user turn
→ semantic structures in H

agent turn
→ semantic structures in H
```

Факт коммуникации сам является пережитым опытом, а семантика реплики может быть представлена обычными `N/g/k` внутри `H`.

## 5.2. `FOLLOW` задаёт историю взаимодействия

Последовательные пережитые события связываются:

```text
H_EVENT_1
   |
 FOLLOW
   ↓
H_EVENT_2
   |
 FOLLOW
   ↓
H_EVENT_3
```

Связный эпизод при необходимости группируется нормативным `k`.

`H` хранит семантическую историю, а не execution log.

## 5.3. Повтор содержания и повтор события — разные вещи

Одинаковое утверждение может повторно встречаться в разных turns.

Domain-local dedup применяется к семантически эквивалентным фактам, но конкретные события общения остаются различимыми за счёт их episodic context / TIME / FOLLOW-структуры.

Так агент может помнить:

```text
пользователь сообщил X
позже пользователь снова сообщил X
```

не создавая при этом лишних копий одного и того же содержательного факта внутри того же domain.

# 6. Text Sensory и `S` Recognition

Внешний текст сначала является сенсорным входом, а не знанием.

```text
InputText != CanonicalAH
Perception != Belief
```

Порядок:

```text
raw text
  ↓
token / lexical candidate recognition
  ↓
surface lookup + morphology candidate lattice
  ↓
known form     → all matching existing s
unknown form   → unresolved lexical candidate, no canonical write
  ↓
external stimulation of every recognized candidate s
```

Text Sensory не выбирает lexical identity по top morphology score/order и не
создаёт/не расширяет canonical `s` на основании такого выбора. Morphology здесь
может только расширить runtime candidate lattice уже известными normal forms.

Распознанные candidate `s` получают сильное внешнее сенсорное возбуждение. Омограф может возбудить
несколько `s`; это сенсорная неоднозначность, а не утверждение об identity.

Создание нового `s` и добавление новой wordform в существующий `R_text` выполняются
только после того, как Perception/Integration разрешили lexical identity. Если
`normalized_hint` указывает на ещё неизвестную лексему, Integration не имеет права
fallback-нуться на другой `s` только потому, что тот содержит ту же surface form.

После semantic Integration внешний пользовательский prompt имеет второй lexical
activation stage. Каждый canonical `s`, реально выбранный как predicate symbol в
разрешённом semantic act, получает отдельный `RESOLVED_SYMBOL` seed. Этот seed:

```text
сильнее обычного NEW_FACT / REACTIVATED_FACT / EXPERIENCE seed;
применяется один раз на canonical S за turn;
получает и S, созданный только после Perception в этом же turn;
не применяется к H-only self-utterance агента;
не заменяет раннее candidate stimulation Text Sensory.
```

Так разделяются две задачи:

```text
Text Sensory: surface candidate activation до disambiguation;
Integration:  strong activation canonical S после disambiguation.
```

Это особенно важно для омографов: ранний слой не обязан делать canonical choice,
но resolved lexical identity перед формированием AgentContext должна стать одним
из сильнейших внешних источников возбуждения.

Дальше тот же текст передаётся Perception Layer для семантического разбора.

# 7. LLM Perception Layer

## 7.1. Trust boundary

**[H][P]**

LLM отвечает за интерпретацию естественного языка, но не владеет канонической памятью.

```text
Text
 ↓
LLM Perception
 ↓
PerceptionResult
 ↓
Deterministic Integration
```

LLM не имеет права:

```text
назначать canonical UID;
выбирать entity по произвольному UID;
писать C/P/H/L напрямую;
удалять/merge-ить canonical entities;
самостоятельно регистрировать T;
использовать w как confidence;
подменять deterministic reasoner скрытым proof.
```

## 7.2. `PerceptionResult`

Runtime-only:

```text
PerceptionResult
├── source.text
├── acts[]
│   ├── AssertionCandidate
│   ├── QueryCandidate
│   └── CommandCandidate
├── act_dependencies[]
└── diagnostics
```

Один turn может содержать несколько acts.

### `ClauseFrameGraph` — runtime structural layer

**[P]** До построения `PerceptionResult` parser формирует dependency-oriented `ClauseFrameGraph`. Это runtime-only структура: она не является новым AH-типом и не материализуется в `C/P/H/L`.

```text
source tokens / morphology
        ↓
clauses + predicate heads
        ↓
ClauseFrameGraph
├── matrix → subordinate
├── finite matrix → nonfinite child
├── matrix → quoted clause
├── predicate coordination groups
└── root / embedded force domains
        ↓
semantic relation decisions
        ↓
PerceptionResult
```

**[P] Source order не задаёт parent/child семантику.** Он допустим только как стабильный порядок обработки независимых peers. Если structural evidence уже даёт направление, оно используется независимо от позиции токенов: в `Улыбаясь, Иван вошёл` finite `вошёл` является matrix frame, а `улыбаясь` — dependent nonfinite frame, хотя находится раньше в строке. Semantic role связи (`OBJECT/PURPOSE/CAUSE/HOW-TO/...`) определяется после ориентации frames и не выводится из направления dependency.

**[P] Speech-act force определяется на уровне clause/root, а не один раз на всё предложение.** Терминальный `?` не превращает каждый predicate того же orthographic sentence в `QUERY`. В `Скажи, когда он придёт?` matrix imperative остаётся `COMMAND`, а subordinate content не становится самостоятельным query-act только из-за внешнего вопросительного знака. Напротив, quoted/direct speech образует собственный force-domain: в `Он спросил: «Ты придёшь?»` matrix frame и quoted query сохраняют разные illocutionary types. Каноническая quotation scope/materialization определяется отдельным runtime scope layer; `ClauseFrameGraph` только сохраняет структурную границу.

Для сохранения этой структуры после parser-а `AssertionCandidate`, `QueryCandidate` и `CommandCandidate` имеют turn-local refs (`A* / Q* / C*`), а `PerceptionResult.act_dependencies` проецирует structural edges `SUBORDINATE / NONFINITE / QUOTED`. Эти edges валидируются как acyclic runtime graph, но сами по себе не являются `ActantRole`, `L.ID` или доказательством truth.

**[P] Zero copula является clause-level implicit predicate candidate.** Обычные nominal predications (`Иван — врач`, `Иван врач`) создают runtime implicit `быть` frame даже без adjective/PRED token. Несколько независимых nominal predications (`Иван врач, Мария учитель`) остаются несколькими frames. Само обнаружение zero-copula shell не назначает `SUBJECT/STATE`: nominal participants проходят обычное predicate-relative semantic role resolution.

**[P] Predicate coordination является group-level structural property.** `ClauseFrameGraph` хранит coordinated peer frames отдельно от parent/child dependencies. Сам факт группы не означает, что все fillers общие. После построения semantic actants parser может поднять один уже разрешённый filler на уровень coordination group только если для той же роли нет конкурирующего filler-а. Один и тот же механизм применяется к любой `ActantRole`; отдельные ветки `subject inheritance`, `object ellipsis`, `recipient ellipsis` и т.п. не являются архитектурной нормой.

Для формально сильных случаев sharing разрешается детерминированно: общий peripheral `SUBJECT` при отсутствии нового subject-domain; postposed `OBJECT` у coordination из устойчиво transitive predicates; resolved pronominal object-ellipsis при совместимой правой predicate frame. Для остальных structurally plausible fillers — peripheral относительно всей группы либо непосредственно стоящих перед coordinator и допускающих rightward ellipsis — после структурного сужения допустим ровно один bounded `SHARED/LOCAL` probe. Он не выбирает новую canonical role, а отвечает только на вопрос, относится ли уже установленный filler той же роли к выбранным coordinated frames. При конкурирующих fillers или разных semantic `SUBJECT` sharing запрещён.

Следствия:

```text
Иван купил и прочитал книгу
→ BUY.SUBJECT = Иван
→ READ.SUBJECT = Иван
→ BUY.OBJECT = книга
→ READ.OBJECT = книга

Иван открыл дверь и закрыл окно
→ два разных OBJECT; group sharing запрещён
```

### Modifier attachment graph и relative antecedents

**[P] Attachment строится как runtime relation `modifier → possible targets`, а не как набор preposition/role special cases.** Для adpositional modifier parser сначала перечисляет структурно допустимых владельцев: текущую predicate frame и локально прилегающие nominal spans. На этом этапе не используются `OBJECT`, падеж, конкретный предлог или уже выбранная AH-role. Поэтому ambiguity обнаруживается одинаково независимо от того, какой actant модель выбрала первым.

```text
Я увидел человека в парке

modifier: «в парке»
targets:
  - event SEE
  - nominal «человека»
```

Если структурно допустим ровно один target, parse продолжается. Если остаётся несколько materially different readings, действует обычный `StructuralClarificationSpec`; LLM не голосует за attachment скрыто. User-selected nominal attachment материализуется обычной lexical predicate realization: описываемый nominal является semantic holder (`SUBJECT`), а semantic role modifier filler определяется отдельным predicate-relative role decision. Нового opaque `L.ID` для attachment не вводится. Конкретные ветки `с+instrumental → OBJECT_ATTACHMENT`, `OBJECT + PP` и т.п. не являются архитектурными механизмами.

**[P] Relative antecedent resolution работает по candidate set, а не по nearest nominal.** Candidates в первую очередь берутся из уже распознанных source actants parent frame; для headless nominal fragment допускается source-NP fallback. Morphological agreement используется только как отрицательный structural filter. Coordinated NP является одним antecedent candidate и может целиком заполнять relative role. Если после фильтрации остаётся несколько source mentions, допустим один bounded local-label probe `C1..Cn/UNCLEAR`; он не видит canonical UID. `UNCLEAR` сохраняет полные runtime alternatives.

Relative adverbs (`где/куда/откуда/когда`) получают relative structure только при наличии предшествующего nominal anchor (`дом, где...`, `день, когда...`). Без nominal anchor (`я знаю, где...`, `я помню, когда...`) они остаются обычными subordinate connectors; surface marker сам не доказывает relative attachment или canonical role.

**[P] NP/PP chunking сохраняет structural phrase integrity, но не назначает semantics.** Adjective/participle/number modifiers и однозначные genitive dependents могут образовывать один NP (`центр большого города`), при этом case-syncretic dependent не поглощается. PP включает весь nominal complement (`в центре города`). Coordinated PP (`в Москве и в Париже`, `из Москвы или Петербурга`) становится одной `AND/OR` actant composition вместо преждевременного набора независимых fillers. Ни один из этих chunking rules сам по себе не выбирает `LOCATION/SOURCE/TIME/...`.

```text
AssertionCandidate
```

## 7.4. Вложенные кандидаты

До появления canonical UID используются локальные ссылки:

```text
FC_1 = MOVE(...)
FC_2 = SAY(OBJECT -> candidate_ref(FC_1))
```

После интеграции:

```text
N_SAY.OBJECT -> N_MOVE
```

### Семантическая роль вложенной ситуации

**[P]** Вложенная ситуация, которую предикат выбирает как своё содержание / complement, представляется через `OBJECT -> candidate_ref(...)`. Это относится не только к сообщению/мышлению, но и к желаемой, запрошенной, начатой и аналогично выбранной ситуации.

```text
Иван попросил Марию прочитать книгу

REQUEST
├── SUBJECT   -> Иван
├── RECIPIENT -> Мария
└── OBJECT    -> READ(...)

Мария хочет купить билет

WANT
├── SUBJECT -> Мария
└── OBJECT  -> BUY(...)
```

`PURPOSE` используется только когда дочерняя ситуация обозначает цель / intended result, **ради которой выполняется родительское действие**, а не содержимое самого родительского предиката.

Controller вложенного предиката — отдельное semantic resolution. Наличие `RECIPIENT`, `OBJECT` или `SUBJECT` у родителя само по себе не разрешает controller универсально; например разные control-предикаты могут выбирать разных участников.

### Bounded semantic probes

**[P]** После детерминированного сужения semantic probe выполняет только одну локальную задачу и использует temperature-zero generation с точным коротким английским protocol label. Для бинарной развилки ожидается ровно `A/B` или `YES/NO`; для действительно конечного множества локальных candidates допустим один прямой `C1/C2/...` choice. Если неоднозначность должна быть сохранена, в protocol физически присутствует `UNCLEAR`. Любой bounded semantic choice использует только exact generation: likelihood/logprob scorer, margin threshold, calibration veto и скрытый tournament не являются semantic voter-ами.

```text
Python removes only formally impossible candidates
→ one bounded semantic probe
→ exact runtime label
→ protocol + admissible-set validation
→ deterministic construction
```

Malformed output fail-closed. Никакой отдельный score/margin не имеет права подтверждать, отклонять или переопределять корректный protocol label.

**[P] Protocol labels отделяются от человекочитаемых описаний вариантов.** Если runtime decision использует labels `FIRST/SECOND`, `OBJECT/RECIPIENT` и т.п., секция `CHOICES` содержит только допустимые labels; участники/описания передаются отдельно. Модель не должна выбирать строку вида `SECOND: Иван`, если канонический runtime protocol ожидает только `SECOND`.

**[P] Семантическое решение откладывается до минимально достаточного структурного контекста.** Perception не должен просить LLM выбирать между ролями заранее, если последующая детерминированная структура способна сузить развилку сильнее. В частности, поверхностный прямой accusative может оставаться обычным `OBJECT`-кандидатом; переинтерпретация участника как `RECIPIENT` допустима только после независимого установления вложенного `OBJECT`-content, когда возникает реальный конфликт единственного semantic `OBJECT`-слота и остаётся узкая semantic cue-развилка, например `CONTENT_ADDRESSEE / NOT_CONTENT_ADDRESSEE`; положительный cue затем детерминированно отображается Python в runtime `RECIPIENT`.

**[P] Детерминированное сужение ролей допускается только из отрицательного доказательства, которое формально исключает роль.** Совпадение с частым падежом, конкретным предлогом, наречием, словарной леммой или конструкцией само по себе не является доказательством канонической AH-роли. Такие признаки остаются evidence для последующего semantic decision. Напротив, формальное противоречие — например несовместимое finite agreement для `SUBJECT` — может удалить роль из множества допустимых. Отсутствующая/неоднозначная морфология не считается отрицательным доказательством.

**[P] `SUBJECT` является семантической ролью actor/holder/experiencer, а не именем грамматического nominative subject.** Поэтому согласованный `NOM` сам по себе не создаёт `SUBJECT`, `DAT/ACC` не исключают `SUBJECT` для experiencer-конструкций, а вопросительное `кто` не гарантирует `SUBJECT` (например, в passive clause оно может запрашивать semantic `OBJECT`). Грамматические subject-like spans разрешено использовать для структурной ориентации/coordination, но canonical ActantRole назначается только после predicate-relative semantic resolution либо отдельной формально доказанной structural norm (например, явно распознанной passive voice).

**[P] Role routing после структурного сужения выполняет одно bounded semantic decision для одного TARGET.** Реальный broad200 показал, что иерархический family-tree и последующая v0.15 property-ladder нестабильны по одной общей причине: несколько последовательных semantic probes умножают вероятность ошибки, а отрицательный ответ на раннем шаге способен навсегда удалить правильную роль. Поэтому Perception сначала детерминированно удаляет только формально невозможные роли, затем один раз показывает модели естественно-языковые relation contracts всех **реально оставшихся** кандидатов и ожидает ровно один runtime semantic cue. Cue не является `ActantRole`, UID, T или N и никогда не попадает в AH; Python владеет отображением `RuntimeRoleCue → ActantRole` и проверяет, что выбранный cue принадлежит уже допустимому множеству. Для role selection запрещены likelihood scorer/margin и скрытые tournaments: используется обычная deterministic generation с exact protocol label и fail-closed validation. Если `allowed_roles` уже сужено структурой, prompt физически не содержит исключённых ролей.

**[P] Человекочитаемое описание role-кандидата является relation contract, а не кратким словарным gloss.** Оно формулирует отношение `TARGET` к текущему событию/предикату и, где ближайшие роли семантически соседствуют, явно проводит границу между ними. Например TOOL означает отдельный инструмент, используемый для выполнения события, тогда как MATERIAL означает вещество/компонент, входящий в состав затронутого или результирующего объекта; TIME локализует событие на временной оси, тогда как HOW-TO описывает способ выполнения. Это не добавляет новую онтологию: модель выбирает runtime semantic cue по relation contracts только среди структурно допустимых кандидатов, а Python владеет отображением результата в `ActantRole`.

**[P] Формальная морфология может использоваться как отрицательное evidence по типу выражения, но не как положительный semantic-role shortcut.** Если все materially possible чтения выбранного span являются чистым `ADVB`, он не может внезапно стать именным SUBJECT/OBJECT/RECIPIENT/SOURCE либо физическим TOOL/MATERIAL; эти роли могут быть исключены до semantic probe. Но само наречие не доказывает TIME, LOCATION, HOW-TO, CAUSE и т.д. — оставшаяся семантическая развилка по-прежнему решается bounded semantic probe.

**[P] Управляющий предлог является частью evidence span, но не таблицей `preposition → ActantRole`.** Для вопроса/актанта Perception сохраняет предлог вместе с его зависимым выражением и передаёт этот минимальный контекст semantic router-у. Значение SOURCE/PURPOSE/LOCATION и т.п. не выводится из одной строки предлога, если это не доказано отдельной структурной нормой.

**[P] То же правило действует внутри relative clause.** Если relative connector управляется предлогом, evidence для его роли включает полный PP (`PREP + relative form`), а bare-case shortcut не имеет права отбросить семантику предлога. Relative role использует тот же one-shot runtime role cue, что обычный actant. Поиск antecedent рассматривает только materially structural nominal readings; микроскопическое несвязанное NOUN-чтение служебного PREP не может стать antecedent.

**[P] Нормализация количества не предсказывает semantic role по словарю единиц.** `NUMERAL + nominal` объединяется в одно значение длительности только **после того**, как nominal head уже независимо классифицирован как `DURATION`. Тогда число становится частью того же source-denoting filler (`два часа`). Если head классифицирован как `OBJECT`, обычная структура `OBJECT + AMOUNT` сохраняется (`три книги`).

**[P] `normalized_hint` является опциональным retrieval hint, а не требованием переводить каждый filler в noun lemma.** Source-denoting adverbial или directional expression может оставаться каноническим filler по своей наблюдаемой форме (`утром`, `домой`), если именно эта форма несёт нужную денотацию. Oracle/Integration не должны объявлять такой факт неверным только из-за отсутствия искусственной noun-normalization.

**[P] Лексически многозначные origin-prepositions не являются достаточным доказательством SOURCE.** В частности, поверхностные `из`/`от` могут быть evidence для origin/source reading, но не имеют права напрямую присвоить canonical SOURCE до semantic resolution: та же форма может участвовать в материальном, причинном и других отношениях. Удаление такого shortcut не запрещает детерминированные структурные нормы там, где роль действительно формально доказана; оно запрещает только `surface preposition → canonical role` как самостоятельное семантическое решение.

**[P] Лексическая неоднозначность morphology разрешается отдельно от semantic-role ambiguity.** Если после material filtering один surface token всё ещё имеет ровно две materially plausible lexical normal forms, analyser score/order не выбирает canonical lexical identity. Perception сначала выполняет **mirrored comparative A/B**: один и тот же сравнительный вопрос задаётся как `A=lemma1, B=lemma2`, затем с переставленными кандидатами. Если обе ориентации выбирают одну dictionary lemma, она принимается. Если ответы демонстрируют чистый positional bias, разрешён один **position-free literal fallback**: модель должна написать только dictionary lemma из контекста, а Python принимает ответ лишь при точном совпадении ровно с одним из двух уже детерминированно заданных morphology candidates; любое третье значение/malformed output fail-closed. Это не scorer и не новый voter по произвольному множеству. Выбранная lexical form лишь фильтрует доступные morph analyses для дальнейшего синтаксиса и entity lookup; она не создаёт canonical UID/T/N и не назначает ActantRole. Если lexical candidates больше двух и детерминированная структура не сузила их до двух, Perception fail-closed вместо hidden tournament/score winner. Тот же принцип применяется к predicate homographs.

### Predicate sense и выбор `T`

**[P] `sense_hint` — runtime semantic cue, а не canonical identity key.** Один predicate `S` может иметь несколько canonical `T`, в том числе два `T` с одинаковым набором ролей, если это разные lexical senses. Поэтому `S + role set` недостаточно для выбора `T`.

Перед canonical write Integration выполняет read-only preflight для уже известного lexical predicate:

```text
current predicate occurrence
+ source context
+ sense_hint?
+ explicit current roles/bindings
+ existing T usage profiles
        ↓
UID-free local options
C1 / C2 / ... / NEW / UNCLEAR
        ↓
Perception exact-label decision
        ↓
deterministic local-label → canonical T mapping
```

Модель не видит UID `T`. Existing options описываются только role schema и краткими observed-use bindings, полученными из canonical `N`. `NEW` означает, что текущий predicate meaning отличается от всех существующих options; тогда создаётся новый `T` даже если его role set совпадает с уже существующим. `UNCLEAR` не разрешает fallback к smallest-role-set/first-UID: ambiguity остаётся явной и integration fail-closed/уходит в clarification path.

`PredicateCandidate.template_selection` — runtime-only результат deterministic mapping после semantic choice. Он может содержать уже выбранный canonical `T` либо указание создать новый sense. Этот field никогда не парсится из model output. После создания нового `T` query/command runtime candidate нормализуется к конкретному выбранному `T`, чтобы downstream inference снова не выполнял `S + role set` guessing. Канонический формат `T=<UID,s*,A>` при этом не расширяется новым sense field.

**[P] Lexeme-hypothesis probe получает morphology profile проверяемого кандидата, но не новую каноническую задачу.** В profile передаются только уже имеющиеся analyser facts наблюдаемой формы (POS, case/number/gender и значимые grammeme-маркеры вроде passive/indeclinable/name/abbreviation). Это помогает различить genuine homographs в контексте без словарных латок. После выбора lexical identity решение монотонно: последующие normalization/entity-lookup utilities обязаны использовать выбранную лемму и не имеют права заново выбрать другую normal form по score/order.

**[P] Падежный синкретизм одной принятой лексемы не разрешается порядком `if/elif`.** Materially possible case readings сохраняются как structural evidence до bounded semantic role decision. Ни синкретизм, ни «чистый» ACC/DAT/NOM сами по себе не назначают и не сужают canonical AH-role по таблице `case → role`: `ждал час` требует `DURATION`, `мне холодно` — semantic experiencer `SUBJECT`, а governed accusative/dative зависит от текущего predicate contract. Формальное case/agreement evidence может только исключить роль, если существует доказуемое грамматическое противоречие. Аналогично postverbal NOM/ACC при устойчиво transitive finite predicate не является unambiguous SUBJECT.

**[P] NP-internal genitive composition требует структурной однозначности.** Следующий nominal span поглощается как genitive-dependent предыдущего nominal head только если его materially possible core cases не содержат конкурирующего non-genitive чтения. Если та же форма materially допускает DAT/ACC/etc., spans остаются раздельными и дальнейшая семантика решается обычным pipeline. Это предотвращает превращение `OBJECT + RECIPIENT` в один lexical entity только из-за вероятного genitive prior.

**[P] Контекстно-свободный morph-score не имеет права уничтожать синтаксически возможное падежное чтение той же лексемы.** Если одна и та же наблюдаемая именная форма имеет materially-compatible разборы одной лексемы, отличающиеся падежом (например русское `Петра`: genitive/accusative), низкий prior конкретного падежа не является отрицательным синтаксическим доказательством. Такие case-syncretic варианты сохраняются до структурного сужения; unrelated low-probability homonyms по-прежнему фильтруются.

**[P] Grammatical person участвует в deterministic coreference compatibility как отрицательное evidence.** Если текущий anaphor имеет явный `3per`, а потенциальный antecedent имеет явный `1per` или `2per`, локальная coreference-гипотеза несовместима и не должна создавать runtime alternative только из-за совпадения числа/неопределённого рода. Это не выбирает antecedent семантически; оно лишь запрещает грамматически несовместимую связь и предотвращает ложные correlated alternatives между deictic speaker/addressee и third-person anaphor. При отсутствии person-evidence ничего не исключается.

**[P] Morphology-marked substantivized anaphors являются nominal-like expressions.** Формы с anaphoric/substantivized morphology участвуют в SUBJECT/OBJECT structure как именные, а не как обычные attributive adjectives. Если после deterministic agreement/coreference compatibility остаётся несколько turn-local source mentions, разрешён один bounded source-label probe (`C1..Cn/UNCLEAR`). Модель видит только исходные mention strings и выбирает локальный label, никогда canonical UID/entity ref. `UNCLEAR` или отсутствие единственного выбора сохраняет runtime alternatives для обычной Integration ambiguity handling.

**[P] Personalized provenance локальной proposition-композиции вычисляется до dependency-order Integration.** Если parent assertion прямо anchored к P-domain deixis (`SELF/USER`) и содержит child через `candidate_ref`, требование P распространяется по этому локальному containment graph до построения любого N. Это необходимо, потому что dependency ordering может интегрировать child раньше parent. Правило не является глобальным распространением domain по произвольным semantic links: non-deictic parent/child остаются C, если другого P/H provenance нет.

**[P] Fronted CONDITION охватывает contiguous additive consequent siblings.** Если clause builder представляет `Если A, B и C` как conditional child A, parent consequent B и следующий same-sentence top-level sibling с additive marker `и/да`, runtime conditional consequent содержит B и C. OR/adversative sibling автоматически не поглощается в тот же AND-consequent, потому что требует другой логической композиции.

**[P] Уже выбранный как семантически релевантный actant нельзя молча отбросить из-за неразрешённой role classification.** `role unresolved` после выбора span означает fail-closed/clarification. Частичная канонизация оставшихся ролей запрещена, потому что превращает неизвестность Perception в ложное утверждение более узкого frame.

**[P] Принятая parent-child semantic relation монотонна внутри одной parse-гипотезы.** Если после детерминированного сужения и bounded probe дочерняя ситуация уже принята как `OBJECT`-content, последующий локальный конфликт ролей участника может уточнить роль участника, но не имеет права переопределить ту же дочернюю ситуацию как `PURPOSE`, `CAUSE`, `HOW_TO` и т.п. Невозможность безопасно согласовать participant role означает fail-closed/clarification, а не semantic fallback к другой relation. Иначе поздний слабый cue получает право отменить более раннее уже принятое семантическое решение и способен записать формально валидную, но неверную канонику.

**[P] Service semantic cue отделяется от канонического имени роли, если ontology-label заставляет модель делать лишнюю формализацию.** После структурного сужения LLM должна отвечать на естественно-семантический вопрос минимального размера, а Python детерминированно переводит cue в runtime role. Например при уже доказанном `OBJECT`-content вопрос не требует от модели выбрать AH-термин `RECIPIENT`; модель выбирает `CONTENT_ADDRESSEE / NOT_CONTENT_ADDRESSEE`, после чего положительный cue отображается в `RECIPIENT`. LLM не должна знать внутреннюю онтологическую терминологию, если для решения достаточно более конкретного semantic cue.

## 7.5. Runtime alternatives

Несколько синтаксических вариантов от LLM:

```text
Candidate A
Candidate B
```

не являются `k`.

`k_AMBIGUOUS` создаётся только после deterministic resolution, если неоднозначность сохранилась между каноническими семантическими кандидатами.

### Structural clarification

**[P]** Не всякая сохраняющаяся неоднозначность является конкуренцией уже построенных canonical entity candidates. Если детерминированный parser обнаружил несколько **структурных чтений** одной source-конструкции и evidence недостаточно для выбора, LLM не должна угадывать attachment.

Протокол:

```text
source utterance
→ record original H experience
→ detect finite structural options
→ persist H-only k_STRUCTURAL_CLARIFICATION dialogue state
→ no C/P semantic reading is committed yet
→ ask user
→ explicit user selection
→ reparse original source with selected structural key
→ normal Perception validation / T completion / Integration
→ attach delayed semantic content to the ORIGINAL H experience
```

`k_STRUCTURAL_CLARIFICATION` — dialogue-state group в `H`, а не truth-level semantic object в `C/P`. Его option groups хранят только program-owned resolution key и user-visible label. Выбор пользователя не превращается в свободный LLM semantic vote.

Диагностический вызов, который не предъявляет clarification пользователю (`generate_response=False`), может вернуть structured clarification в результате, но не должен вооружать pending-dialogue queue: следующий независимый acceptance case не является ответом на предыдущий diagnostic case.

После выбора структурное чтение компилируется обычными `T/N/g/k/L`, без создания ad-hoc opaque relation ID. Например выбранное именное чтение `Пётр с биноклем` может материализоваться как обычная lexical predicate realization, тогда как predicate-attached чтение даёт `TOOL` родительскому `N`.

## 7.6. `QueryCandidate`

```text
QueryCandidate
├── local_id?
├── predicate
├── actants[]
├── requested_roles[]
├── query_mode
└── quoted
```

MVP:

```text
query_mode ∈ {FILL_ROLE, EXISTS}
```

`FILL_ROLE` может содержать одну или несколько незаполненных semantic roles. Поэтому:

```text
Кто кому что дал?
→ one QueryCandidate
→ requested_roles = [SUBJECT, RECIPIENT, OBJECT]
```

Это не три независимых вопроса. `QueryGoalBuilder` создаёт один multi-role inference goal, а reasoner обязан извлечь все requested bindings из **одного и того же canonical N**. Нельзя собирать ответ по одному role-fill search на роль, потому что тогда значения могут происходить из разных фактов.

Скалярный `requested_role` допустим только как backward-compatible runtime view для single-WH query и не является нормативным контрактом.

Quoted query сохраняется как содержание чужой/вложенной реплики и не попадает в top-level query execution текущего turn.

## 7.7. `CommandCandidate`

```text
CommandCandidate
├── local_id?
├── predicate
├── actants[]
├── negated
└── quoted
```

Отрицание является частью semantic command contract:

```text
Не открывай дверь
→ CommandCandidate(OPEN, OBJECT=door, negated=true)
```

Parser-local negation scope определяется тем же predicate-relative механизмом, что и для assertion; отрицание не должно теряться до behavioral layer.

Дальнейший поток:

```text
COMMAND
 ↓
semantic resolution
 ↓
behavioral decision
 ↓
execution
```

Quoted command является содержанием цитаты, а не приказом текущему агенту, поэтому не направляется в top-level execution.

## 7.8. Quotation scope

`QUOTED` structural edge в `ClauseFrameGraph` задаёт начало quotation scope. Все descendant acts под этим edge наследуют runtime `quoted=true`, даже если их непосредственная связь внутри цитаты имеет тип `SUBORDINATE` или `NONFINITE`.

Для assertion-content:

```text
quoted AssertionCandidate
→ canonical N with Mt.semantic_scope = QUOTED
→ may be referenced by matrix SAY / ASK / THINK-like proposition structure
→ no ordinary occurrence confirmation
→ no ordinary asserted-fact activation seed
→ ignored by ordinary EXISTS / ROLE_FILL world-fact lookup
```

Отрицание внутри цитаты создаёт `FALSE(scoped proposition)`, но не выполняет semantic correction/refutation внешнего world fact. Поскольку канонический `L` не имеет `semantic_scope`, directional `FOLLOW/CAUSE` relation, затрагивающий quoted proposition, не материализуется как обычный world-level `L`; это лучше явной потери quoted relation detail, чем ложное знание. Quoted-only conditional expression также не получает самостоятельный world-fact activation seed.

Для query/command-content:

```text
quoted QueryCandidate   -> preserve, do not execute as current query
quoted CommandCandidate -> preserve, do not execute as current command
```

Quotation scope ортогонален conditional scope: quoted conditional content остаётся quoted content, а не становится внешним утверждением только из-за наличия `IF`.

## 7.9. Proposition composition и nonasserted scope

Сложное предложение не обязано сводиться к плоскому списку assertions. Между
`ClauseFrameGraph` и canonical Integration существует runtime-only выражение:

```text
PropositionExprCandidate :=
    REF(local_assertion)
  | AND(expr, ...)
  | OR(expr, ...)
  | FALSE(expr)
```

Это не новый AH-тип. Integration отображает `REF` в scoped `N`, а логические
операторы — в уже существующие canonical `g_AND/g_OR/g_FALSE`. Поэтому
`сказал, что A и B`, `думает, что A или B`, а также ветви `IF` сохраняют
proposition-level композицию и не теряют дочерние frames.

`AssertionStatus` различает как минимум:

```text
ASSERTED
EMBEDDED
CONDITIONAL
```

Quotation остаётся ортогональным scope-флагом. `OBJECT`-content, `PURPOSE` и
`HOW-TO` по умолчанию являются `EMBEDDED`: соответствующий `N` создаётся для
ссылки из matrix proposition, но не считается самостоятельным фактом мира, не
получает ordinary confirmation/seed и исключается из обычного `EXISTS/ROLE_FILL`.
Фактивность не выводится из самого `что/где/когда` и должна быть отдельным
механизмом.

Conditional runtime contract хранит не только leaf refs, но и antecedent/consequent
`PropositionExprCandidate`. Integration материализует именно это дерево; набор из
нескольких refs нельзя безусловно заменять `AND`.

Surface subordinator (`чтобы`, `когда`, `где`, `куда`, `откуда`, `потому` и т.п.)
создаёт только structural subordinate edge. Он не присваивает canonical
`PURPOSE/TIME/LOCATION/SOURCE/CAUSE`; semantic relation parent↔child выбирается
после построения обоих frames.

Resource caps являются только защитой вычислений. Если после `max_acts` или
`max_actants_per_act` остаётся meaningful deterministic structure, parser обязан
завершиться explicit incomplete-parse error; частичный `PerceptionResult` не
передаётся в Integration.

# 8. Deterministic Integration

## 8.1. Назначение

Этот слой превращает неканонические LLM-candidates в точные структуры AH.

```text
PerceptionResult
      ↓
Candidate Validation
      ↓
Predicate / T Resolution
      ↓
Actant Resolution
      ↓
Entity Resolution
      ↓
Context / Deictic Resolution
      ↓
Ambiguity Handling
      ↓
Canonical Construction
      ↓
Domain Resolution
      ↓
Domain-local Deduplication
      ↓
Full Validation
      ↓
Atomic AH Mutation
      ↓
Activation Seed / Reactivation
```

Ни один полусозданный факт не должен остаться в памяти.

## 8.2. Predicate / Template Resolution

```text
PredicateCandidate
→ existing compatible T
| controlled monotonic expansion of one existing T
| validated creation of new T
```

`T` разрешается до финального mapping актантов, потому что именно `T` задаёт роли.

После resolution:

```text
FilledRoles(candidate) ⊆ Roles(T)
```

## 8.3. Entity Resolution

```text
ER(mention, Context, AH)
→ existing m
| ambiguity
| new m
```

Признаки:

```text
name / aliases
Pr
relations
facts
past H episodes
current activation
current Context
```

LLM поставляет semantic cues; deterministic resolver принимает каноническое решение.

`name / aliases` — retrieval index, а не identity key. Совпадение имени само по себе не доказывает, что упоминание относится к уже существующему `m`, особенно если кандидат находится в другом semantic domain.

Внутри одного turn уже установленная identity должна переиспользоваться через runtime `entity_ref`, даже если два evidence-span не совпадают буквально. Например `рядом с журналом` и относительное `который` могут ссылаться на один `m_ЖУРНАЛ`: содержащий span допустим как evidence того же semantic head.

Если до обычного lexical lookup уже имеется сильный provenance/identity anchor — `SELF/USER` deixis, разрешённый `candidate_ref` или ранее установленный turn-local `entity_ref` — Integration сначала вычисляет **provisional provenance domain**. Это не отдельный внешний Domain Resolver и не финальный commit: это детерминированное ограничение поиска сущности внутри той же транзакции. При таком domain lock одноимённый `m` из другого `C/P/H` не имеет права перехватить identity только по имени.

Если сильного provenance anchor нет, глобальный name/alias lookup может использоваться как candidate-generation механизм; несколько равноправных кандидатов должны остаться явной неоднозначностью, а не быть слиты по имени. Финальный domain routing выполняется после entity resolution по обычным правилам.

Если подходящего объекта нет — создаётся новый `m`.

Если кандидатов несколько и выбрать нельзя — создаётся `k_AMBIGUOUS`.

**[P] Relational reference resolution использует уже канонические факты без merge identity.** Описательная ссылка вроде `моего друга` сначала разрешает owner через deixis (`мой -> USER`) и descriptor как отдельную известную сущность/роль (`друг -> m_ДРУГ`). Затем deterministic resolver использует reverse actant index только как read-only retrieval: находит `N`, в котором одновременно участвуют owner и descriptor, и рассматривает прочего semantic participant как referent. Например уже сохранённое:

```text
N_ЕСТЬ
├── SUBJECT    -> m_USER
├── OBJECT     -> m_ДРУГ
└── AUXILLIARY -> m_МИША
```

даёт runtime resolution `моего друга -> m_МИША`, **не** превращая `m_ДРУГ` и `m_МИША` в один объект и не создавая нового canonical отношения. Если подходящих referent несколько, результат остаётся ambiguity. Поддерживающий `N` сохраняется как runtime evidence/attention anchor.

Для query такой referent и поддерживающий `N` могут получить отдельный `QUERY_RECALL` seed до turn-local post-input tick. Это attention/retrieval event: он не доказывает запрашиваемый predicate, не создаёт новый `N` и не является `h_N` confirmation. Exact inference после этого всё равно остаётся rule-driven; цель seed — дать Workspace/AgentContext уже найденную семантическую цепочку, когда exact predicate (`звать`, `называться` и т.п.) в AH отдельно не материализован.

## 8.4. Дейксис

```text
"я"      → SELF
"она"    → contextual entity resolution
"вчера"  → concrete TIME from Context
"там"    → active LOCATION from Context
```

Формально:

```text
Resolve(s, Context) -> q
```

Контекстные слова не получают постоянный плавающий `m`, если сами не стали предметом метаязыкового рассуждения.

## 8.5. Создание нового факта

```text
1. resolve predicate;
2. resolve/create predicate s;
3. resolve/create T;
4. resolve actants;
5. resolve/create semantic entities;
6. resolve C/P/H domain;
7. construct N;
8. construct required L/g/k;
9. validate complete semantic subgraph;
10. deduplicate in target domain;
11. atomic commit;
12. semantic seed / reactivation.
```

Actant relations уже содержатся в `N/T`; отдельные `L` для каждой пары `N → actant` не создаются.

## 8.6. Обновление `Pr`

После уверенного resolution владельца:

```text
target m/k/N
 ↓
show existing Pr to semantic matcher
 ↓
match existing property or propose new property name
 ↓
deterministic validation
 ↓
addProperty / editProperty
```

LLM не получает права произвольного property write.

# 9. Политика записи знаний

## 9.1. Формально валидное утверждение записывается

**[P] MVP**

```text
recognized assertion
+ formal validation passed
→ canonical fact
```

Внешний fact-check не блокирует запись.

Даже:

```text
"У Земли две луны"
```

может стать `N`, если это корректно распознанное утверждение.

Trust/belief не кодируются через `w`.

## 9.2. По умолчанию память растёт

```text

```

Совместимая информация дополняет существующий подграф.

Редактирование существующей identity выполняется только после уверенного resolution.

## 9.3. Временное изменение не равно противоречию

```text
Маша жила в Москве в 2025.
Маша живёт в Париже в 2026.
```

Это две ситуации с разными TIME, а не конфликт.

# 10. Deduplication

## 10.1. Только внутри target domain

```text
Equivalent(N_incoming, N_existing)
AND same_domain
→ Reuse(N_existing)
```

При reuse:

```text
N.Mt.occurrence_count += 1
reactivate N
```

Новый `N` не создаётся.

Если семантически эквивалентный факт есть в другом `C/P/H`, это не считается дубликатом для текущего домена.

## 10.2. `occurrence_count` не является весом

```text
occurrence_count != w
```

Повтор не делает:

```text
w += constant
```

Повтор создаёт confirmation/reactivation event, а изменение веса выполняет `h`.

## 10.3. Собственная реплика агента не подтверждает `C/P`

H-only запись собственного ответа:

```text
не increment-ит occurrence_count C/P-факта;
не считается внешним confirmation;
не запускает C/P self-training.
```

Повтор в самом `H` может учитываться как повтор пережитого содержания, не затрагивая C/P.

# 12. Activation и веса

## 12.1. `x`

`x` — текущий уровень возбуждения excitable AH-элемента.

Внешний текст сначала стимулирует распознанные `s`, а после канонической интеграции semantic seed получает соответствующий `N`.

## 12.2. `w`

```text
w != parser confidence

```

Чем больше `w`, тем сильнее данный путь участвует в spreading activation.

# 13. Ignition Engine

## 13.1. Время

Вся внутренняя динамика работает в engine ticks.

```text
engine running
→ ticks advance

engine stopped
→ memory time does not advance
```

В ticks измеряются:

```text
activation propagation;
decay;
Hebbian plasticity;
lifetime;
consolidation spacing;
GC timing.
```

`tick_rate` — частота вычислительного цикла. В runtime config она задаётся эквивалентным
`tick_interval_seconds = 1 / tick_rate`. Для MVP штатный wall-clock cadence:

```text
tick_rate = 1 Hz
tick_interval_seconds = 1.0
```

То есть при работающем clock один обычный cognitive tick планируется раз в секунду.
Когнитивное время всё равно измеряется **числом реально выполненных ticks**: если вычисление
заняло дольше интервала, clock не создаёт скрытые catch-up ticks. Поэтому все параметры в
`*_ticks` остаются tick-based; при штатном 1 Hz один tick практически соответствует одной
секунде wall time.

`ν` — частота импульсов pacemaker-а, реализуемая поверх того же tick clock.

## 13.2. Synchronous snapshot

**[P]**

Каждый tick считается из одного snapshot.

```text
State_τ
   ↓
calculate all tick effects
   ↓
simultaneous commit
   ↓
State_(τ+1)
```

Следствия:

```text
порядок обхода элементов не влияет на результат;
новый сигнал проходит максимум одно новое ребро за tick;
новый w начинает влиять только со следующего tick;
GC не удаляет элемент посреди вычисления snapshot.
```

## 13.3. Incoming buffer

Для каждого excitable элемента на tick хранится сумма пришедших импульсов.

Ассоциативная связь:

```text
impulse(A→B) = output_A * L.w
```

Гиперсвязь `N` передаёт свой output актантам через `N.w`.

Для lexical recall canonical pointer direction и activation direction различаются:

```text
canonical structure:  T -> S, N -> T
activation retrieval: S -> T -> N -> actants
```

`S -> T` передаёт новый lexical output без дополнительного веса: `T` является
шаблоном именно этого predicate-S. `T -> N` масштабируется `N.w`, поэтому сила
конкретной реализации участвует в том, насколько легко она всплывает по
упоминанию предиката. Это feed-forward retrieval path; обратного `N -> T -> S`
пути в MVP нет, чтобы не создавать структурный положительный feedback loop.

Scoped proposition content (`EMBEDDED/CONDITIONAL/QUOTED`) не становится
самостоятельным lexical-recall root. Если `N` явно superseded через `FALSE(N)`,
лексический путь возбуждает актуальный `FALSE(N)`, а не исторический positive N.

Итог:

```text
z_i = Σ incoming weighted impulses
```

Impulses, рассчитанные на `τ`, записываются во входной buffer соседей для следующего causal tick.

## 13.4. `f(x_t, z)` — активация и output

**[D][P]**

```text
x_raw = f(x_t, z)
x_act = clamp(x_raw)
input_gain = max(0, x_raw - x_t)
output_t = min(x_max, input_gain)
```

`x` и `output` имеют разный смысл:

```text
x      = retained cognitive activation;
output = только вновь приобретённое возбуждение этого tick,
         которое ещё должно распространиться дальше.
```

Стабильный остаточный `x`, включая epoch-local floor, не переизлучается на каждом tick. Иначе один и тот же сохранённый заряд превращался бы в вечный источник энергии для downstream-узлов. Передача импульса не уменьшает `x` источника.

Новый входной пакет измеряется **до storage clamp**. Поэтому уже сильно возбуждённый
узел не «глохнет» для распространения нового внешнего события только потому, что
его `x` близок к `x_max`. Например повторное сильное упоминание S при `x≈0.9`
может передать почти полный новый lexical packet, хотя сохранить внутри узла ему
остаётся лишь небольшой headroom до `x_max`. При `z=0` `input_gain=0`, поэтому
relative floor по-прежнему ничего сам не переизлучает.

`x_raw` используется для определения силы новой реактивации до насыщения, после чего применяется configurable clamp:

```text
0 <= x_act <= x_max
```

## 13.5. Первый tick нового возбуждения

**[D][P]**

Если элемент только что получил новое возбуждение / начал новый decay epoch:

```text
incoming z
  ↓
f(x,z)
  ↓
x_act
  ├── set current excitation
  └── send output
  ↓
activation/reactivation event
  ↓
NO g on this fresh tick
```

Новое возбуждение не гасится сразу после получения.

## 13.6. Следующие ticks

Для уже возбуждённого элемента:

```text
existing x
+ incoming z
   ↓
f(x,z)
   ↓
x_act / output
   ↓
plasticity event accounting
   ↓
g decay
   ↓
x_next
```

При `z = 0` retained `x` продолжает жить и затухать по `g`, но `output=0`: уже распространённое возбуждение не отправляется соседям повторно.

## 13.7. `g` — decay

Decay — отдельная операция, не часть `f`.

Базовая форма epoch задаёт относительную плавающую нижнюю границу:

```text
x_floor = α * x_start
0 <= α < 1
```

`g` затухает только transient-компоненту над floor:

```text
transient = max(0, x - x_floor)
transient_next = transient * R_step(age)
x_next = x_floor + transient_next
```

где `R(0)=1`, `R(age)` монотонно стремится к `0`. Эквивалентная полная epoch-кривая `D(age)` удовлетворяет:

```text
D(0) = 1
lim D(age) = α
```

Следствие: **одни только engine ticks не имеют права стереть активный контекст ниже относительного floor**. Пользователь может долго читать, думать или писать следующий prompt; retained activation сохраняется. При этом floor не является источником постоянных импульсов, потому что `output` передаёт только новый прирост `x`.

Желаемая форма transient decay:

```text
медленный верхний спад
→ более резкая средняя часть
→ мягкое приближение к floor
```

Конкретная функция и `α` — config.

Новый внешний prompt начинает новую общую decay epoch от текущего состояния:

```text
x_start_i := current x_i
x_floor_i := α * x_start_i
decay_age_i := 0
```

Floor не пересчитывается каждый tick и не следует за текущим `x`. Он меняется только при новой epoch: новый prompt или достаточно сильная не-background реактивация конкретного элемента.

## 13.8. Reactivation и reset локального decay epoch

Для уже затухающего элемента вычисляется ожидаемая потеря без подпитки:

```text
x_decay_expected = g(x_t, decay_state)
Δ_decay = x_t - x_decay_expected
```

После входа:

```text
x_raw = f(x_t, z)
Δ_input = x_raw - x_t
x_act = clamp(x_raw)
```

Сравнение выполняется до clamp, чтобы saturation по `x_max` не скрывало силу входного воздействия.

Правило:

```text
reset_threshold = max(
    Δ_decay * reactivation_reset_ratio,
    reactivation_min_input
)

if semantic_input and Δ_input > reset_threshold:
    reset local decay epoch
    x_next = x_act
    x_start = x_act
    decay_age = 0
else:
    continue current decay epoch
    x_next = g(x_act, x_start, decay_age)
```

Равенство epoch не сбрасывает.

Слабый input всё равно влияет на `x`, но затухает как transient над прежним floor и не поднимает `x_start`. Чисто pacemaker-порожденный input также не имеет права rebase-ить floor независимо от своей величины: ν — background excitability, а не новый смысловой контекст.

Сам факт отправления outgoing impulse не reset-ит decay epoch источника.

## 13.9. Канонический tick algorithm

```text
INPUT:
  snapshot State_τ
  incoming_buffer_τ
  external/pacemaker seeds scheduled for τ

PHASE 1 — collect
  z_i := sum incoming impulses + scheduled seeds

PHASE 2 — activation/output
  x_raw_i := f_i(x_i, z_i)
  Δ_input_i := x_raw_i - x_i
  x_act_i := clamp(x_raw_i)
  output_i := max(0, x_act_i - x_i)
  detect activation/reactivation event a_i

PHASE 3 — propagate
  for every outgoing L:
      next_buffer[target] += output_i * L.w
  for every active N hyperconnection:
      next_buffer[actant] += output_N * N.w

PHASE 4 — plasticity
  calculate pending L.w / N.w updates from events of this tick

PHASE 5 — decay
  fresh/reset activation:
      x_next_i := x_act_i
      decay_age := 0
  otherwise:
      x_next_i := g_i(x_act_i, x_start_i, decay_age_i)
      # decay transient above alpha*x_start; floor itself is retained

PHASE 6 — lifecycle / GC decisions
  update N lifecycle from qualifying events
  mark expired / orphan candidates

PHASE 7 — Workspace
  Workspace_(τ+1) := refs with committed x_next > t

PHASE 8 — simultaneous commit
  commit x
  commit w
  commit decay state
  commit lifecycle
  swap incoming buffers
  apply GC deletions
```

# 14. Пластичность `h`

## 14.1. Activation event

```text
a_i(τ) = 1
```

только если на tick произошла новая активация / реактивация.

Остаточное:

```text
x > 0
```

не является новым Hebbian event.

**[P]** Pacemaker provenance распространяется вместе с чисто pacemaker-порождённой
волной возбуждения через последующие causal ticks. Такая background-wave может менять
`x`, попадать в Workspace и распространять импульсы, но не считается associative
experience для `h` и не является qualifying reactivation для lifecycle. Если к узлу
примешивается внешний/семантический input, activation снова считается обычным
cognitive event.

## 14.2. `h_L`

Для существующей связи `A → B`:

```text
a_A(τ)=1
AND
a_B(τ)=1
→ L.w increases
```

С задержкой в один tick:

```text
A activates on τ
B activates only because of A on τ+1
```

положительное Hebbian strengthening автоматически не происходит.

Иначе обычное распространение само бесконечно усиливало бы собственный путь.

Weak depression:

```text
exactly one endpoint has activation event on tick
→ weak L.w decrease
```

Инактивность обоих endpoint сама по себе ничего не ослабляет.

Обычная depression имеет ненулевой configurable floor и не удаляет семантическую связь.

## 14.3. `h_N`

`N.w` меняется по семантическим событиям подтверждения / опровержения.

```text
external repeated assertion
resolves to same N
→ confirmation event
→ N.w increases through h_N

explicit FALSE(N)
→ refutation event
→ strong N.w decrease
```

Собственный ответ агента не создаёт confirmation event для `C/P`.

`occurrence_count++` и `h_N` — разные операции.

# 15. Lifecycle и GC

## 15.1. Consolidation только для `N`

**[P]**

```text
NEW
 ↓ qualifying spaced reactivation #1
REINFORCED
 ↓ qualifying spaced reactivation #2
CONSOLIDATED
```

`m`, `g`, `k`, `L` не имеют отдельного consolidation lifecycle.

Машинные lifecycle-поля хранятся как служебное состояние `N`, например через `Mt`.

## 15.2. Lifetime

```text
NEW:
  expires_tick =
    created_tick + initial_lifetime_ticks

REINFORCED:
  expires_tick =
    reactivation_tick + reinforced_lifetime_ticks

CONSOLIDATED:
  no ordinary TTL expiration
```

## 15.3. Qualifying reactivation

```text
qualifies =
    activation/reactivation event
    AND enough engine ticks since previous qualifying event
```

Быстрый внутренний цикл не должен консолидировать факт за несколько мгновенных проходов.

Позднее самостоятельное associative resurfacing может считаться reactivation, если выдержан spacing.

## 15.4. GC

GC удаляет:

```text
expired NEW N;
expired REINFORCED N;
hackathon-required isolated/lost structures;
true structural orphans after deletion.
```

`CONSOLIDATED` не удаляется обычным TTL.

После удаления `N` связанные `m/g/k/L` удаляются только если на них больше нет живых ссылок.

`FALSE(N_old)` и H-ссылки защищают исторически значимый `N_old` от ошибочного orphan GC.

**[P]** `H`-гиперузел с `Mt.event_instance=true` является самим пережитым событием
диалога и не удаляется ordinary TTL GC независимо от стадии consolidation. Это
не означает автоматическую консолидацию содержания C/P; правило защищает identity
эпизода и `InteractionContext.last_experience_ref`, в том числе пока медленная LLM
генерирует ответ и engine ticks продолжают идти.

# 16. Workspace

## 16.1. Определение

**[M][P]**

```text
Workspace_τ =
{ ref(e) | e is excitable and x_e(τ) > t }
```

Workspace содержит refs, а не копии.

```text
AH = source of truth
Workspace = dynamic active view
```

## 16.2. Порог `t`

```text
x > t
→ элемент является самостоятельным активным корнем контекста

x <= t
→ элемент не является самостоятельным корнем
```

Но:

```text
x <= t
```

не означает:

```text
deleted;
unreachable;
blocked for spreading;
blocked for inference.
```

`t` не является propagation gate.

## 16.3. Нет второго cognitive reranker

После `x > t` не вводится дополнительный:

```text
top-k;
LLM relevance selector;
semantic reranker.
```

Иначе фокус внимания определял бы уже не Ignition Engine.

Token budget — инфраструктурное ограничение сериализации, а не новый механизм когнитивной релевантности.

**[P]** Переполнение token/context budget обрабатывается fail-closed. Runtime не имеет
права молча обрезать начало `AgentContext`, удалять ACTIVE roots или подменять Workspace
скрытым top-k. Проверка выполняется на реально токенизированном LLM input с резервом
под generation; overflow возвращает явную ошибку.

## 16.4. Workspace и reasoner

Workspace — приоритетная область старта поиска.

Reasoner может переходить к неактивным элементам, если это требуется логическим правилом.

Сам факт посещения reasoner-ом не добавляет элемент в Workspace.

# 17. Детерминированная проекция в LLM

## 17.1. Три ответственности

```text
Ignition decides WHAT is active.
Workspace records active refs.
Projector decides HOW to represent their semantics.
```

Projector не решает, что важно.

## 17.2. Режимы `ACTIVE` и `DEPENDENCY`

`ACTIVE`:

```text
root independently selected for AgentContext
→ full own semantics
→ own Pr exposed if type has Pr
→ Mt hidden
```

`DEPENDENCY`:

```text
dereferenced only to understand an ACTIVE root
→ minimal semantic representation
→ Pr not exposed
→ dependency does not become Workspace member
```

Projection mode — режим сериализатора. Поэтому `L`, не имеющий собственного `x`, может быть root-представлением, например когда он является semantic inference result; это не означает, что canonical `L` получил excitation field.

## 17.3. Один full block на root

Каждый active root сериализуется полностью ровно один раз.

Ссылки внутри него не запускают recursive full projection.

Если referenced element сам является active root, его full block выводится отдельно.

## 17.4. MinimalSemanticProjection

```text
MinimalSemanticProjection(e)
→ минимальное представление,
  достаточное LLM для понимания семантики e
```

Внутренний dereference может идти глубже одного уровня, если это нужно для построения смысла, но output:

```text
не раскрывает чужие Pr;
не раскрывает лишний neighborhood;
не меняет Workspace;
не показывает x/w/t/ticks;
не запускает рекурсивный full dump.
```

## 17.5. Проекция по типам

### `s`

```text
ACTIVE / DEPENDENCY
→ semantic lexical symbol

R_text
→ never exposed
```

### `m`

```text
ACTIVE
→ identity / human-readable semantics
→ all own Pr

DEPENDENCY
→ minimal identity semantics only
```

### `T`

```text
ACTIVE
→ predicate semantics
→ actant-role schema

DEPENDENCY
→ only predicate semantics + role mapping
  required to understand containing N
```

### `N`

```text
ACTIVE
→ predicate via T→s
→ role → actant mapping
→ own Pr
→ no w / Mt

DEPENDENCY
→ compact semantic statement
```

Пример:

```text
[N1]
Иван читает книгу
```

### `L`

```text
root result
→ relation ID
→ direction
→ both endpoints minimally represented

dependency
→ same minimal structural meaning
```

Пример:

```text
Собака IS-A Животное
```

### `g`

```text
ACTIVE
→ FunctionRegistry semantic meaning
→ operands minimally represented

DEPENDENCY
→ same functional meaning inline
```

Пример:

```text
отрицание факта "Иван находится в Москве"
```

### `k`

```text
ACTIVE
→ k identity / own Pr
→ immediate ordered members
→ every member minimally represented
→ no recursive full traversal

DEPENDENCY
→ minimal meaning of the grouped whole
```

## 17.6. Что скрыто от LLM

Обычный AgentContext не содержит:

```text
x
w
t
tick number
decay age
activation path
lifecycle state
GC state
search depth
visited set
rule IDs
search budget
UID proof trace
Mt
R_text
```

Структурные UID **не входят в model-visible AgentContext**. Они остаются только в operator/debug канале для адресуемости и трассировки. Agent LLM получает семантическое представление памяти, а не сериализацию внутреннего AH-графа.

## 17.7. Операторская прозрачность входа Agent LLM

**[P]** GUI обязан различать model-visible context и диагностический trace. Для каждого
живого Agent-вызова оператору доступны три представления:

```text
Agent CONTEXT
→ точный AgentContext.rendered
→ CURRENT INPUT + ACTIVE MEMORY + INFERENCE RESULTS
→ это model-visible user-message до chat-template

Memory INPUT
→ точный model-visible ACTIVE MEMORY / INFERENCE payload
→ отдельно debug-only объяснение каждого ACTIVE root
   (root UID, x, t, output, decay age, lifecycle, projection tick)

Agent FINAL prompt
→ результат chat-template: system + AgentContext + generation marker
```

Debug-only поля `x/t/tick/lifecycle/UID trace` не добавляются в `AgentContext.rendered` и
не передаются Agent LLM. Они существуют только в операторском канале и объясняют,
почему конкретный root попал в model-visible memory (`x > t`).

Для медленной локальной модели логический `AgentContext` и memory payload должны быть
видимы уже во время выполняющегося Agent request; для этого backend может хранить
runtime-only snapshot текущего in-flight request. Он не является conversation history,
не сохраняется в AH/H и очищается после завершения запроса.

## 17.8. Производительность диагностического GUI

**[P]** Операторские панели не входят в когнитивный runtime и не имеют права
определять его частоту. Canvas может обновляться с высокой визуальной частотой, но
текстовые/табличные diagnostics по умолчанию синхронизируются не чаще wall-clock
cognitive cadence (MVP: около 1 Hz) и обновляются event-driven при завершении turn.

Тяжёлые операции выполняются лениво:

```text
hidden dock / inactive diagnostic tab
→ no semantic reprojection
→ no full QTextDocument rewrite
→ no full table rebuild

visible diagnostics
→ reuse latest immutable graph snapshot when possible
→ cache stable human-readable semantic projection
→ update only changed runtime cells/text
```

Кэширование GUI является presentation-only. Оно не кэширует решения reasoner-а, не
изменяет `x/w`, Workspace, AH, AgentContext или порядок cognitive ticks. При повторном
открытии панели допустим принудительный refresh её диагностического представления.

## 17.9. Model-visible semantic compression

**[P]** Workspace и AgentContext имеют разные форматы. Workspace остаётся точным
когнитивным множеством `x > t` и может содержать `S/T/N/M/G/K`. Перед Agent LLM
выполняется **детерминированная semantic compression**, которая не меняет Workspace:

```text
Workspace roots
→ semantic closure / source utterance recovery
→ remove implementation-only scaffolding
→ deduplicate repeated meaning
→ human-readable ACTIVE MEMORY
```

Model-visible правила:

```text
S / T / L
→ не сериализуются отдельными строками;
→ они продолжают участвовать в Ignition/retrieval.

N / g / meaningful k
→ proposition-level memory;
→ при наличии H source-event допустима точная исходная формулировка пользователя;
→ иначе deterministic human-readable rendering.

M
→ SELF/USER отдельно не печатаются;
→ actants уже представленного N не дублируются;
→ standalone active entity может быть показана человекочитаемо.

current H USER event и semantic content, введённый этой же текущей репликой
→ не дублируются в ACTIVE MEMORY, потому что уже присутствуют в CURRENT INPUT.

old H event
→ может быть показан как явно прошлая реплика, если сам H root активен.
```

Semantic compression не является selector/reranker/top-k: она не решает, какие знания
активны. Она только устраняет внутренние `S/T/UID/role-dump` детали и повторное
представление одного и того же смысла. Точный исходный Workspace сохраняется отдельно в
`AgentContextDiagnostic`.

# 18. `AgentContext`

## 18.1. Состав

```text
AgentContext =
    current Input
    + ModelSemanticProjection(Workspace roots)
    + Semantic Inference Results
```

`P` и `H` не добавляются отдельным скрытым selector-ом. Они попадают в контекст, если их элементы активированы или вошли в semantic result reasoner-а.

## 18.2. Порядок смысловой важности в serialization

```text
1. semantic proposition / relevant entity meaning;
2. distinction between current input and remembered context;
3. deterministic natural-language phrasing;
4. structural detail only when it is itself semantically necessary.
```

UID, `S/T` scaffolding и raw role-dump являются operator/debug representation, а не
Agent input. Естественная фраза допустима, если она детерминированно получена из AH или
из точного H source-event и не добавляет нового содержания.

# 19. Symbolic Inference

## 19.1. Граница LLM / reasoner

LLM:

```text
parses query;
maps language to predicate/roles;
helps propose new T through validation;
verbalizes final answer.
```

Reasoner:

```text
performs proof/search deterministically.
```

## 19.2. Runtime state

```text
InferenceState
├── goal
├── bindings
├── premises
├── current proposition
├── rule
├── depth / budget
└── UID trace
```

`InferenceState ∉ AH`.

Промежуточные search states не сохраняются как знания.

## 19.3. Role matching

```text
predicate
+ known roles
+ requested role
→ matching N
→ bind / extract value
```

Механизм не зависит от конкретного имени предиката и поэтому работает с динамически созданными `T`.

## 19.4. `IS-A`

MVP поддерживает транзитивность:

```text
A IS-A B
B IS-A C
────────
A IS-A C
```

Произвольное graph neighborhood не превращается в автоматическое наследование любых фактов.

## 19.5. `FOLLOW`

```text
N1 FOLLOW N2
N2 FOLLOW N3
────────────
N1 precedes N3
```

`FOLLOW != CAUSE`.

## 19.6. `CAUSE`

Минимальный MP-подобный вывод:

```text
A
A CAUSE B
─────────
B
```

При явно представленной negation semantics:

```text
A CAUSE B
FALSE(B)
─────────
FALSE(A)
```

может использоваться MT-подобный rule.

## 19.7. Rule-driven search

```text
path exists
!=
proposition is derivable
```

Graph traversal только находит кандидатов.

Каждый логический шаг должен быть разрешён конкретным inference rule.

## 19.8. Search priority

Порядок исследования может использовать:

```text
goal relevance;
closeness to requested binding;
current x;
Workspace proximity.
```

Это приоритет поиска, не truth criterion.

## 19.9. Stop conditions

```text
GOAL_SATISFIED
SEARCH_EXHAUSTED
BUDGET_EXHAUSTED
```

Логические исходы:

```text
PROVED
DISPROVED
UNKNOWN
```

`DISPROVED` требует доказанного отрицания; отсутствие факта означает `UNKNOWN`.

Cycles режутся normalized `visited` state.

Для M2:

```text
max_inference_depth >= 6
```

## 19.10. UID Trace

Каждый реально использованный canonical `N/L/g/...` фиксируется в trace.

Trace нужен для:

```text
debug;
tests;
M2;
live demo.
```

Trace:

```text
не пишется в H;
не показывается LLM по умолчанию;
не считается пережитым опытом.
```

# 20. Материализация inference result

## 20.1. Что сохраняется

Search intermediate states не материализуются.

Новый финальный `PROVED` semantic conclusion после proof проходит обычный canonical commit:

```text
Inference Conclusion
      ↓
canonical construction
      ↓
validation
      ↓
domain resolution from premises
      ↓
domain-local dedup
      ↓
AH commit
```

Простой retrieval уже существующего факта не создаёт копию.

## 20.2. Домен вывода

**[P]**

```text
C < P < H
```

Если все посылки из `C`:

```text
Premises ⊆ C
→ conclusion → C
```

Если есть `P`, но нет `H`:

```text
Premises ∩ P ≠ ∅
AND
Premises ∩ H = ∅
→ conclusion → P
```

Если использована хотя бы одна `H`-посылка:

```text
Premises ∩ H ≠ ∅
→ conclusion → H
```

Эквивалентно:

```text
Domain(conclusion)
= max(Domain(premise))

C = 0
P = 1
H = 2
```

Более контекстуальная посылка делает вывод столь же контекстуальным.

## 20.3. После materialization

Semantic conclusion сразу доступен текущему `AgentContext` как inference result.

Commit результата не считается внешним confirmation event и не должен искусственно увеличивать `h_N` как повторное наблюдение.

# 21. Формирование ответа и запись собственного опыта

## 21.1. Генерация

```text
current Input
+ Workspace Projection
+ Inference Results
→ LLM Agent
→ Response / Action
```

LLM не получает debug trace и internal activation mechanics.

### Runtime diagnostic: final Agent prompt

GUI может показывать read-only диагностическую копию **точного request-local текста после
checkpoint chat-template**, который был передан Agent-роли модели, а также число входных
tokens. Это не AgentContext selector, не дополнительная память и не часть H:

```text
AgentContext + agent system prompt
→ checkpoint chat template
→ exact rendered Agent input   # diagnostics only
→ tokenizer / model
```

Диагностическая копия никогда не участвует в следующем turn, не сохраняется как знание и
не даёт модели скрытой conversation history.

## 21.2. Собственный ответ записывается в `H`

**[P]**

Минимальный обязательный путь MVP не требует второго дорогого LLM Perception-вызова:

```text
Agent Response
→ canonical H event_instance N
→ Pr.text = exact utterance
→ FOLLOW / episode linkage
```

Это уже является каноническим пережитым событием в `H` и гарантирует, что агент помнит
**что именно он произнёс**, даже когда локальная модель отвечает медленно. Опциональный
`parse_agent_response_to_h=true` дополнительно прогоняет собственную реплику через те же
perception/canonicalization primitives и добавляет её семантическое содержание в H-only
структуры. Этот deep-semantic self-parse никогда не пишет C/P и не создаёт external
confirmation/`RESOLVED_SYMBOL` seeds.

Таким образом для MVP:

```text
H utterance event = mandatory
second semantic self-parse = optional, default OFF for latency
```

## 21.3. Собственный ответ не возвращается в `C/P`

Запрещён когнитивный feedback loop:

```text
Agent Response
→ ordinary external perception
→ C/P
→ confirmation
→ strengthening
```

Разрешено:

```text
Agent Response
→ H only
```

Даже если ответ содержит галлюцинацию, память фиксирует пережитый факт собственного высказывания, но не превращает его в новое независимое свидетельство о мире.

## 21.4. Реплика пользователя

Внешний пользовательский turn имеет две функции:

```text
User message
→ H as experienced interaction

User message semantic content
→ C for intersubjective facts
→ P for personalized facts
```

То есть источник не задаёт semantic domain содержания; `H` фиксирует сам пережитый акт взаимодействия.

Индексы — производные структуры для скорости; они не являются вторым источником истины.

Минимально:

```text

```

Правило:

```text
canonical records → indexes

```

Любой index должен быть перестраиваемым из AH.

# 26. Persistence

Persistence — поддерживающий слой над `AH Core`, а не отдельная семантическая модель.

Обязательно сохраняются канонические структуры и параметры памяти, без которых нельзя восстановить её состояние:

```text
S
C
P
H
L
UIDs
Pr / Mt
w
```

`x`, decay/lifecycle state и точная snapshot policy относятся к runtime persistence и должны быть окончательно привязаны к конфигу движка перед реализацией сохранения.

Не являются семантической памятью:

```text
PerceptionResult
temporary candidate alternatives
InferenceState
UID debug trace
serialized AgentContext
scratch buffers of current tick
```

Indexes являются производными и должны быть перестраиваемыми из canonical state.

Конкретный backend persistence архитектурой не фиксируется.

# 27. Hierarchy, Heterarchy, Episode

## 27.1. Hierarchy

```text
Hierarchy
= DAG over one homogeneous structural relation,
  e.g. IS-A
```

`k` может рефицировать выбранную hierarchy как один meta-object.

## 27.2. Heterarchy

```text
Heterarchy
= connected semantic subgraph
  with heterogeneous relation types
```

`k` задаёт границу и состав выбранного подграфа, не заменяя отношения внутри.

## 27.3. Episode

```text
Episode in H
= H facts/events
  connected by FOLLOW DAG
```

Один `N` может участвовать в нескольких `k`/структурах.

Workspace не считается H-episode: это runtime focus, а не пережитая история.

# 28. Пример `g`: альтернативные факты

Фраза:

```text
"Яблоки бывают зелёными или красными"
```

MVP-представление:

```text
g_OR
├── N_GREEN
└── N_RED

N_GREEN
├── T_COLOR
├── SUBJECT -> m_APPLE
└── STATE   -> m_GREEN

N_RED
├── T_COLOR
├── SUBJECT -> m_APPLE
└── STATE   -> m_RED
```

`OR` соединяет два законченных `N`, а не два raw property values.

Полная кванторная семантика generic statements в MVP не реализуется.

# 29. Пример domain materialization

Исходно:

```text

```

Вывод:

```text
DOG IS-A ANIMAL
```

Посылки только `C`:

```text
→ materialize in C
```


вывод:

```text

```

использовал `P`, но не `H`:

```text

```

```text
→ materialize in H
```

## 30.1. Function policy registry

**[P]** `f`, `g`, `h_L` и `h_N` выбираются из детерминированного программного registry по `kind/function_id`; TOML передаёт только идентификатор и численные параметры. Произвольный `eval` математического текста из конфига не используется. Это сохраняет воспроизводимость, валидацию и возможность hot-reconfigure между ticks.

MVP registry:

```text
f / ignition.activation.kind:
  additive_clamp
    x_raw = x + gain * z

  saturating_additive
    x_raw = x + gain * z * (1 - x/x_max)

g / ignition.decay.kind:
  sigmoid_epoch
    нормированная sigmoid epoch-кривая;
    D(0)=1, lim D=alpha

  exponential_epoch
    D(age) = alpha + (1-alpha) * 2^(-age/half_life_ticks)

h_L / ignition.plasticity.link_kind:
  additive_hebb

h_N / ignition.plasticity.hypernode_kind:
  additive_confirmation_refutation
```

Общий clamp `0 <= x <= x_max`, synchronous tick ordering, определение activation event, pacemaker provenance и simultaneous commit остаются обязанностью `IgnitionEngine`, а не конкретной policy. Смена policy через hot config не сбрасывает canonical AH или текущее `x`; новая функция начинает действовать между ticks.

Для live-настройки MVP GUI предоставляет два operator-facing hot sliders без cognitive reset:

```text
Floating floor   → ignition.decay.alpha
Upper fall speed → ignition.decay.midpoint_ticks
                   (ползунок отображается как speed: вправо = меньше midpoint = быстрее)
```

Изменение sliders применяется к `DecayPolicy` между ticks и не создаёт activation event. Повышение `alpha` через конфиг само по себе не имеет права увеличить текущий `x`; новый повышенный floor полностью вступает в силу после следующей легитимной epoch boundary.

Новые function IDs добавляются только вместе с:

```text

2. config validation;
3. documented parameters;
4. regression tests;
5. сохранением инвариантов §13–15.
```

```text
agent/orchestrator
  → coordinates modules
  → never mutates AH directly
```

Эта декомпозиция должна позволить тестировать каждый блок отдельно, не подменяя когнитивную механику LLM-магией.
