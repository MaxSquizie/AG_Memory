# Архитектура MVP агента на АГ-памяти

**Статус:** единая рабочая спецификация v0.4  
**Целевой уровень:** Senior / «Воспламенение»  
**Область:** текстовый LLM-агент  
**Назначение:** руководство к реализации: какие данные существуют, какой модуль ими владеет, в каком порядке идёт обработка и где проходят границы ответственности.

## Обозначения

- **[M]** — следует из формализма АГ-памяти Р. В. Душкина.
- **[H]** — требуется постановкой хакатона.
- **[P]** — принятое проектное решение.
- **[D]** — прямое уточнение механики Р. В. Душкиным, переданное в ходе проектирования.
- **[DEFER]** — сознательно не входит в MVP.

Секция «Рекомендуемая структура кода» — инженерная декомпозиция, выведенная из принятых архитектурных границ; она не добавляет новых семантических типов АГ-памяти.

Главное правило документа: ниже описана одна актуальная архитектура. Старые варианты решений и уже отвергнутые ветки не сохраняются.

---

# 1. Архитектура верхнего уровня

## 1.1. Что строим

**[P]** АГ-память — долговременная структурированная когнитивная память LLM-агента. Она должна одновременно поддерживать:

```text
1. запись нового текстового опыта;
2. каноническое представление знаний;
3. ассоциативное распространение возбуждения;
4. формирование текущего фокуса внимания;
5. символический вывод;
6. передачу активной семантики в LLM;
7. запись собственной пережитой истории агента.
```

QA — один из режимов использования памяти, а не её основное назначение.

## 1.2. Полный поток

```text
External Text
      ↓
Text Sensory / S Recognition
      ↓
LLM Perception
      ↓
PerceptionResult
      ↓
Deterministic Integration
      ↓
AH = <S,C,P,H,L>
      ↓
Activation Seed / Reactivation
      ↓
Ignition Engine
      ↓
Workspace
      ↓
Recall + Symbolic Inference
      ↓
Deterministic Context Projection
      ↓
AgentContext
      ↓
LLM Agent
      ↓
Response / Decision / Action
      ↓
H-only Experience Integration
      ↓
AH updated with experienced response
```

Параллельно вход пользователя всегда фиксируется как пережитый опыт в `H`, а его семантическое содержание может дополнительно попасть в `C` и `P`.

## 1.3. Постоянное состояние

```text
State_t = <AH_t, Context_t>
```

`AH_t` — состояние памяти.

`Context_t` — runtime-контекст текущего взаимодействия: текущий turn, дейктические якоря, собеседники, время, conversation/episode context и собранный для LLM контекст.

**[P]** Канонические знания живут в `AH`. Runtime-объекты используются для вычисления и не заменяют память.

## 1.4. Recall и Inference — разные механизмы

```text
Recall != Inference
```

Recall отвечает:

> Что стало релевантным из-за текущего возбуждения памяти?

Inference отвечает:

> Что логически следует из формализованных фактов и отношений?

Поэтому:

```text
Ignition + Workspace
→ ассоциативный контекст

Symbolic Inference
→ логические выводы
```

Активация влияет на релевантность и порядок поиска, но не делает утверждение истинным.

# 2. Модульная схема

Код должен быть разделён по ответственности.

```text
┌──────────────────────────────┐
│ Interaction / Orchestrator   │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ Text Sensory + S Recognition │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ LLM Perception               │
│ candidate extraction only    │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ Deterministic Integration    │
│ validation / resolution      │
│ canonical construction       │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ AH Core / Store              │
│ <S,C,P,H,L>                  │
│ canonical operations         │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ Ignition Engine              │
│ x / f / g / h / t / ν        │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ Workspace                    │
│ refs with x > t              │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ Symbolic Inference           │
│ role / IS-A / FOLLOW / CAUSE │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ Context Projector            │
│ deterministic serialization  │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ LLM Agent                    │
└──────────────┬───────────────┘
               ↓
┌──────────────────────────────┐
│ H Experience Integration     │
└──────────────────────────────┘
```

Поддерживающие компоненты:

```text
FunctionRegistry
Entity / Symbol / Template indexes
Persistence
Lifecycle / GC
DSL
Diagnostics / UID Trace
Evaluation
RAG baseline
```

Ни один внешний модуль не пишет канонические структуры в обход `AH Core`.

# 3. Каноническая модель данных

## 3.1. `AH`

**[M]**

```text
AH = <S, C, P, H, L>
```

Для краткости:

```text
E = C ∪ P ∪ H
```

`E` — обозначение, а не отдельный раздел памяти.

## 3.2. `S` — абстрактные символы первого порядка

**[M]**

```text
s = <UID, R>
```

Для текстового агента:

```text
R = R_text
```

**[P]** Один `s` соответствует устойчивой лексической единице / парадигме. `R_text` содержит формы, по которым она распознаётся.

```text
known wordform
→ reuse existing s

new wordform of known lexeme
→ extend R_text

new lexical unit
→ create new s
```

Пример:

```text
s_APPLE
└── R_text
    ├── яблоко
    ├── яблока
    ├── яблоку
    └── ...
```

Критическое различие:

```text
s_APPLE != m_APPLE
```

`s` — языковой символ.  
`m` — семантическое понятие или сущность.

Отдельные `lemma` / `canonical_form` в каноническую структуру не вводятся: самим каноническим языковым символом является `s`; словоформы нужны для распознавания, а LLM выбирает форму при генерации.

## 3.3. Элемент `C/P/H`

**[M]**

```text
e = <q, x, f>

q ∈ {
    s*,
    m,
    m*,
    g,
    k,
    T,
    N
}
```

где:

```text
x — текущий уровень возбуждения;
f — функция активации элемента.
```

## 3.4. `m` — самостоятельно адресуемая семантическая сущность

**[M]**

```text
m = <UID, Pr, Mt>
```

**[P]** `m` создаётся, когда содержание обладает собственной устойчивой идентичностью и должно независимо участвовать в:

```text
активации;
ассоциациях;
отношениях;
ролях актантов;
рассуждении.
```

Примеры:

```text
m_IVAN
m_APPLE
m_RED
m_MOSCOW
m_PERSON
m_SELF
m_USER_01
```

Класс и экземпляр — оба `m`:

```text
m_IVAN --IS-A--> m_PERSON
```

UID — каноническая машинная идентичность.

Имя не является identity key.

```text
IdentityProfile(m)
≈ properties + relations + facts + history + current context
```

`IdentityProfile` — принцип resolution, а не новый канонический тип.

## 3.5. `Pr` и `Mt`

**[M]** Поля `Pr/Mt` структурно есть только у:

```text
m
k
N
```

У `s`, `T`, `g`, `L` этих полей нет.

Свойство:

```text
p = <name, value, type, unit>
```

`Pr` — свойства без обязательной специальной семантики для кода.

`Mt` — мета-свойства, которые интерпретируются программно.

Пример:

```text
m_IVAN.Pr:
  name = Иван
  age = 32
  eye_color = карий
```

Правило выбора:

```text
локальная характеристика владельца
→ Pr

самостоятельное содержание,
которому нужна собственная активация /
ассоциация / relation / reasoning
→ отдельная AH-структура

машинный служебный атрибут
→ Mt
```

Не нужно прятать самостоятельный факт в property:

```text
Pr.moved_to = "Париж"     # плохо, если это отдельное событие
```

вместо:

```text
N_MOVE(...)
```

## 3.6. `T` — шаблон модели управления предикатного символа

**[M]**

```text
T = <UID, s*, A>
Q = |A|
```

`s*` указывает на языковой предикат.

`A` задаёт роли актантов.

Канонический классификатор:

```text
SUBJECT
OBJECT
AUXILLIARY
RECIPIENT
SOURCE
ABSENTEE
LOCATION
STATE
TIME
DURATION
CAUSE
PURPOSE
TOOL
MATERIAL
AMOUNT
HOW-TO
```

Не все роли конкретного `N` обязаны быть заполнены.

### Динамическое создание `T`

**[P]** Набор шаблонов не закрыт.

```text
unknown predicate
      ↓
LLM TemplateCandidate
      ↓
deterministic validation
      ↓
resolve/create predicate s
      ↓
create canonical T
      ↓
register T in index
      ↓
resume original assertion integration
```

LLM предлагает предикат и роли, но:

```text
не назначает canonical UID;
не пишет T напрямую в AH;
не создаёт inference rule автоматически.
```

Новый `T` означает только, что агент теперь умеет представлять новый тип предикатной ситуации.

## 3.7. `N` — гиперсвязь / конкретный факт

**[M]**

```text
N =
<UID,
 w,
 T*,
 {s_i* | e_i*}[1..Q],
 Pr,
 Mt>
```

Один `N` — одна конкретная реализация одного `T`.

```text
one N = one predicate realization
one sentence may produce multiple N
N may be actant of another N
```

Пример:

```text
N_READ
├── T* -> T_READ
├── SUBJECT -> m_IVAN
└── OBJECT  -> m_BOOK
```

Вложенный факт:

```text
N_MOVE
├── SUBJECT  -> m_MASHA
└── LOCATION -> m_PARIS

N_SAY
├── SUBJECT -> m_IVAN
└── OBJECT  -> N_MOVE
```

Роли задаёт `T`; `N` хранит заполнение этих позиций.

`N.w` — вес гиперсвязи в активационной динамике. Это не truth/confidence.

## 3.8. `L` — типизированная направленная связь

**[M]**

```text
L = <UID, ID, w, (e1*, e2*)>
```

Направление:

```text
e1 --ID,w--> e2
```

Ключевые `ID` MVP:

```text
IS-A
FOLLOW
CAUSE
```

Разделение ответственности:

```text
N → предикатный факт
L → структурное типизированное отношение
g → функциональная композиция
k → идентифицированная группировка
```

Новый естественно-языковой глагол создаёт/использует `T/N`, а не новый `L.ID`.

## 3.9. `g` — функциональная конструкция

**[M]**

```text
g = <UID, ID, {e_i*}>
```

MVP использует в том числе:

```text
AND(...)
OR(...)
FALSE(...)
```

`g.ID` имеет машинную семантику. Поэтому код содержит детерминированный:

```text
FunctionRegistry
```

Для каждого `g.ID` registry определяет:

```text
functional semantics;
operand schema;
engine / reasoner handler;
canonical semantic projection for LLM.
```

Пример:

```text
AH:
g_FALSE_17
  ID = FALSE
  operands = [N8]

Projection:
"отрицание факта: Иван находится в Москве"
```

LLM не должна самостоятельно угадывать семантику opaque enum.

Новый `g.ID` добавляется только вместе с программным handler и projection.

## 3.10. `k` — идентифицированная группировка / мета-объект

**[M]**

```text
k = <UID, ordered_members, Pr, Mt>
```

`k` превращает выбранный набор / подграф в отдельный адресуемый объект.

Он нужен для:

```text
hierarchy;
heterarchy;
episode;
object model;
ambiguity set;
turn/dialogue content grouping.
```

`k`:

```text
не создаёт отношения между членами;
не заменяет N;
не заменяет L;
не выполняет логическую функцию.
```

Его задача — дать целому:

```text
UID;
границу состава;
порядок непосредственных членов;
Pr/Mt;
возможность быть actant/member другого объекта.
```

## 3.11. Неоднозначная ссылка через `k`

**[P]**

Если deterministic resolution оставляет несколько равноправных кандидатов:

```text
k_AMBIGUOUS
├── m_1
├── m_2
└── ...

Mt.TYPE = AMBIGUOUS_REFERENCE
```

Семантика:

```text
Ref(k) = m_1 OR m_2 OR ... OR m_n
```

а не утверждение о всех кандидатах сразу.

После уточнения ссылка в факте заменяется на конкретный `m`.

# 4. Семантические области `C / P / H`

## 4.1. Определения

**[P]**

```text
C — интерсубъективная модель мира.

P — персонализированная модель агента
    и конкретных известных ему объектов.

H — пережитая история агента.
```

Это не уровни достоверности.

## 4.2. Одинаковая внутренняя природа

`C`, `P`, `H` используют один и тот же набор AH-типов:

```text
s*
m
m*
g
k
T
N
```

`H` не является логом движка. Тики, stack trace, UID trace, вызовы функций и telemetry туда не пишутся.

## 4.3. Семантика может дублироваться между доменами

Один смысл допустимо представить отдельными каноническими элементами в нескольких доменах.

```text
C:
  N_C = "Иван — человек"

P:
  N_P = "Иван — человек"

H:
  N_H = "Иван — человек"
```

Эти элементы имеют разные UID.

Следствие:

```text
deduplication scope = one target domain
```

Эквивалентный `N` в другом домене не блокирует создание локального `N`.

Глубокое копирование всех актантов не требуется: H/P/C-элементы могут ссылаться на уже существующие семантические сущности из других доменов, если identity должна быть общей.

## 4.4. Домен определяется смыслом

```text
"Яблоки бывают красными"
→ C

"Мне нравятся красные яблоки"
→ P
```

Источник сообщения не определяет домен содержательного факта.

## 4.5. Каждая коммуникация дополнительно является `H`

Пользовательское сообщение создаёт два слоя:

```text
User message
      ↓
┌──────────────────────┬──────────────────────┐
↓                      ↓
пережитый turn → H     semantic facts
                       ├── C
                       └── P
```

Собственный ответ агента:

```text
Agent response
→ H
→ no automatic C/P integration
```

Это фундаментальная защита от self-reinforcement:

```text
generation != learning
utterance != confirmation
```

# 5. Диалог как пережитый опыт в `H`

## 5.1. Никакого отдельного типа «dialogue memory»

**[P]** Реплики пользователя и агента записываются в `H` теми же каноническими типами `m/g/k/T/N`, что используются в `C` и `P`.

То есть код не должен вводить специальный log-record, который существует вне АГ-формализма.

```text
user turn
→ semantic structures in H

agent turn
→ semantic structures in H
```

Факт коммуникации сам является пережитым опытом, а семантика реплики может быть представлена обычными `N/g/k` внутри `H`.

## 5.2. `FOLLOW` задаёт историю взаимодействия

Последовательные пережитые события связываются:

```text
H_EVENT_1
   |
 FOLLOW
   ↓
H_EVENT_2
   |
 FOLLOW
   ↓
H_EVENT_3
```

Связный эпизод при необходимости группируется нормативным `k`.

`H` хранит семантическую историю, а не execution log.

## 5.3. Повтор содержания и повтор события — разные вещи

Одинаковое утверждение может повторно встречаться в разных turns.

Domain-local dedup применяется к семантически эквивалентным фактам, но конкретные события общения остаются различимыми за счёт их episodic context / TIME / FOLLOW-структуры.

Так агент может помнить:

```text
пользователь сообщил X
позже пользователь снова сообщил X
```

не создавая при этом лишних копий одного и того же содержательного факта внутри того же domain.

# 6. Text Sensory и `S` Recognition

Внешний текст сначала является сенсорным входом, а не знанием.

```text
InputText != CanonicalAH
Perception != Belief
```

Порядок:

```text
raw text
  ↓
token / lexical form recognition
  ↓
lookup R_text
  ↓
known form     → existing s
new wordform   → extend existing s.R_text
new lexeme     → create s
  ↓
external stimulation of recognized s
```

Распознанные `s` получают сенсорное возбуждение.

Дальше тот же текст передаётся Perception Layer для семантического разбора.

# 7. LLM Perception Layer

## 7.1. Trust boundary

**[H][P]**

LLM отвечает за интерпретацию естественного языка, но не владеет канонической памятью.

```text
Text
 ↓
LLM Perception
 ↓
PerceptionResult
 ↓
Deterministic Integration
```

LLM не имеет права:

```text
назначать canonical UID;
выбирать entity по произвольному UID;
писать C/P/H/L напрямую;
удалять/merge-ить canonical entities;
самостоятельно регистрировать T;
использовать w как confidence;
подменять deterministic reasoner скрытым proof.
```

## 7.2. `PerceptionResult`

Runtime-only:

```text
PerceptionResult
├── source.text
├── acts[]
│   ├── AssertionCandidate
│   ├── QueryCandidate
│   └── CommandCandidate
└── diagnostics
```

Один turn может содержать несколько acts.

## 7.3. `AssertionCandidate`

```text
AssertionCandidate
├── local_id
├── predicate
├── actants[]
├── evidence
└── alternatives[]
```

Predicate:

```text
predicate
├── surface
├── normalized_hint
├── sense_hint?
└── evidence
```

Actant:

```text
actant
├── role
├── mention?
├── normalized_hint?
├── semantic_hint?
├── candidate_ref?
├── evidence
└── parser_confidence?
```

`semantic_hint` — подсказка parser-а, не AH-тип.

`parser_confidence` — уверенность разбора:

```text
parser_confidence != truth
parser_confidence != w
```

`evidence` по возможности содержит span исходного текста.

## 7.4. Вложенные кандидаты

До появления canonical UID используются локальные ссылки:

```text
FC_1 = MOVE(...)
FC_2 = SAY(OBJECT -> candidate_ref(FC_1))
```

После интеграции:

```text
N_SAY.OBJECT -> N_MOVE
```

## 7.5. Runtime alternatives

Несколько синтаксических вариантов от LLM:

```text
Candidate A
Candidate B
```

не являются `k`.

`k_AMBIGUOUS` создаётся только после deterministic resolution, если неоднозначность сохранилась между каноническими семантическими кандидатами.

## 7.6. `QueryCandidate`

```text
QueryCandidate
├── predicate
├── actants[]
├── requested_role?
└── query_mode
```

MVP:

```text
query_mode ∈ {FILL_ROLE, EXISTS}
```

После resolution запрос превращается в direct lookup или `InferenceGoal`.

## 7.7. `CommandCandidate`

Parser только распознаёт команду:

```text
COMMAND
 ↓
semantic resolution
 ↓
behavioral decision
 ↓
execution
```

# 8. Deterministic Integration

## 8.1. Назначение

Этот слой превращает неканонические LLM-candidates в точные структуры AH.

```text
PerceptionResult
      ↓
Candidate Validation
      ↓
Predicate / T Resolution
      ↓
Actant Resolution
      ↓
Entity Resolution
      ↓
Context / Deictic Resolution
      ↓
Ambiguity Handling
      ↓
Canonical Construction
      ↓
Domain Resolution
      ↓
Domain-local Deduplication
      ↓
Full Validation
      ↓
Atomic AH Mutation
      ↓
Activation Seed / Reactivation
```

Ни один полусозданный факт не должен остаться в памяти.

## 8.2. Predicate / Template Resolution

```text
PredicateCandidate
→ existing T
| validated creation of new T
```

`T` разрешается до финального mapping актантов, потому что именно `T` задаёт роли.

После resolution:

```text
FilledRoles(candidate) ⊆ Roles(T)
```

## 8.3. Entity Resolution

```text
ER(mention, Context, AH)
→ existing m
| ambiguity
| new m
```

Признаки:

```text
name / aliases
Pr
relations
facts
past H episodes
current activation
current Context
```

LLM поставляет semantic cues; deterministic resolver принимает каноническое решение.

Если подходящего объекта нет — создаётся новый `m`.

Если кандидатов несколько и выбрать нельзя — создаётся `k_AMBIGUOUS`.

## 8.4. Дейксис

```text
"я"      → SELF
"она"    → contextual entity resolution
"вчера"  → concrete TIME from Context
"там"    → active LOCATION from Context
```

Формально:

```text
Resolve(s, Context) -> q
```

Контекстные слова не получают постоянный плавающий `m`, если сами не стали предметом метаязыкового рассуждения.

## 8.5. Создание нового факта

```text
1. resolve predicate;
2. resolve/create predicate s;
3. resolve/create T;
4. resolve actants;
5. resolve/create semantic entities;
6. resolve C/P/H domain;
7. construct N;
8. construct required L/g/k;
9. validate complete semantic subgraph;
10. deduplicate in target domain;
11. atomic commit;
12. semantic seed / reactivation.
```

Actant relations уже содержатся в `N/T`; отдельные `L` для каждой пары `N → actant` не создаются.

## 8.6. Обновление `Pr`

После уверенного resolution владельца:

```text
target m/k/N
 ↓
show existing Pr to semantic matcher
 ↓
match existing property or propose new property name
 ↓
deterministic validation
 ↓
addProperty / editProperty
```

LLM не получает права произвольного property write.

# 9. Политика записи знаний

## 9.1. Формально валидное утверждение записывается

**[P] MVP**

```text
recognized assertion
+ formal validation passed
→ canonical fact
```

Внешний fact-check не блокирует запись.

Даже:

```text
"У Земли две луны"
```

может стать `N`, если это корректно распознанное утверждение.

Trust/belief не кодируются через `w`.

## 9.2. По умолчанию память растёт

```text
AH_(t+1) = AH_t + Δ
```

Совместимая информация дополняет существующий подграф.

Редактирование существующей identity выполняется только после уверенного resolution.

## 9.3. Временное изменение не равно противоречию

```text
Маша жила в Москве в 2025.
Маша живёт в Париже в 2026.
```

Это две ситуации с разными TIME, а не конфликт.

# 10. Deduplication

## 10.1. Только внутри target domain

```text
Equivalent(N_incoming, N_existing)
AND same_domain
→ Reuse(N_existing)
```

При reuse:

```text
N.Mt.occurrence_count += 1
reactivate N
```

Новый `N` не создаётся.

Если семантически эквивалентный факт есть в другом `C/P/H`, это не считается дубликатом для текущего домена.

## 10.2. `occurrence_count` не является весом

```text
occurrence_count != w
```

Повтор не делает:

```text
w += constant
```

Повтор создаёт confirmation/reactivation event, а изменение веса выполняет `h`.

## 10.3. Собственная реплика агента не подтверждает `C/P`

H-only запись собственного ответа:

```text
не increment-ит occurrence_count C/P-факта;
не считается внешним confirmation;
не запускает C/P self-training.
```

Повтор в самом `H` может учитываться как повтор пережитого содержания, не затрагивая C/P.

# 11. Явное отрицание и коррекция

## 11.1. Semantic supersession

**[P]**

Старый факт не уничтожается при явном опровержении.

```text
N_old
 ↓
FALSE(N_old)
```

Алгоритм:

```text
1. preserve N_old;
2. create/resolve g_FALSE(N_old);
3. FALSE(N_old) becomes current semantic representative;
4. move/rebuild current associative emphasis around FALSE;
5. strongly decrease N_old.w;
6. do not rewrite every old reference blindly;
7. preserve N_old for history and possible reversal.
```

Обычная Hebbian depression не должна выполнять semantic correction.

## 11.2. Неразрешимая неоднозначность

Если нельзя понять, какая версия корректна:

```text
candidate A
candidate B
 ↓
k_AMBIGUOUS
 ↓
clarification
```

MVP не вводит отдельный тяжёлый conflict engine.

# 12. Activation и веса

## 12.1. `x`

`x` — текущий уровень возбуждения excitable AH-элемента.

Внешний текст сначала стимулирует распознанные `s`, а после канонической интеграции semantic seed получает соответствующий `N`.

Новые actants не нужно вручную возбуждать целиком: дальнейшее распространение выполняет сама гиперсеть.

## 12.2. `w`

`w` у `L` и `N` — сила пути передачи возбуждения.

```text
w != truth
w != belief
w != reliability
w != parser confidence
w != occurrence_count
```

Чем больше `w`, тем сильнее данный путь участвует в spreading activation.

# 13. Ignition Engine

## 13.1. Время

Вся внутренняя динамика работает в engine ticks.

```text
engine running
→ ticks advance

engine stopped
→ memory time does not advance
```

В ticks измеряются:

```text
activation propagation;
decay;
Hebbian plasticity;
lifetime;
consolidation spacing;
GC timing.
```

`tick_rate` — частота вычислительного цикла.

`ν` — частота импульсов pacemaker-а, реализуемая поверх того же tick clock.

## 13.2. Synchronous snapshot

**[P]**

Каждый tick считается из одного snapshot.

```text
State_τ
   ↓
calculate all tick effects
   ↓
simultaneous commit
   ↓
State_(τ+1)
```

Следствия:

```text
порядок обхода элементов не влияет на результат;
новый сигнал проходит максимум одно новое ребро за tick;
новый w начинает влиять только со следующего tick;
GC не удаляет элемент посреди вычисления snapshot.
```

## 13.3. Incoming buffer

Для каждого excitable элемента на tick хранится сумма пришедших импульсов.

Ассоциативная связь:

```text
impulse(A→B) = output_A * L.w
```

Гиперсвязь `N` передаёт свой output актантам через `N.w`.

Итог:

```text
z_i = Σ incoming weighted impulses
```

Impulses, рассчитанные на `τ`, записываются во входной buffer соседей для следующего causal tick.

## 13.4. `f(x_t, z)` — активация и output

**[D][P]**

```text
x_raw = f(x_t, z)
x_act = clamp(x_raw)
output_t = x_act
```

Результат `f` одновременно:

```text
становится новым возбуждением самого элемента;
является величиной исходящего импульса до веса связи.
```

Передача импульса не уменьшает `x` источника.

`x_raw` используется для определения силы новой реактивации до насыщения, после чего применяется configurable clamp:

```text
0 <= x_act <= x_max
```

## 13.5. Первый tick нового возбуждения

**[D][P]**

Если элемент только что получил новое возбуждение / начал новый decay epoch:

```text
incoming z
  ↓
f(x,z)
  ↓
x_act
  ├── set current excitation
  └── send output
  ↓
activation/reactivation event
  ↓
NO g on this fresh tick
```

Новое возбуждение не гасится сразу после получения.

## 13.6. Следующие ticks

Для уже возбуждённого элемента:

```text
existing x
+ incoming z
   ↓
f(x,z)
   ↓
x_act / output
   ↓
plasticity event accounting
   ↓
g decay
   ↓
x_next
```

При `z = 0` элемент продолжает передавать остаточное возбуждение согласно `f`, после чего `g` снижает его состояние.

## 13.7. `g` — decay

Decay — отдельная операция, не часть `f`.

Базовая форма epoch:

```text
x(age) = x_start * D(age)
```

Ограничения:

```text
D(0) = 1
0 < D(age) <= 1
D(age) monotonically decreases
lim D(age) = α
0 < α < 1
```

Желаемая форма:

```text
медленный спад
→ более резкая средняя часть
→ медленный хвост
```

Конкретная функция — config.

Новый внешний prompt начинает новый общий decay epoch от текущего состояния:

```text
x_start_i := current x_i
decay_age_i := 0
```

## 13.8. Reactivation и reset локального decay epoch

Для уже затухающего элемента вычисляется ожидаемая потеря без подпитки:

```text
x_decay_expected = g(x_t, decay_state)
Δ_decay = x_t - x_decay_expected
```

После входа:

```text
x_raw = f(x_t, z)
Δ_input = x_raw - x_t
x_act = clamp(x_raw)
```

Сравнение выполняется до clamp, чтобы saturation по `x_max` не скрывало силу входного воздействия.

Правило:

```text
if Δ_input > Δ_decay:
    reset local decay epoch
    x_next = x_act
    decay_age = 0
else:
    continue current decay epoch
    x_next = g(x_act, decay_state)
```

Равенство epoch не сбрасывает.

Слабый input всё равно влияет на `x`; он просто не считается достаточной реактивацией для reset.

Сам факт отправления outgoing impulse не reset-ит decay epoch источника.

## 13.9. Канонический tick algorithm

```text
INPUT:
  snapshot State_τ
  incoming_buffer_τ
  external/pacemaker seeds scheduled for τ

PHASE 1 — collect
  z_i := sum incoming impulses + scheduled seeds

PHASE 2 — activation/output
  x_raw_i := f_i(x_i, z_i)
  Δ_input_i := x_raw_i - x_i
  x_act_i := clamp(x_raw_i)
  output_i := x_act_i
  detect activation/reactivation event a_i

PHASE 3 — propagate
  for every outgoing L:
      next_buffer[target] += output_i * L.w
  for every active N hyperconnection:
      next_buffer[actant] += output_N * N.w

PHASE 4 — plasticity
  calculate pending L.w / N.w updates from events of this tick

PHASE 5 — decay
  fresh/reset activation:
      x_next_i := x_act_i
      decay_age := 0
  otherwise:
      x_next_i := g_i(x_act_i, decay_state)

PHASE 6 — lifecycle / GC decisions
  update N lifecycle from qualifying events
  mark expired / orphan candidates

PHASE 7 — Workspace
  Workspace_(τ+1) := refs with committed x_next > t

PHASE 8 — simultaneous commit
  commit x
  commit w
  commit decay state
  commit lifecycle
  swap incoming buffers
  apply GC deletions
```

# 14. Пластичность `h`

## 14.1. Activation event

```text
a_i(τ) = 1
```

только если на tick произошла новая активация / реактивация.

Остаточное:

```text
x > 0
```

не является новым Hebbian event.

## 14.2. `h_L`

Для существующей связи `A → B`:

```text
a_A(τ)=1
AND
a_B(τ)=1
→ L.w increases
```

С задержкой в один tick:

```text
A activates on τ
B activates only because of A on τ+1
```

положительное Hebbian strengthening автоматически не происходит.

Иначе обычное распространение само бесконечно усиливало бы собственный путь.

Weak depression:

```text
exactly one endpoint has activation event on tick
→ weak L.w decrease
```

Инактивность обоих endpoint сама по себе ничего не ослабляет.

Обычная depression имеет ненулевой configurable floor и не удаляет семантическую связь.

## 14.3. `h_N`

`N.w` меняется по семантическим событиям подтверждения / опровержения.

```text
external repeated assertion
resolves to same N
→ confirmation event
→ N.w increases through h_N

explicit FALSE(N)
→ refutation event
→ strong N.w decrease
```

Собственный ответ агента не создаёт confirmation event для `C/P`.

`occurrence_count++` и `h_N` — разные операции.

# 15. Lifecycle и GC

## 15.1. Consolidation только для `N`

**[P]**

```text
NEW
 ↓ qualifying spaced reactivation #1
REINFORCED
 ↓ qualifying spaced reactivation #2
CONSOLIDATED
```

`m`, `g`, `k`, `L` не имеют отдельного consolidation lifecycle.

Машинные lifecycle-поля хранятся как служебное состояние `N`, например через `Mt`.

## 15.2. Lifetime

```text
NEW:
  expires_tick =
    created_tick + initial_lifetime_ticks

REINFORCED:
  expires_tick =
    reactivation_tick + reinforced_lifetime_ticks

CONSOLIDATED:
  no ordinary TTL expiration
```

## 15.3. Qualifying reactivation

```text
qualifies =
    activation/reactivation event
    AND enough engine ticks since previous qualifying event
```

Быстрый внутренний цикл не должен консолидировать факт за несколько мгновенных проходов.

Позднее самостоятельное associative resurfacing может считаться reactivation, если выдержан spacing.

## 15.4. GC

GC удаляет:

```text
expired NEW N;
expired REINFORCED N;
hackathon-required isolated/lost structures;
true structural orphans after deletion.
```

`CONSOLIDATED` не удаляется обычным TTL.

После удаления `N` связанные `m/g/k/L` удаляются только если на них больше нет живых ссылок.

`FALSE(N_old)` и H-ссылки защищают исторически значимый `N_old` от ошибочного orphan GC.

# 16. Workspace

## 16.1. Определение

**[M][P]**

```text
Workspace_τ =
{ ref(e) | e is excitable and x_e(τ) > t }
```

Workspace содержит refs, а не копии.

```text
AH = source of truth
Workspace = dynamic active view
```

## 16.2. Порог `t`

```text
x > t
→ элемент является самостоятельным активным корнем контекста

x <= t
→ элемент не является самостоятельным корнем
```

Но:

```text
x <= t
```

не означает:

```text
deleted;
unreachable;
blocked for spreading;
blocked for inference.
```

`t` не является propagation gate.

## 16.3. Нет второго cognitive reranker

После `x > t` не вводится дополнительный:

```text
top-k;
LLM relevance selector;
semantic reranker.
```

Иначе фокус внимания определял бы уже не Ignition Engine.

Token budget — инфраструктурное ограничение сериализации, а не новый механизм когнитивной релевантности.

## 16.4. Workspace и reasoner

Workspace — приоритетная область старта поиска.

Reasoner может переходить к неактивным элементам, если это требуется логическим правилом.

Сам факт посещения reasoner-ом не добавляет элемент в Workspace.

# 17. Детерминированная проекция в LLM

## 17.1. Три ответственности

```text
Ignition decides WHAT is active.
Workspace records active refs.
Projector decides HOW to represent their semantics.
```

Projector не решает, что важно.

## 17.2. Режимы `ACTIVE` и `DEPENDENCY`

`ACTIVE`:

```text
root independently selected for AgentContext
→ full own semantics
→ own Pr exposed if type has Pr
→ Mt hidden
```

`DEPENDENCY`:

```text
dereferenced only to understand an ACTIVE root
→ minimal semantic representation
→ Pr not exposed
→ dependency does not become Workspace member
```

Projection mode — режим сериализатора. Поэтому `L`, не имеющий собственного `x`, может быть root-представлением, например когда он является semantic inference result; это не означает, что canonical `L` получил excitation field.

## 17.3. Один full block на root

Каждый active root сериализуется полностью ровно один раз.

Ссылки внутри него не запускают recursive full projection.

Если referenced element сам является active root, его full block выводится отдельно.

## 17.4. MinimalSemanticProjection

```text
MinimalSemanticProjection(e)
→ минимальное представление,
  достаточное LLM для понимания семантики e
```

Внутренний dereference может идти глубже одного уровня, если это нужно для построения смысла, но output:

```text
не раскрывает чужие Pr;
не раскрывает лишний neighborhood;
не меняет Workspace;
не показывает x/w/t/ticks;
не запускает рекурсивный full dump.
```

## 17.5. Проекция по типам

### `s`

```text
ACTIVE / DEPENDENCY
→ semantic lexical symbol

R_text
→ never exposed
```

### `m`

```text
ACTIVE
→ identity / human-readable semantics
→ all own Pr

DEPENDENCY
→ minimal identity semantics only
```

### `T`

```text
ACTIVE
→ predicate semantics
→ actant-role schema

DEPENDENCY
→ only predicate semantics + role mapping
  required to understand containing N
```

### `N`

```text
ACTIVE
→ predicate via T→s
→ role → actant mapping
→ own Pr
→ no w / Mt

DEPENDENCY
→ compact semantic statement
```

Пример:

```text
[N1]
Иван читает книгу
```

### `L`

```text
root result
→ relation ID
→ direction
→ both endpoints minimally represented

dependency
→ same minimal structural meaning
```

Пример:

```text
Собака IS-A Животное
```

### `g`

```text
ACTIVE
→ FunctionRegistry semantic meaning
→ operands minimally represented

DEPENDENCY
→ same functional meaning inline
```

Пример:

```text
отрицание факта "Иван находится в Москве"
```

### `k`

```text
ACTIVE
→ k identity / own Pr
→ immediate ordered members
→ every member minimally represented
→ no recursive full traversal

DEPENDENCY
→ minimal meaning of the grouped whole
```

## 17.6. Что скрыто от LLM

Обычный AgentContext не содержит:

```text
x
w
t
tick number
decay age
activation path
lifecycle state
GC state
search depth
visited set
rule IDs
search budget
UID proof trace
Mt
R_text
```

Структурные UID могут присутствовать для стабильной адресуемости, но debug trace остаётся отдельным каналом.

# 18. `AgentContext`

## 18.1. Состав

```text
AgentContext =
    current Input
    + Projection(Workspace roots)
    + Semantic Inference Results
```

`P` и `H` не добавляются отдельным скрытым selector-ом. Они попадают в контекст, если их элементы активированы или вошли в semantic result reasoner-а.

## 18.2. Порядок смысловой важности в serialization

```text
1. stable identity / refs;
2. predicate-role / relation structure;
3. semantic representation;
4. natural-language phrasing where it improves comprehension.
```

Естественная фраза допустима, если она детерминированно получена из AH и не скрывает структуру.

# 19. Symbolic Inference

## 19.1. Граница LLM / reasoner

LLM:

```text
parses query;
maps language to predicate/roles;
helps propose new T through validation;
verbalizes final answer.
```

Reasoner:

```text
performs proof/search deterministically.
```

## 19.2. Runtime state

```text
InferenceState
├── goal
├── bindings
├── premises
├── current proposition
├── rule
├── depth / budget
└── UID trace
```

`InferenceState ∉ AH`.

Промежуточные search states не сохраняются как знания.

## 19.3. Role matching

```text
predicate
+ known roles
+ requested role
→ matching N
→ bind / extract value
```

Механизм не зависит от конкретного имени предиката и поэтому работает с динамически созданными `T`.

## 19.4. `IS-A`

MVP поддерживает транзитивность:

```text
A IS-A B
B IS-A C
────────
A IS-A C
```

Произвольное graph neighborhood не превращается в автоматическое наследование любых фактов.

## 19.5. `FOLLOW`

```text
N1 FOLLOW N2
N2 FOLLOW N3
────────────
N1 precedes N3
```

`FOLLOW != CAUSE`.

## 19.6. `CAUSE`

Минимальный MP-подобный вывод:

```text
A
A CAUSE B
─────────
B
```

При явно представленной negation semantics:

```text
A CAUSE B
FALSE(B)
─────────
FALSE(A)
```

может использоваться MT-подобный rule.

## 19.7. Rule-driven search

```text
path exists
!=
proposition is derivable
```

Graph traversal только находит кандидатов.

Каждый логический шаг должен быть разрешён конкретным inference rule.

## 19.8. Search priority

Порядок исследования может использовать:

```text
goal relevance;
closeness to requested binding;
current x;
Workspace proximity.
```

Это приоритет поиска, не truth criterion.

## 19.9. Stop conditions

```text
GOAL_SATISFIED
SEARCH_EXHAUSTED
BUDGET_EXHAUSTED
```

Логические исходы:

```text
PROVED
DISPROVED
UNKNOWN
```

`DISPROVED` требует доказанного отрицания; отсутствие факта означает `UNKNOWN`.

Cycles режутся normalized `visited` state.

Для M2:

```text
max_inference_depth >= 6
```

## 19.10. UID Trace

Каждый реально использованный canonical `N/L/g/...` фиксируется в trace.

Trace нужен для:

```text
debug;
tests;
M2;
live demo.
```

Trace:

```text
не пишется в H;
не показывается LLM по умолчанию;
не считается пережитым опытом.
```

# 20. Материализация inference result

## 20.1. Что сохраняется

Search intermediate states не материализуются.

Новый финальный `PROVED` semantic conclusion после proof проходит обычный canonical commit:

```text
Inference Conclusion
      ↓
canonical construction
      ↓
validation
      ↓
domain resolution from premises
      ↓
domain-local dedup
      ↓
AH commit
```

Простой retrieval уже существующего факта не создаёт копию.

## 20.2. Домен вывода

**[P]**

```text
C < P < H
```

Если все посылки из `C`:

```text
Premises ⊆ C
→ conclusion → C
```

Если есть `P`, но нет `H`:

```text
Premises ∩ P ≠ ∅
AND
Premises ∩ H = ∅
→ conclusion → P
```

Если использована хотя бы одна `H`-посылка:

```text
Premises ∩ H ≠ ∅
→ conclusion → H
```

Эквивалентно:

```text
Domain(conclusion)
= max(Domain(premise))

C = 0
P = 1
H = 2
```

Более контекстуальная посылка делает вывод столь же контекстуальным.

## 20.3. После materialization

Semantic conclusion сразу доступен текущему `AgentContext` как inference result.

Commit результата не считается внешним confirmation event и не должен искусственно увеличивать `h_N` как повторное наблюдение.

# 21. Формирование ответа и запись собственного опыта

## 21.1. Генерация

```text
current Input
+ Workspace Projection
+ Inference Results
→ LLM Agent
→ Response / Action
```

LLM не получает debug trace и internal activation mechanics.

## 21.2. Собственный ответ записывается в `H`

**[P]**

```text
Agent Response
→ semantic experience integration
→ H
```

Для реализации можно переиспользовать те же perception/canonicalization primitives, но write-domain этого пути жёстко ограничен `H`.

Цель — сохранить семантику того, что агент действительно сказал или сделал, теми же AH-типами, которыми хранится остальной опыт.

## 21.3. Собственный ответ не возвращается в `C/P`

Запрещён когнитивный feedback loop:

```text
Agent Response
→ ordinary external perception
→ C/P
→ confirmation
→ strengthening
```

Разрешено:

```text
Agent Response
→ H only
```

Даже если ответ содержит галлюцинацию, память фиксирует пережитый факт собственного высказывания, но не превращает его в новое независимое свидетельство о мире.

## 21.4. Реплика пользователя

Внешний пользовательский turn имеет две функции:

```text
User message
→ H as experienced interaction

User message semantic content
→ C for intersubjective facts
→ P for personalized facts
```

То есть источник не задаёт semantic domain содержания; `H` фиксирует сам пережитый акт взаимодействия.

# 24. Runtime contracts между модулями

# 25. Индексы

Индексы — производные структуры для скорости; они не являются вторым источником истины.

Минимально:

```text
UID index
R_text → s index
predicate s → T index
entity name/alias → m candidates
Pr index for findSymbols
N canonical signature index per C/P/H
L outgoing adjacency
L incoming adjacency
N → actants index
actant → N reverse index
k membership index
FOLLOW adjacency
IS-A adjacency
CAUSE adjacency
```

Правило:

```text
canonical records → indexes
not indexes → canonical truth
```

Любой index должен быть перестраиваемым из AH.

# 26. Persistence

Persistence — поддерживающий слой над `AH Core`, а не отдельная семантическая модель.

Обязательно сохраняются канонические структуры и параметры памяти, без которых нельзя восстановить её состояние:

```text
S
C
P
H
L
UIDs
Pr / Mt
w
```

`x`, decay/lifecycle state и точная snapshot policy относятся к runtime persistence и должны быть окончательно привязаны к конфигу движка перед реализацией сохранения.

Не являются семантической памятью:

```text
PerceptionResult
temporary candidate alternatives
InferenceState
UID debug trace
serialized AgentContext
scratch buffers of current tick
```

Indexes являются производными и должны быть перестраиваемыми из canonical state.

Конкретный backend persistence архитектурой не фиксируется.

# 27. Hierarchy, Heterarchy, Episode

## 27.1. Hierarchy

```text
Hierarchy
= DAG over one homogeneous structural relation,
  e.g. IS-A
```

`k` может рефицировать выбранную hierarchy как один meta-object.

## 27.2. Heterarchy

```text
Heterarchy
= connected semantic subgraph
  with heterogeneous relation types
```

`k` задаёт границу и состав выбранного подграфа, не заменяя отношения внутри.

## 27.3. Episode

```text
Episode in H
= H facts/events
  connected by FOLLOW DAG
```

Один `N` может участвовать в нескольких `k`/структурах.

Workspace не считается H-episode: это runtime focus, а не пережитая история.

# 28. Пример `g`: альтернативные факты

Фраза:

```text
"Яблоки бывают зелёными или красными"
```

MVP-представление:

```text
g_OR
├── N_GREEN
└── N_RED

N_GREEN
├── T_COLOR
├── SUBJECT -> m_APPLE
└── STATE   -> m_GREEN

N_RED
├── T_COLOR
├── SUBJECT -> m_APPLE
└── STATE   -> m_RED
```

`OR` соединяет два законченных `N`, а не два raw property values.

Полная кванторная семантика generic statements в MVP не реализуется.

# 29. Пример domain materialization

Исходно:

```text
C:
DOG IS-A MAMMAL
MAMMAL IS-A ANIMAL
```

Вывод:

```text
DOG IS-A ANIMAL
```

Посылки только `C`:

```text
→ materialize in C
```

Если:

```text
C:
DOG IS-A ANIMAL

P:
REX IS-A DOG
```

вывод:

```text
REX IS-A ANIMAL
```

использовал `P`, но не `H`:

```text
→ materialize in P
```

Если доказательство использовало факт конкретного пережитого эпизода из `H`:

```text
→ materialize in H
```

```text

   и назначаются deterministic layer.

7. Один текст может породить несколько N.

8. N может быть actant другого N.

11. Семантика с собственной когнитивной жизнью
    не прячется в Pr.

12. C/P/H — semantic domains, а не truth levels.

13. H использует те же AH-типы, что C/P.

14. Same semantics may exist in several C/P/H domains.

15. Dedup is domain-local.

16. Every user turn is experienced in H.

17. User semantic content may additionally update C/P.

18. Every agent response is experienced in H.

19. Agent response never automatically feeds C/P.

20. Generation != learning.

21. Utterance != confirmation.

22. Formally valid assertion may be stored even if false.

23. w is not truth/confidence/reliability/frequency.

24. occurrence_count != w.

26. Duplicate perception does not perform direct w += constant.

27. Explicit refutation preserves N_old via FALSE(N_old).

28. f(x,z) produces both new x and outgoing output.

29. Sending an impulse does not consume x.

30. Fresh excitation tick has no g decay.

31. Tick calculation is synchronous.

33. Weight updates affect propagation from the next tick.

34. x>t defines Workspace membership.

35. t does not gate propagation or inference.

36. Workspace has no second cognitive reranker.

37. ACTIVE root is fully serialized once.

38. Dependencies receive only minimal semantic projection.

39. Active m/k/N exposes own Pr.

40. Mt, x, w, ticks and debug trace are hidden from LLM.

42. h_L+ requires same-tick activation/reactivation of endpoints.

43. Inactivity alone does not depress links.

44. Consolidation lifecycle belongs to N.

45. Inference is rule-driven; graph reachability alone is not proof.

46. LLM is not the proof engine.

47. UID trace is runtime diagnostics, not H.

48. New proved conclusion is materialized by premise provenance:
    C-only → C;
    any P without H → P;
    any H → H.

49. Search intermediate states are never materialized.

50. Quantified generalized logic is outside MVP.
```
