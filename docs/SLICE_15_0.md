# Срез v0.15.0 — канонический конфликт полярности и допустимость посылок

## 1. Назначение

Версия 0.15.0 замыкает в один рабочий контур обнаружение, хранение, восстановление, отображение и учёт при выводе неразрешённого противоречия вида `P` / `NOT(P)`.

Срез реализует нормативный принцип v4: конфликт не является выбором «истинной версии». Он делает взаимоисключающие выражения адресуемыми и запрещает reasoner-у использовать любую из сторон как безусловную посылку, пока конфликт не разрешён формальным способом.

Каноническая модель АГ-памяти не расширяется новым типом узла. Используется существующий `k`:

```text
k_CONFLICT
Mt.TYPE = CONFLICT
members = { P, NOT(P) }
```

`k` только задаёт identity набора. Операционная семантика принадлежит `ConflictEngine`.

## 2. Что считается конфликтом в этом срезе

Автоматически распознаётся только формально определимый полярный конфликт:

```text
asserted P
asserted NOT(P)
→ unresolved conflict
```

Обе стороны должны:

- существовать в одном семантическом домене `C` или `P`;
- быть действительно утверждённым содержанием пользовательского опыта, а не просто вложенной формулой;
- относиться к одной и той же канонической proposition `P`;
- сохранять различие `NOT(P)` и `FALSE(P)`.

Это намеренно консервативная граница. Два положительных утверждения с разными значениями не считаются конфликтом только из-за одинакового предиката. Для такого случая нужна явная `FUNCTIONAL`/взаимоисключающая схема, предусмотренная архитектурой, но не объявляемая реализованной в 0.15.0.

## 3. Момент обнаружения

Конфликт регистрируется после того, как интеграция уже связала содержательную proposition с пользовательским событием в `H`.

Это важно для составных `g`: факт утверждения `NOT(P)` определяется по его реальному occurrence, а не добавлением запрещённых `Pr/Mt` к `g`.

Порядок:

```text
формализация
→ canonical integration P / NOT(P)
→ запись пользовательского occurrence в H
→ ConflictEngine.register_asserted_roots(...)
→ create/reuse k_CONFLICT
→ activation seed конфликтной группы
```

Ответ Main LLM, который записывается только как пережитое событие агента в `H`, не считается внешним подтверждением `C/P` и сам по себе не создаёт такой conflict-set.

## 4. Каноническое хранение

При первом обнаружении создаётся один `Group` с:

```text
TYPE = CONFLICT
conflict_kind = POLARITY
members = (positive, negative)
```

Повтор `P` или `NOT(P)`:

- не создаёт второй conflict-set;
- не меняет победителя, потому что победителя нет;
- не трактует `occurrence_count`, `x` или `w` как достоверность.

Группа сериализуется вместе с обычной AH и после загрузки снова участвует в проверке допустимости. Отдельное хранилище истины не создаётся.

## 5. Разрешённость конфликта

Наличие исторического `k_CONFLICT` и текущая неразрешённость — разные вещи.

`ConflictEngine.is_unresolved_group(...)` вычисляет допустимость членов по текущему состоянию памяти. Поэтому явное:

```text
FALSE(P)
```

делает `P` недопустимой factual premise. После этого пара `P` / `NOT(P)` больше не является одновременно допустимой, хотя сам адресуемый conflict-set может остаться в канонической истории.

Это позволяет не переписывать историю памяти разрушительно и сохраняет различие:

```text
NOT(P)     — отрицательное содержание
FALSE(P)   — мета-опровержение конкретной proposition/support
```

## 6. Поведение вывода

Перед использованием canonical expression как посылки reasoner проверяет её конфликтную допустимость.

Проверка встроена в:

- `FormulaGoal` / наземный и кванторный formula reasoning;
- `RoleFillGoal`;
- `MultiRoleFillGoal`;
- `ExistsGoal`;
- `RelationGoal`;
- `CAUSE`-вывод, включая explicit-premise и legacy direct path.

Если единственный релевантный путь зависит от неразрешённой конфликтной proposition:

```text
status = UNKNOWN
stop_reason = CONFLICTED
```

Если имеется независимый непротиворечивый путь, он может быть доказан нормально. Поэтому конфликт локализуется по зависимостям и не вызывает логического взрыва:

```text
P
NOT(P)
≠> arbitrary Q
```

При proof через цепочку конфликтный промежуточный узел также не принимается как допустимый шаг.

## 7. Активация и наблюдаемость

Созданный conflict-set получает отдельный activation seed `CONFLICT`. Это делает сам факт противоречия доступным текущему Workspace, но не превращает возбуждение в доказательство.

При обращении reasoner-а к конфликтной proposition через `InferenceAttention` фокус может быть перенесён на conflict-set и его членов, сохраняя общий принцип v4: когнитивно значимый шаг проходит через обычный контур внимания/возбуждения.

Проекция отображает конфликт явно:

```text
CONFLICT[...; ...]
```

а человекочитаемый AgentContext — как неразрешённый конфликт между выражениями. Main LLM не требуется самостоятельно обнаруживать противоречие по двум несвязанным строкам.

## 8. Сохранённые инварианты

- `AH = <S,C,P,H,L>` остаётся единственной канонической памятью.
- Новый canonical node kind не введён.
- `k` не стал скрытым логическим оператором.
- `activation != truth`, `w != confidence`.
- Повтор утверждения не разрешает конфликт.
- `UNKNOWN != FALSE`.
- `NOT(P) != FALSE(P)`.
- Конфликт не блокирует независимые доказательства.
- `IS-A`, `FOLLOW`, `CAUSE` сохранены; `CAUSE` не получает автоматическую транзитивность.
- Main LLM не решает конфликт и не пишет canonical AH напрямую.

## 9. Граница готовности

К 0.15.0 завершён полярный конфликт `P` / `NOT(P)` как полный вертикальный срез: интеграция → canonical `k_CONFLICT` → persistence → активация → admissibility всех основных reasoner paths → projection → регрессии.

Не объявлены готовыми в этом срезе:

- положительные конфликты значений по `FUNCTIONAL`-слоту/предикату;
- конфликт, требующий отдельной temporal/context incompatibility schema;
- автоматическое разрешение конфликтов по внешней политике источников.

Последний пункт сознательно не должен превращаться в универсальный truth-engine: v4 запрещает выбирать сторону по числу повторов, новизне, `x` или `w`.
