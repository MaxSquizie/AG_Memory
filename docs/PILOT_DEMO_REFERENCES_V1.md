# Эталоны первого демо-набора (рабочий черновик v1)

Статус: **v1 зафиксирован (frozen)** — pre-fixed референс, зафиксирован до запуска
прототипа. Любое изменение после запуска требует новой версии документа, а не правки
in-place. Спорные трактовки помечены заранее (§4). Контракт формализатора зафиксирован
отдельно; этот документ — только эталоны и схема оценки для шести предложений демо-набора.

Демо-набор:

| ID | Текст | Роль в наборе |
|----|-------|---------------|
| S1 | «У вороны есть лапки.» | базовый случай, старт прототипа |
| S2 | «У стола есть ножки.» | перенос внутри конструкции |
| S3 | «У меня есть книга.» | то же построение, иное значение (обладание) |
| S4 | «Ворона обладает перьями.» | внеконструкционный перенос (другой глагол) |
| S5 | «У вороны лапки.» | эллипсис copula — решающий тест генеральности |
| S6 | «Вороны любят червей.» | отрицательный контроль |

## 1. Модель оценки

Два независимых результата: **корректность механизма** и **покрытие примеров**.

Классы исхода на предложение:

- **C1 — верно формализовано.** Итоговая структура совпадает с целевым чтением или
  допустимой альтернативой (§4), все ограничения соблюдены, и **семантика завершена**:
  значение предиката и связь участников разрешены. Незавершённость представляется
  отдельным открытым решением с альтернативами (например, неразрешённый выбор
  {HAVE, HAS_PART}); такой результат — C2, а не C1. Само по себе HAVE — конкретное
  значение, а не «грубая семантика».
- **C2 — честно неполно или частично.** Любой из: NO_CANDIDATE / INSUFFICIENT_CONTEXT
  с корректным miss-отчётом (исход, версия контекста, отработавшие генераторы,
  кандидаты, причины исключения); верный, но незавершённый результат (полезная
  структура сохранена, семантика не разрешена). Механизм пройден; покрытие — нет.
  **Не засчитывается как успешная формализация.**
- **C3 — провал механизма.** Любой из: принят неверный смысл (даже при соблюдении
  ограничений и access control); нарушение ограничения; чтение необъявленных данных;
  сбой подписки/пересчёта.

Итоговый отчёт содержит две независимые строки:

- **Механизм:** пройден, если нет ни одного C3 (включая семантически неверный принятый
  смысл при соблюдении ограничений).
- **Работоспособность:** S1 обязан быть C1 (базовый случай набора); остальные
  предложения отчитываются числом C1/C2. Шесть честных отказов (все C2) при чистом
  механизме не демонстрируют работоспособную формализацию и засчитываются как провал
  этой строки.

## 2. Типы обоснований (закрытый набор)

Каждое основание в эталоне и в трассе разрешается в один из пяти типов:

1. **R** — запись именованного языкового ресурса: название + версия, ID записи,
   возвращаемые значения. В этом прототипе:
   - **R1** = pymorphy3/OpenCorpora — только морфология (лемма, падеж, часть речи),
     значений слов не содержит;
   - **R2** = семантический лексикон — в этом прототипе **не создаётся** (§7.2).
     Кандидаты значений предикатов формируются Python заранее из версионированной
     схемы решений (§8); M — источник *выбора* среди них, а не генерации. Предложение
     LLM значения вне замкнутого множества кандидатов недопустимо. Единое правило:
     ответ с неизвестным ID или некорректным JSON отклоняется Python — это ошибка
     протокола (отказ вызова), а не нарушение механизма; C3 становится только принятие
     такого ответа.
2. **C** — фрагмент контекста (span исходного текста).
3. **D** — алгоритмический вывод: ID правила/операции + ссылки на входные свидетельства.
   Исходный span показывает, что прочитано; D объясняет переход к кандидату.
4. **M** — результат микро-шота (вопрос + ответ). Хранится **только как след решения для
   воспроизведения**; правильность по нему не оценивается — эталон устанавливается
   независимо от него.
5. **A** — декларированное допущение эталона (формулировка + владелец). Допущения о
   связи участников формулируются как *дефолтное прагматическое прочтение*, а не как
   строгое следствие словарного свойства: общее знание («лапки — часть тела») само по
   себе не устанавливает, что упомянутые лапки принадлежат именно этой вороне.

Правило против утечки: допущение типа A **не передаётся парсеру как доказательство**.
Если целевое чтение требует A, то либо A явно добавляется во входной контекст (и тогда
оно становится частью проверяемого входа), либо ожидаемый результат помечается
**условным**. Критерий «система обладает знанием» **не устанавливается по её ответу**:
базовый прогон фиксирует обычные целевые прочтения как ожидаемые; отдельный расширенный
прогон с явным A во входном контексте измеряет влияние добавленного знания (§4).

## 3. Схема трассы (на каждое предложение)

```
исходный текст
→ сегментация и структурные кандидаты        [число кандидатов]
→ морфологические варианты                   [число, источник: R1]
→ кандидаты рамок                            [по каждому: источник R/C/D/M]
→ допустимые привязки                        [по каждой: основание]
→ ограничения                                [каждое исключение + основание]
→ микро-шоты                                 [вопрос + ответ, replay-able]
→ итоговая структура                          [класс исхода C1/C2/C3]
```

Метрики фиксируются **только после запуска** (в эталоне не предзадаются): число
кандидатов до/после ограничений, число пересчётов, число микро-шотов, время в трёх
частях — локальные вычисления / ожидание LLM / общее.

Механизм подписок: подписки строятся автоматически из reads; явные триггеры — только
для не-данных событий. Для коллекций подписка срабатывает на **добавление, изменение и
удаление** элемента.

Само-тест подписок входит в объём прототипа (синтетический, вне демо-набора): каждое из
трёх событий над читаемой коллекцией должно запустить пересчёт. Access control запрещает
необъявленное чтение, но не доказывает, что обработчик запросил все необходимые данные:
полнота reads проверяется поведенческим тестом на каждый обработчик (пертурбация каждого
заявленного read → пересчёт запущен) и ревью дизайна.

## 4. Эталоны по предложениям

Общие правила кодирования: целевое чтение vs допустимая альтернатива; запрещённые
выводы; условность при отсутствии знания. Режим всех предложений — ASSERT, статус
содержания — FACT (если не указано иное).

Порядок аргументов отношений зафиксирован заранее: **HAS_PART(целое, часть)** —
например, HAS_PART(ворона, лапки). Проверка инверсии выполняется относительно этой
конвенции.

Протокол прогонов: **базовый** — без A1–A3 во входном контексте; ожидаемые чтения
зафиксированы заранее (обычные целевые), не выводятся из ответа системы. **Расширенный**
— с явным A1–A3 во входном контексте; измеряет влияние добавленного знания. Разница
прогонов интерпретируется как чувствительность к контексту, а не как наличие/отсутствие
знания.

### S1 «У вороны есть лапки.»

Структура: у + GEN(вороны) + есть + NOM(pl)(лапки).

- **Целевое:** HAS_PART(ворона, лапки). Обоснование: конструкция лицензирует
  отношение владения/части [C]; связь упомянутых участников — допущение **A1**
  (дефолтное прагматическое прочтение; общее partonymy-знание не устанавливает связь
  конкретных упомянутых сущностей).
- **Условность:** HAS_PART требует A1 (дефолтное прочтение; в базовом прогоне парсеру
  не передаётся). Коммит значения, отличного от целевого (HAVE/LOCATIVE/LIKE) — C3
  (принят неверный смысл). Сохранённая неразрешённость {HAVE, HAS_PART} или
  INSUFFICIENT_CONTEXT — C2 (честная неполнота).
- **Кандидаты значения** — схема решений (§8); **выбор** — M.
- **Допустимо:** HAVE + part-feature.
- **Запрещено:** LOCATIVE («у вороны» как локация); инверсия (лапки обладают вороной).

### S2 «У стола есть ножки.»

Структура: у + GEN(стола) + есть + NOM(pl)(ножки).

- **Целевое:** HAS_PART(стол, ножки), допущение **A2** (дефолтное прочтение: упомянутые
  ножки — часть этого стола).
- **Условность:** как в S1 (коммит HAVE вместо HAS_PART — C3; неразрешённый выбор — C2).
- **Кандидаты значения** — схема (§8); **выбор** — M.
- **Запрещено:** LOCATIVE; инверсия.

### S3 «У меня есть книга.»

Структура: у + GEN(меня) + есть + NOM(книга).

- **Целевое:** HAVE(я, книга). Обоснование: конструкция [C]; допущений не требует.
- **Кандидаты значения** — схема (§8); **выбор** — M.
- **Запрещено:** HAS_PART (книга — не часть человека); LOCATIVE; инверсия.
- Замечание: асимметрия с S1/S2 намеренна — проверяется, что part-маркер не
  проставляется безразлично ко всем объектам конструкции.

### S4 «Ворона обладает перьями.»

Структура: NOM(ворона) + глагол + INSTR(перьями). Внеконструкционный случай.

- **Целевое:** HAS_PART(ворона, перья), допущение **A3** (дефолтное прочтение:
  упомянутые перья — часть этой вороны).
- **Кандидаты значения** — схема (§8); лемма «обладать» — якорь поиска; **выбор** — M.
- **Условность:** как в S1 (коммит HAVE вместо HAS_PART — C3; неразрешённый выбор — C2).
- **Запрещено:** LOCATIVE; инверсия; сводимость к отношению типа S6.

### S5 «У вороны лапки.»

Структура: у + GEN(вороны) + NOM(pl)(лапки), **без глагола** — эллипсис copula.
Решающий тест генеральности: если чтение S1 получалось точным совпадением с записью
«у X есть Y», этот случай вне записи и законный исход — C2 (NO_CANDIDATE + отчёт).

- **Целевое:** то же, что в S1 (HAS_PART при A1; честная неразрешённость {HAVE, HAS_PART} — C2).
- **Допустимый честный исход:** C2 с корректным miss-отчётом.
- **Запрещено:** коммит LOCATIVE; инверсия; ручная предзадача пропущенной связки
  (эллипсис должен быть получен механизмом, а не заложен в эталон как вход).

### S6 «Вороны любят червей.»

Отрицательный контроль. Структура: NOM(pl)(вороны) + глагол + ACC(pl)(червей).

- **Целевое:** отношение настроенности LIKE(вороны, червей).
- **Кандидаты значения** — схема (§8); лемма «любить» — якорь поиска; **выбор** — M.
- Нераскрытое значение предиката («отношение с двумя участниками») **не является**
  успешной формализацией: оно не сохраняет смысл «любят» и засчитывается как C2.
- **Запрещено:** принятие HAVE или любой рамки владения; инверсия.
- Пере-предложение HAVE-кандидата, отсечённого ограничениями, — нормальное поведение
  генератора; фиксируется в метрике избыточности, не в C3.

## 5. Проверки на уровне набора (set-level)

- **D1 — различение части и обладания.** Если система обладает знаниями A1–A3:
  чтения S1/S2(/S4) должны быть отличимы от S3 сохраняющим маркером (HAS_PART или
  HAVE+part-feature). В базовом прогоне без A1–A3 единообразный коммит HAVE во всех
  трёх — C3 на предложение (принят неверный смысл); честная неразрешённость
  {HAVE, HAS_PART} — C2 как данные о покрытии. Расширенный прогон с явным контекстом
  проверяет, разрешается ли различение.
- **D2 — отдельность отношения S6.** Чтение S6 не совпадает ни с одним из S1–S5.
- **D3 — перенос без правил под примеры.** Механизм идентичен во всех шести прогонах;
  добавление записи/правила, привязанного к конкретному предложению набора, между
  прогонами = провал генеральности (фиксируется как данные о границе механизма).

## 6. Что эталон намеренно не содержит

- Предзаданных чисел вызовов LLM и кандидатов — только post-hoc метрики (§3).
- Конкретных символов таксономии как обязательных: HAS_PART vs HAVE+part-feature —
  вопрос представления, а не механизма; эталон требует *представленного различия*.
- Независимого эталона из ответов микро-шотов (§2, тип M).

## 7. Открытые до запуска (помечены заранее)

1. Протокол прогонов зафиксирован (§4): базовый без A1–A3 + расширенный с явным
   контекстом; критерий не выводится из ответа системы.
2. R2 в прототипе **не создаётся**. Создание лексикона само по себе не гарантирует
   работу без LLM: словарные значения могут оставаться неоднозначными, и выбор всё
   равно потребует M. Решение о R2 переносится за пределы прототипа.
3. Само-тест подписок (§3) выполняется синтетически, вне демо-набора; контекстный
   сценарий (добавление рамки в дискурс) переносится в пилот 5.

## 8. Схема вариантов и микро-шоты bounded selection (S1, S6)

### 8.1 Версионированная схема решений (артефакт прототипа)

Файл `schemas/decision_schema_v1.json`; поле `version` обязательно; любое изменение —
новая версия, трасса ссылается на версию схемы.

Замкнутое множество отношений для прототипа:

- HAVE(x, y) — владение
- HAS_PART(целое, часть)
- LOCATIVE(x, место)
- LIKE(x, y) — положительная настроенность

**Граница демо:** ограничение этими четырьмя отношениями — объявленная граница данного
демо, а не утверждение о покрытии языка. Чтение вне множества отчитывается как
NO_CANDIDATE (miss), а не молча сводится к ближайшему.

Формирование кандидатов: для каждого слота рамки Python предлагает **все объявленные
отношения**, исключая только доказуемую несовместимость (тип/число аргументов).
Семантические фильтры «форма → значение» не используются: конструкция значения не
определяет, и предфильтрация подсказывает селектору ответ. В частности, «у + GEN»
допускает пространственное чтение — LOCATIVE по форме не отсевается; его отклонение
должно опираться на содержание конкретного высказывания.

### 8.2 Формат микро-шота bounded selection (строгий шаблон)

Язык протокола: английский (согласован). Шаблон:

```
Decision slot: {slot_id} — predicate value of frame {frame_id}
Context span: {source text}
Mentions and preliminary structural links: X={...}, Y={...}
Candidates (schema v{N}, closed set):
  V1. HAVE(x, y) — possession
  V2. HAS_PART(whole, part)
  ...
Task: select the admissible candidate(s), or report that none fits / context is insufficient.
Response (JSON): {"outcome": "ONE_SELECTED" | "MULTIPLE_ADMISSIBLE" |
                 "INSUFFICIENT_CONTEXT" | "NONE_FIT",
                 "selected": ["V#"], "note": "..."}
```

Правила:
- Валидация до принятия: `selected` ⊆ множество кандидатов, все ID известны, JSON
  корректен — проверяет Python. Нарушение → ответ отклонён (ошибка протокола); C3
  становится только принятие невалидного ответа.
- Связка исхода и JSON однозначна: ONE_SELECTED — ровно один ID; MULTIPLE_ADMISSIBLE —
  минимум два различных ID; INSUFFICIENT_CONTEXT и NONE_FIT — пустой список. Только
  NONE_FIT переходит в NO_CANDIDATE + miss-отчёт; INSUFFICIENT_CONTEXT сохраняет
  собственный статус.
- Исходы селектора разделены: один выбран / несколько допустимы (неразрешённый выбор —
  честный неполный результат, не ошибка) / недостаточно контекста / ни один не подходит.
- Невыбранный кандидат **не считается опровергнутым**; причины отклонения не требуются
  (обязательные причины заставляли бы модель выдумывать основания). `note` — необязательно.
- Неверный JSON или неизвестный ID = ошибка протокола: Python отклоняет ответ; это
  отказ вызова (учитывается в бюджете), а не нарушение механизма. Принятие такого ответа
  становится C3.
- Один вызов на слот, без допросов. Ответ микро-шота — след решения (тип M), не эталон:
  правильность оценивается по §4.

### 8.3 Конкретные микро-шоты S1 и S6

**S1.** Слот: значение предиката; рамка: у + GEN(ворона) + есть + NOM(лапки).
Кандидаты: все четыре объявленных отношения (доказуемой несовместимости нет):
V1 HAVE / V2 HAS_PART / V3 LOCATIVE / V4 LIKE.
Ожидание (базовый прогон): целевое — HAS_PART (A1 как дефолтное прочтение, парсеру не
передаётся); выбор определяется M. ONE_SELECTED=HAS_PART → C1. Коммит значения вне
целевого (HAVE/LOCATIVE/LIKE) → C3. MULTIPLE_ADMISSIBLE с {HAVE, HAS_PART} или
INSUFFICIENT_CONTEXT → C2. В расширенном прогоне (явное A1) ожидается разрешение до
HAS_PART.

**S6.** Слот: значение предиката; рамка: NOM(вороны) + V + ACC(червей).
Кандидаты: все четыре объявленных отношения.
Ожидание: ONE_SELECTED=LIKE → C1. Коммит HAVE/LOCATIVE/HAS_PART → C3 (провал
отрицательного контроля). MULTIPLE_ADMISSIBLE, включающее LIKE и другие → C2.
