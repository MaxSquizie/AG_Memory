# Heuristics адаптивного парсера — аудит «мигрировать vs отбросить»

**Статус:** готово (эта сессия). Завершает пункт B из `FORMALIZER_STATUS_AND_REMAINING_WORK.md` и снимает последнее
решение, блокировавшее удаление `adaptive_parser.py`.

## Метод
Каждый модуль прочитан по его реальным функциям (не по имени) и классифицирован:
- **способность** — формальная семантика/структура, которую V7 обязан воспроизвести;
- **поведенческая эвристика** — ремонт дефекта upstream или text-gen workaround конкретного адаптивного парсера.

Правило (two-tier invariant): структурные правила (морфология + синтаксис → синтаксическое решение) допустимы, если они
**заявлены и покрыты корпусным тестом**; лексико-семантические маппинги — только через языковые ресурсы или bounded LLM-пробу.

## По модулям

## Итоговое решение
1. **`generalized_naming`** — единственная реальная способность: мигрировать как declared semantic decision (именование/идентичность) с bounded probe; валидация на данных реального бэкенда в Phase 2/3. До этого именные конструкции честно NO_CANDIDATE/UNRESOLVED.
2. **`coordination_normalization`, `association_continuation`, `correlated_alternatives`** — отбросить как есть (ремонт дефектов upstream / text-gen). Конкретная способность, если окажется нужной, добавляется **явной declared rule/пробой с тестом**, а не копированием эвристики.

## Что это снимает
- Удаление `adaptive_parser.py` больше не блокировано «непонятно, что делать с 4 модулями»: решение по каждому зафиксировано.
- Единственный обязательный порт перед удалением legacy — **именование** (пункт 1); остальные три удаляются вместе с парсером.
