# Общие задачи формализации: реализация после аудита

Основание: [аудит достижимости проб](FORMALIZER_PROBE_REACHABILITY_20261014.md)
и [разделение ответственности](../FORMALIZER_PROBE_RESPONSIBILITIES.md).
Базовый коммит для сравнения: `0146c68dd58e0bf7c47ffc4bfba3a7147f847bd4`.

## Что включено

Профиль `composition`, общий для GUI документов и native-оракла, включает
`ProposalPolicy.composition.structural_tasks = CLOSED_RELATIONS_V1`.
Проба получает целую исходную область до прежних проверок ключевых слов и
мягкого разбиения предложения. Она может выбрать обычную лексическую предикацию,
отрицание, модальность, логическую или временную связь, пропозициональный
аргумент, нечисловой квантор, вопрос к формуле либо группировку скобками.

Это закрытые структурные варианты, а не свободная генерация графа. Модель
выбирает тип, направление, исходные границы, владельца и роль содержания.
Морфология, валентность, типы, связность, неразрывность условий, seal и T5/T6
проверяются прежними механизмами. Новые канонические смыслы не угадываются.

## Что проверяется по смыслу

В тестах фиксируются конкретные ответы закрытых проб, а результат проверяется
через настоящий `execute_native`, тот же релиз GUI, запись AH и журнал.
Например:

* «Мария спит только если Иван пришёл» даёт `SLEEP → ARRIVE`, а не обратную связь.
* «Если бы Иван пришёл, Мария бы спала» сохраняет COUNTERFACTUAL, включая
  принадлежность второй частицы внешнему условию.
* «Иван сообщил, что Пётр пришёл» не превращает «сообщил» в SAY и не утверждает
  отдельный ARRIVE.
* «Каждый студент, который прочитал книгу, может сдать экзамен» помещает
  STUDENT и описание чтения в ограничение, а POSSIBLE — в следствие.
* «Каждый студент может читать книгу и спать» при подтверждённом выборе общего
  участника использует одну связанную переменную в обоих действиях; наружу
  не выходят ни READ, ни SLEEP.
* «Иван может хотеть читать книгу» сохраняет вложенное содержание и контроллера;
  «Иван должен мочь читать книгу» сохраняет оба модальных слоя.

HTTP-тесты используют локальный сервер с подготовленными ответами. Проверены
положительные исходы и отказ, затем replay при закрытом сервере. Это проверка
достижимости и корректности реализации, **не измерение точности живой модели**.
Золотые формулы оракула не изменены; константные ответы старых HTTP-заглушек
заменены адресованными выборами актуального протокола.

## Ручная проверка

После обновления кода нужно пересобрать тестовый профиль, чтобы GUI загрузил
новую политику. Из корня проекта:

```powershell
python tools/prepare_formalizer_v7_gui.py --config artifacts/formalizer-lab/gui.toml --out artifacts/gui-composition --profile composition
python -m ah.gui.app --config artifacts/gui-composition/gui.toml
```

В описании подключения должно быть «общий выбор типа связи, границ и участников».
В разборе доступны исходный фрагмент, русское название задачи, варианты,
выбранные части, грамматические признаки и состояние оставшегося поиска.
При остановке до вопроса показывается причина. Эти записи включены и в
человекочитаемый отчёт. Отрисовка новой карточки проверена через Qt offscreen.

## Явные границы результата

* Числовые кванторы и арифметический движок остаются отложенными по решению
  пользователя. Новая ветка не выдаёт числовой квантор за обычный EXISTS.
* Общий путь ограничен зарегистрированными конструкторами, ролями, типами,
  ресурсами и бюджетами. Он не является доказательством полноты русского языка.
  Локальное подтверждение не означает перебора всех мыслимых интерпретаций.
* Неверный смысловой выбор модели может пройти структурную проверку. Для этого
  сохранены исходные альтернативы и ручная прослеживаемость. Живой модельный
  прогон и отдельная от разработки оценка качества перефраз здесь не выполнены:
  подключённого пользовательского сервера модели в этой среде нет.
* Старые production-релизы сами не изменяются: новая политика включена в общем
  TEST_ONLY-профиле `composition`; её включение в другой релиз требует обычной
  проверки и подписи ресурсов.
