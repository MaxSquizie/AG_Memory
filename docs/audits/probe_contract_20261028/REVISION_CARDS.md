# Карточки продолжения аудита: актуальность оснований

Дата: 2026-10-28. Только аудит; контролируемые свидетельства в check_inventory_contract.py и inventory_contract_evidence.json. Они не моделируют весь запуск GUI и не доказывают ошибочную долговременную запись.

## R1. Завершённый инвентарь именных функций

Цепочка: component_predication.compose_alternatives → nominal_functions.prepare → function_inventory.begin → structural_tasks.choose/source_set → NOMINAL_FUNCTION + FUNCTION_INVENTORY → nominal_reference_groups.project / qualitative_quantity.resolve / component_phrases.prepositional_groups.

Вход производителя: конкретные token_id, ограничения задачи, вход родителя, контекст, domain_feedback. begin учитывает их в подписи. prepare возвращает True также при повторном использовании завершённого инвентаря. Потребитель prepared проверяет только вид, список token_id, complete и отсутствие superseded: вычисленная подпись не сравнивается. Более того, prepared не принимает constraints, тогда как prepare передаёт cfg['_task_constraints']; просто добавить сравнение этих двух по-разному вычисленных подписей недостаточно.

Контролируемый свидетель: завершить инвентарь при input_signature=A, заменить вход на B. prepared=True, хотя подписи различны. begin при B корректно требует пересчёт. Значит гарантии этих интерфейсов различны.

Ограничивающее свидетельство: compose_alternatives перед потребителями явно вызывает prepare. Это защищает обычную последовательность от одного лишь изменения подписи. Не доказано, что GUI достигает потребителя в обход prepare. Нельзя объявлять этот свидетель доказательством неправильного разбора.

Необходимое свойство: готовность относится к точной идентичности задачи, доступной обоим концам. Локальная достаточность: потребитель принимает только результат для ожидаемой идентичности, а несовпадение требует вычисления/явной неполноты. Это не решает отзыв доказательств при неизменной идентичности (R2).

## R2. Отзыв ответа не отзывает производный инвентарь

Цепочка: структурная проба → proof → NOMINAL_FUNCTION/TEMPORAL_FUNCTION → complete → component_probe_replay.supersede → повторный begin и rows/units.

Контролируемый свидетель использует исходно валидный proof: licensed=True. После реального supersede(p1,p2), licensed=False, но begin для обоих инвентарей возвращает None (разрешает reuse); nominal_functions.rows и temporal_functions.units возвращают по одной записи со старым proof. Ни signature, ни флаг superseded этих производных записей не меняется при supersede пробы.

Потребители: component_clause.build_clause исключает temporal_functions.owned_refs из обычных компонентов; temporal_attachment.attach использует снимки функций в frame.semantic либо units, нормализует время, затем назначает область. nominal_reference_groups.project переносит функцию в reference_constraint; preserves_nominal_functions требует сохранения выбранной функции. На этих границах нет проверки licensed каждого основания инвентаря. Снимки внутри frame — дополнительный потребитель, который нельзя исправить одним фильтром units.

Доказано локально: после явно отозванного основания интерфейсы продолжают предоставлять результат как активный и завершённый. Не доказано: полный планировочный путь, на котором такой отзыв происходит между подготовкой и записью данного корня без компенсирующего пересчёта.

Необходимое свойство: актуальность результата включает актуальность всех положительных и отрицательных оснований, в том числе ответа о завершении перечисления. Последний сейчас хранится у именного домена как decision_ref отдельной строки; complete сам по себе не содержит полного набора зависимостей. Для времени complete тоже не несёт ссылки на ответ NONE.

Локальная достаточность: при отзыве любого основания результат и его снимки недоступны для семантического использования до пересчёта. Возможны разные реализации: проверка полного замыкания при чтении или транзитивная инвалидация. Нужны оба направления: отзыв не должен терять отрицательное основание, а чтение не должно обходить проверку через syntax_trace/frame.semantic. Проверка только одного decision_ref недостаточна.

## R3. Память зависит от количества кандидатов

Цепочка: запрос композиции → CompositionSession.memory → compile_goals/reader.read → readable_memory → контекст пробы.

Фактический ранний выход: reader отсутствует ИЛИ len(options)<2 → пустая строка. Свидетель с подключённым reader и одним кандидатом возвращает пустую строку без чтения. Это доказательство отключения канала, а не того, что конкретному слоту обязательно нужна память.

У singleton всё ещё могут различаться ответы «подходит», «не подходит», «недостаточно данных». Поэтому число предъявленных кандидатов не доказывает независимость задачи от контекста. Контраст для проверки окончательного запроса: одинаковое высказывание с опущенным участником в двух разных контекстах; единственный предъявленный кандидат допустим только в одном. Если все другие каналы тоже одинаковы, обоснованный выбор невозможен. Этот контраст пока не прогонялся как реальная проба.

Необходимое свойство: обязательность контекста задаётся семантической обязанностью слота и происхождением кандидата. Достаточность локального изменения: передача различающего контекста во всех задачах, которые от него зависят, либо явное сохранение неизвестности. Безусловное чтение всей памяти не является требованием.

## R4. Ранее установленные ограничения в следующей пробе

component_constraints.question читает все NOMINAL_HOST_QUESTION данного region_ref с selected и переводит их в текст «Already established interpretation constraints». Фильтра актуальности proof/решения/версии входа здесь нет. compatible_bundle аналогично использует ESTABLISHED_PREDICATE_ROLE того же task_scope, сохраняя proof, но не вызывая licensed для него. Для partial_readings ниже в этой же функции проверка valid_domain уже существует.

Это статически установленная асимметрия потребителей. Динамический конфликт двух версий одного хозяина здесь не воспроизведён. Проверить нужно не только очистку полей после отказа, но и текст следующей пробы: иначе исполнитель получает отозванное решение как обязательное основание.

## R5. Граница записи не является отсутствующей защитой

native_frontend выполняет structural_seal перед resolve_references и лексическим выбором. Поэтому seal не может свидетельствовать о готовности этих последующих решений. native_plan.node_for отдельно проверяет структурные флаги, выбранную лексику, неполные компоненты и ссылки. nominal_reference_binding.validate проверяет живую долговременную привязку, журнал CONTEXT_READ, хэш и полноту поиска.

Это реальные защиты, их нельзя игнорировать и утверждать «любая stale-запись попадёт в память». Но проверка долговременной идентичности не доказывает актуальность более раннего решения о функции исходного слова. Необходима отдельная цепочка от исходного proof через reference_constraint до соответствующего корня, с учётом пересмотров. Она пока не закрыта.

## Предел достаточности

R1–R4 показывают разные обязанности одного семейства: идентичность задачи, жизнеспособность оснований, достаточность контекста и верность его проекции. Исправление только текста пробы не закрывает первые две; фильтрация строк журнала не закрывает уже скопированные результаты и отрицательные доказательства завершения. Для всего контура остаются непроверенные режимы, генераторы и рёбра из основного отчёта. Достаточность описана только для конкретных границ при указанных предпосылках.
