# F07/F12: жизненный цикл инвентарей и установленных хозяев

29 октября 2026. Исправления общего алгоритма, без частных языковых правил.

## Исправленные границы

1. `function_inventory.begin/current/complete/live` теперь разделяют идентичность задачи и жизнеспособность результата. Идентичность включает исходный источник, точные вхождения, ограничения, вход родителя, контекст и domain_feedback. Потребители передают тот же `_task_constraints`, который использовал prepare; prepared больше не проверяет только список токенов.
2. У каждой генерации инвентаря свой inventory_ref. Завершение сохраняет все положительные proofs единиц и отрицательный completion_proof. Для NOMINAL отсутствие завершения не допускается. TEMPORAL без отрицательного ответа завершается только при покрытии всех исходных вхождений. Изменение источника во время подготовки запрещает публикацию.
3. Завершённый инвентарь содержит хеши единиц. Отзыв любого основания, изменение содержимого единицы или повторная подготовка лишают старый результат разрешения. Проверяется также скопированная единица, не только изменённая строка syntax_trace.
4. rows/units больше не возвращают отозванные единицы. На границе построения предлога/группы недействительный существующий инвентарь вызывает InventoryUnavailable. Сборщики clause/predication переводят это в явный FUNCTION_INVENTORY_UNRESOLVED и не возвращают зависимые кадры. Нет скрытого перехода от неготового общего инвентаря к прежним лексическим правилам.
5. Построенные кадры сохраняют function_inventory_refs. Temporal attachment проверяет их до использования снимков, normalize проверяет саму единицу. Проекция структуры для следующих проб и native_plan проверяют зависимости выбранного кадра. Это дополнительная защита после исправления первичного producer/read контракта, а не единственная проверка в конце.
6. NOMINAL_HOST_QUESTION сохраняет вход родителя, источник и отпечаток реального выбора. Следующий вопрос читает только живое решение своего входа. Пересмотр хозяина отзывает предыдущий вопрос через общий supersede. Скопированные описания сохраняют свидетельства хозяев; следующие структурные пробы и граница построения плана проверяют их.

Идентичность текущей задачи сравнивается при reuse/prepare. Лицензия уже построенного дочернего результата при чтении в родителе проверяется по его собственному receipt: смена текущего parent scope сама по себе не отзывает ребёнка. Эти две проверки намеренно различаются.

Ссылки на инвентари и свидетельства хозяев исключены из сравнения *языкового* содержания composition_equivalence. Иначе одинаковые интерпретации от двух производителей становились неразличимыми языковыми вариантами лишь из-за разного происхождения. Выбранное представление сохраняет собственные зависимости; код не объявляет их ненужными.

## Проверки

- check_inventory_lifecycle: реальные choose/codec proofs; точные/изменённые constraints; отзыв положительной и отрицательной страницы; старые копии, изменение payload единицы, повторная подготовка, недопустимость лексического fallback; различие текущего parent scope и лицензии ребёнка; отказ нормализовать отозванный снимок.
- check_host_constraint_lifecycle: реальный select_hosts и текст последующего question; выбор виден при актуальности, скрыт для другого родителя и после supersede; зависимый снимок перестаёт быть действительным.
- Прошли nominal probe chain, типы выбора, обычный и вложенный PARTIAL, OOV contracts и три сквозных content-reference contrasts. PARTIAL остаётся без записи. Это сценарные исполнители, не Luna/локальная модель.
- В type-fixture инвентарь теперь строится через begin и допустимое полное покрытие пустого TEMPORAL-набора. Не создаётся искусственное завершение NOMINAL без отрицательного основания.

## Что не объявляется закрытым

Исправлены конкретные R1/R2 инвентарей и R4 проекции хозяев из REVISION_CARDS. Это не полная миграция всех F07/F12: ещё требуется проверить остальные ручные копии semantic-полей, lexical recovery, constraints и пути повторного использования результатов диспетчера. Не заявлена глобальная очистка каждого производного поля; проверяемые зависимые результаты блокируются на перечисленных границах и пересчитываются при следующем prepare.

Для late inventory/host guards в native_plan подтверждены расположение в коде и жизнеспособность используемого валидатора; отдельный GUI-сценарий отзыва именно между лексической готовностью и записью не исполнялся. Сквозные сценарии подтверждают отсутствие регрессии перечисленных обычных путей, не полноту всех порядков событий. F05 полнота генераторов, F08 прочие протоколы и F15/F16 политики остаются отдельно.
