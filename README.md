# AH Agent MVP

**Ассоциативно-гетерархическое (AH) ядро памяти для текстового LLM-агента.**

## Что это и зачем

Большинство агентов не помнят ничего между диалогами, либо используют векторный поиск по заметкам: он находит похожие куски текста, но не умеет рассуждать над фактами. Он не понимает «кто есть кто», не отслеживает одну и ту же сущность через десятки упоминаний, не замечает противоречий, не помнит, что было раньше, и не может объяснить, почему ответил именно так.

`ah-agent-mvp` даёт агенту **структурную долговременную память**, которая работает полностью локально. Память хранит произошедшее как типизированные факты с участниками и логической структурой («Иван дал книгу Пете»), связывает их между собой, распространяет по этим связям «возбуждение» (связанные воспоминания подсвечиваются вместе) и делает над ними символьные выводы: транзитивность, кванторы, временные интервалы, причинность. Агент может вспомнить конкретный факт, отследить сущность, обнаружить противоречие, явно поправить старый вывод и показать полное происхождение любого ответа.

Название отражает устройство памяти:
- **ассоциативная** — узлы соединены связями, и активация распространяется по ним, поэтому связанные воспоминания «загораются» вместе;
- **гетерархическая** — факты группируются по типам, шаблонам и доменам, образуя иерархию.

### Из чего состоит память

Память — это граф из семи типов узлов:

| Узел | Что хранит |
|------|-----------|
| `S`  | устойчивое слово / парадигма (лексическая единица) |
| `m`  | конкретная сущность-манифестация (объект, персона) |
| `g`  | логический оператор (`AND`, `OR`, `NOT`, кванторы) |
| `k`  | множество / неопределённая ссылка (`AMBIGUOUS`) |
| `T`  | типизированный шаблон-утверждение (предикат + валентность) |
| `N`  | пропозиция — конкретный факт с актантами |
| `L`  | ассоциативная связь между узлами (`IS-A`, `FOLLOW`, `CAUSE`, …) |

Каждый узел живёт в одном из трёх **доменов**:
- **C** — *canonical*: устойчивые факты и знания;
- **P** — *propositional*: текущие рассуждения и выводы;
- **H** — *experiential*: пережитый опыт (диалог, события, следы внимания).

Поверх канонического хранилища лежат производные индексы (полностью перестраиваются из `AH`), движок активации и проекция в контекст агента.

## Что получает ваш агент

- **Точное вспоминание.** Факты хранятся как пропозиции с актантами, поэтому агент вспоминает именно то, что произошло, вместе с участниками.
- **Отслеживание сущностей.** Одна и та же персона/объект — один узел во всех наблюдениях; кореференция разрешается по доказательству.
- **Символьный вывод.** Над графом работают логические правила: транзитивность `IS-A`/`FOLLOW`, вывод по `CAUSE`, кванторы (`EXISTS`/универсальные), временные интервалы, явное опровержение `FALSE(N)`.
- **Обнаружение противоречий.** Конфликтующие утверждения не затираются: агент видит обе стороны с причиной.
- **Явная коррекция.** Старый вывод можно поправить (`FALSE(N)`); история при этом сохраняется.
- **Пояснимость.** У каждого вывода есть полный provenance/trace, и весь граф виден в GUI.
- **Локальность.** Работает с локальными бэкендами (Ollama, LM Studio, HuggingFace в отдельном процессе) и имеет мост на Android NPU; ядро не зависит от `torch`/`transformers`/облака.

## Как это устроено

Один когнитивный цикл (turn):

```text
внешний текст
→ восприятие: детерминированный формализатор T0–T6b
   (токенизация → структура → морфология/зависимости → рамки → seal → семантика → IR → консолидация → журнал → коммит)
→ Ignition ticks: распространение активации по графу
→ Workspace = узлы с x > t (то, что «горячее» сейчас)
→ Symbolic Inference: транзитивность, кванторы, вывод
→ опциональная материализация вывода (C < P < H)
→ проекция ACTIVE/DEPENDENCY → AgentContext
→ ответ LLM-агента
→ интеграция ответа в память (H-only путь) + FOLLOW / episodic history
→ персистентность
```

Восприятие обрабатывает **детерминированный формализатор**: он превращает русский текст в типизированные кандидаты, проверяет их и записывает в граф. У восприятия два исхода — валидный результат или явная ошибка с причиной; тихого «угадывания» нет. Ниже — как устроен сам формализатор.

## Формализатор: как устроен

### Полный цикл обработки одного наблюдения

```text
RawInput → T0 → SRL → T1 → TD → T2 → TP → structural_seal
         → T3 → T4 → assemble_candidate_ir → C → T5 → T6  (+ T6b — ревизия/отзыв)
```

Каждая стадия работает в своей колонке: у неё зафиксированы вход, выход, разрешённые чтения и отказы; выйти за свою колонку стадия не может.

1. **T0.** Каждый символ исходной строки помечается как токен, пунктуация или пробел — ни одна буква не теряется; фиксируется снимок ресурсов.
2. **SRL (структурная разбивка).** Кандидаты границ предложений/клауз и эллипсиса. Гипотеза токена всегда включает вариант «оставить как есть»; расстояние до известного слова используется только для ранжирования вариантов.
3. **T1 (морфология и лексика).** Для каждого слова — лемма, часть речи, падеж/число/род; двусмысленные варианты сохраняются отдельными кандидатами. Незнакомое слово остаётся как есть, пока нет основания считать его опечаткой.
4. **TD (зависимости и кореференция).** Кандидаты зависимостей и разрешения местоимений по четырём каналам доказательств (морфология / синтаксис / дискурс / память). Несовместимые по известным признакам кандидаты отклоняются с записью причины. Строится дерево областей действия для кванторов, отрицания, модальности и времени.
5. **T2 (рамки).** Из слов собираются предикативные рамки по объявленным операциям и ресурсу валентности; недостающие участники фиксируются как кандидаты, непокрытые связи честно помечаются.
6. **TP (локальные гипотезы модели).** Когда детерминированных кандидатов недостаточно, модель предлагает ограниченную локальную структуру — только из объявленных типов узлов и рёбер, без канонических идентификаторов и без утверждения об истинности; предложение детерминированно проверяется.
7. **structural_seal.** Структура фиксируется для этой версии интерпретации: дальнейшее изменение запрещено, незакрытая часть выдаётся как честная неполнота.
8. **T3 (семантическое разрешение).** Для каждого слота — ограниченный выбор значения из заранее объявленного набора; каждое решение остаётся предварительным и несёт основания.
9. **T4 (поиск и исход).** Итог: `RESOLVED` / `AMBIGUOUS` / `INSUFFICIENT_CONTEXT` / `NO_CANDIDATE` / `UNRESOLVED`; каждый не-`RESOLVED` несёт явную причину. Однозначное решение требует одновременного выполнения трёх условий; наличие одного кандидата само по себе недостаточно.
10. **assemble_candidate_ir.** Все выходы собираются в неизменяемый IR — единственный результат формализации.
11. **C (консолидация).** Планы объединения идентичных сущностей, дедупликация и каноническая привязка; либо изолированный открытый шаблон для нового слова. Записей в граф ещё нет.
12. **T5 (журнал).** Формируется батч и запись журнала; факт попадает в журнал только при исходе `RESOLVED`.
13. **T6 (единственный писатель).** Утверждённые факты записываются в граф одной атомарной транзакцией с идемпотентными маркерами; после сбоя состояние восстанавливается детерминированно до того же результата.
14. **T6b (ревизия и отзыв).** Новые данные создают новую версию интерпретации того же наблюдения; отзыв наблюдения каскадно инвалидирует его основания и закрывает открытые конфликты.

### Типы оснований: O C W R D M A P

Каждое решение опирается на типизированные основания двух классов с разными правами.

**Truth-grounds — утверждают, что содержание является фактом:**
- **O** — само наблюдение: исходный фрагмент текста дословно;
- **C** — объявленное контекстное утверждение (дословная цитата); может подтверждать другие наблюдения, но само в память как факт не записывается;
- **W** — версионированная фоновая запись с собственным происхождением и интервалом действия.

**Interpretation grounds — объясняют, как распознаны значение и структура:**
- **R** — запись ресурса (морфология, валентность, смыслы);
- **D** — сработавшее проверяемое правило и зафиксированные признаки;
- **M** — валидированный выбор модели или локальная гипотеза (сохранены запрос и ответ); повтор того же выбора не усиливает основание;
- **A** — явно объявленная внешняя гипотеза, которая сама по себе не является фактом;
- **P** — свидетельство предшествующего наблюдения из контекста; используется только для разрешения местоимений.

Факт в память попадает только на основании O/C/W. Остальные типы (R/D/M/A/P) объясняют выбор интерпретации и структуру, но истинность содержания подтверждают только truth-grounds.

### Честная неполнота

Покрытие структуры отчитывается отдельным статусом — `FULL_CANONICAL` / `OPEN_LEXICAL` / `PARTIAL` / `NONE` — независимо от семантического исхода. Отсутствие записи в ресурсе даёт явный диагноз (например, неизвестную валентность); незанятый слот и непокрытая связь сохраняются как кандидаты с причиной.

### Два независимых состояния решения

Жизненный цикл решения (`OPEN → PROVISIONAL → … → COMMITTED / SUPERSEDED / FROZEN`) отделён от семантического исхода (`RESOLVED` / `AMBIGUOUS` / `INSUFFICIENT_CONTEXT` / `NO_CANDIDATE` / `UNRESOLVED`). `RESOLVED` выдаёт T4; `COMMITTED` появляется только после условий коммита и маркера.

### Коммит и ревизия

T5 пишет журнал, T6 — единственный писатель утверждённых фактов: одна атомарная транзакция, идемпотентные маркеры, детерминированное восстановление после сбоя до того же конечного состояния. T6b создаёт новую версию интерпретации при новых данных; отзыв наблюдения каскадно снимает его основания и закрывает открытые конфликты — отозванный кандидат перестаёт быть видимым, память остаётся открытой (open world).

### Конфликты без молчаливого удаления

Кандидат, противоречащий закоммиченному факту или другому фрагменту того же батча, исключается из коммита и остаётся видимым как открытый отчёт `CONFLICTING_EVIDENCE` с причиной и стабильным детерминированным идентификатором. Отчёт закрывается только явным актом (отзыв / замена / разъяснение говорящего); альтернатива не исчезает без следа.

### Логика, кванторы и время

Над графом работают логические операторы (`AND`/`OR`/`XOR`/`NOT`) и кванторы (`EXISTS`/`FORALL`) в канонической форме; элиминация дизъюнкта требует явной временной лицензии. Отрицание несёт область действия как интервал. Временные утверждения прикрепляются к фактам с интервалом и семантикой `CONTINUOUS`/`EXISTENTIAL`; противоречие проверяется по гарантированной одновременности, опираясь на типизированные интервалы.

### Вывод по закоммиченному состоянию

Запросы-цели выполняются read-only поверх утверждённых фактов; производные выводы дописываются в журнал (append-only), существующие записи, версии и маркеры остаются неизменными.

### Адаптивный опыт (R-X)

Кэш хранит опыт: он влияет на приоритет кандидатов, текущее предложение всегда разбирается заново, новая интерпретация никогда не блокируется кэшем. Чтение разделено по стадиям (морфологическое / структурное / семантическое), повторное использование записи не создаёт нового основания.

### Детерминизм и версионирование

Один вход и один снимок ресурсов дают одинаковый результат на каждой стадии; изменение объявленного источника вызывает пересчёт, исход при этом может остаться прежним. Каждая интерпретация версионируется; ревизия создаёт новую версию истории.

## Требования и установка

- **Python ≥ 3.12.**
- **Локальная LLM** — любой из поддерживаемых бэкендов: Ollama, LM Studio или HuggingFace в отдельном процессе; либо мост на Android NPU. Ядро само не тянет `torch`/`transformers`.
- Базовое ядро лёгкое (зависимость только `pymorphy3`); остальное — опциональные extras:

```bash
# ядро + тесты
pip install -e ".[test]"

# GUI (PySide6 + VisPy) и локальная LLM (torch/transformers)
pip install -e ".[gui,llm]"

# отдельные бэкенды / возможности
pip install -e ".[llm-lora]"     # LoRA-адаптеры
pip install -e ".[llm-vision]"   # мультимодальность
```

Точка входа — два console-скрипта: `ah-agent` (CLI) и `ah-gui` (GUI).

## Как запустить

### GUI (основной способ работы)

```bash
# Windows
run_gui.bat                 # config/default.toml
run_gui_ollama.bat         # бэкенд Ollama
run_gui_lmstudio.bat       # бэкенд LM Studio

# Linux/macOS
./run_gui.sh
# или напрямую:
ah-gui --config config/default.toml
```

GUI показывает AH как GPU-сцену (цвет узла = домен, «жар»/размер = возбуждение `x`, белая вспышка = активация, голубая обводка = Workspace), содержит диалог с агентом, полный TOML-редактор конфига с picker'ом пути к модели и инспектор узлов. Все параметры можно менять из GUI; поля помечены `LIVE / NEXT_TURN / RESTART_LLM / RESTART_RUNTIME`.

Путь к локальной модели задаётся только в конфиге:

```toml
[paths]
llm_model_dir = "C:/Models/Qwen"
```

### Включение формализатора

Чтобы восприятие обрабатывал детерминированный формализатор, задайте переменную окружения перед запуском:

```bash
AH_FORMALIZER=1 ah-gui --config config/default.toml
# или для CLI:
AH_FORMALIZER=1 ah-agent --config config/default.toml <команда>
```

### CLI (диагностика и загрузка данных)

```bash
ah-agent --config config/default.toml <команда>
```

| Команда | Назначение |
|---------|-----------|
| `summary` | сводка по runtime |
| `dsl "<выражение>"` | выполнить одну DSL-команду/пайплайн |
| `dump-json` / `dump-dot` | дамп канонического/runtime-графа (JSON / Graphviz) |
| `tick [n]` | вручную продвинуть Ignition на n тиков |
| `refute <uid> [--tick]` | создать/повторить `FALSE(N)` и запланировать опровержение |
| `import-corpus <path>` | холодная загрузка структурированного JSON/.ahm/.prj в AH |
| `import-text <path>` | загрузить сырой текст как опыт USER (по умолчанию строгий семантический парсинг) |
| `import-dialogue <path>` | загрузить диалог `ah_dialogue_v1` |
| `import-memory <path>` | заменить живой AH снапшотом персистентности |
| `reset-memory` | очистить AH/runtime/context и заново создать SELF/USER |

Пример DSL:

```bash
ah-agent dsl "findRoles role=LOCATION value=@M_1 domain=H | findLists domain=H | where meta.TYPE=Episode"
```

### Конфигурация

Главный файл — `config/default.toml`; рядом лежат готовые пресеты под бэкенды: `ollama.toml`, `lmstudio.toml`, `android.toml`. Конфиг управляет: путями и параметрами LLM, начальными весами интеграции, функциями активации `f/g/h/t/ν`, силой семантических/сенсорных seed'ов, lifecycle/GC, глубиной и бюджетом вывода, порогом Workspace, бюджетом AgentContext, политикой персистентности, identity агента/пользователя и числом тиков оркестратора.

## Как встроить в своего агента

Ядро собирается из конфига в живой runtime, после чего каждый ход прогоняется через оркестратор:

```python
from ah.config import AppConfig
from ah.bootstrap import RuntimeServices

services = RuntimeServices.build(AppConfig.from_toml("config/default.toml"))
# на каждый входной текст:
result = services.agent.handle_user_text("Иван дал книгу Пете.")
```

- `RuntimeServices` держит все подсистемы (ядро, восприятие, интеграцию, вывод, DSL, персистентность) и готов к работе.
- Оркестратор принимает текст и возвращает структурированное восприятие + ответ агента; память при этом обновляется атомарно.
- LLM работает в отдельном процессе по JSONL-протоколу, поэтому вашему ядру не нужны `torch`/CUDA — достаточно запустить бэкенд (Ollama/LM Studio) и указать путь к модели в конфиге.
- Персистентность — атомарный JSON (`temp → os.replace`); при старте память поднимается из снапшота, индексы перестраиваются автоматически.

## Прозрачность и отладка

- **GUI-сцена** — весь граф в 2.5D/3D: домен цветом, возбуждение размером/«жаром», вспышка при активации; инспектор узлов показывает поля и связи.
- **CLI-дампы** — `dump-json` / `dump-dot` выгружают канонический или runtime-граф в JSON/Graphviz.
- **DSL** — высокоуровневые запросы к памяти (`findRoles`, `findLists`, `where`, пайплайны).
- **Диагностика и trace** — read-only инспектор, трассировка выводов, полный provenance каждого вывода.

## Состояние проекта и лицензия

Проект — MVP с крупным тестовым свитом (605 тестов) и готовыми GUI/CLI-точками входа; восприятие обрабатывает детерминированный формализатор (`AH_FORMALIZER=1`). В репозитории **не указана лицензия** — перед коммерческим использованием уточните условия у автора.

## Структура проекта

```text
config/            # default.toml + пресеты (ollama/lmstudio/android)
```
