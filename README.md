# AG Memory

**Ассоциативно-гетерархическая долговременная память для LLM-агентов.**

AG Memory — это архитектура и рабочее ядро когнитивной памяти, в которой языковой опыт превращается в **типизированную семантическую структуру**, связывается с уже известными сущностями и событиями, получает явные основания и затем участвует в ассоциативном вспоминании и символическом выводе.

Проект ориентирован на текстового агента и локальный runtime. Формализатор принимает русский текст, строит проверяемое представление смысла и отделяет **интерпретацию** от **утверждения факта**: модель может предложить локальную гипотезу, но не может сама назначить каноническую идентичность, объявить содержание истинным или записать его в память.

> Главная идея AG Memory: память должна хранить не текст о мире, а структурированное представление того, **что произошло, с кем, в какой логической форме, на каком основании и при каких условиях это всё ещё считается действующим**.

## Идея проекта

АГ-память рассматривается как долговременное состояние агента, а не как архив сообщений.

Она должна уметь одновременно:

- сохранять новый опыт;
- поддерживать устойчивые идентичности сущностей;
- представлять события и отношения через роли;
- хранить отрицание, дизъюнкцию, импликацию, модальность и кванторы как структуру;
- учитывать время и область действия утверждений;
- сохранять несколько независимых оснований одного и того же содержания;
- отзывать устаревшую опору без уничтожения истории;
- распространять активацию по ассоциациям;
- формировать текущий фокус внимания;
- строить символические выводы с трассируемым происхождением;
- проецировать только релевантную часть памяти в контекст LLM.

Два механизма принципиально разделены:

```text
Recall    = что сейчас релевантно?
Inference = что следует из уже формализованных знаний?
```

Высокая активация делает узел заметным для агента, но не делает его истинным. Истинность и доступность факта определяются его структурой и живыми путями поддержки.

## Модель памяти

Внутреннее состояние описывается как:

```text
AH = <S, C, P, H, L>
```

| Компонент | Назначение |
|---|---|
| `S` | устойчивые языковые символы и распознаваемые словоформы |
| `C` | канонические знания и устойчивые семантические структуры |
| `P` | пропозициональный контур рассуждений и производных результатов |
| `H` | пережитый опыт: диалог, события, эпизоды, собственная история агента |
| `L` | типизированные направленные связи между элементами памяти |

Внутри семантических доменов используется несколько базовых типов:

| Тип | Смысл |
|---|---|
| `s` | языковой символ: лексическая единица и её формы |
| `m` | самостоятельно адресуемая сущность или понятие |
| `T` | шаблон предиката: какие роли допускает отношение |
| `N` | конкретная реализация предиката — пропозиция или событие |
| `g` | функциональная конструкция с машинной семантикой |
| `k` | адресуемая группировка, эпизод или набор альтернатив |
| `L` | направленная типизированная ассоциация |

### Почему сущность и её имя — разные вещи

```text
s_IVAN != m_IVAN
```

`s_IVAN` относится к языку: это способ распознать и выразить слово «Иван».

`m_IVAN` относится к памяти: это конкретная семантическая сущность, которая может участвовать в событиях, отношениях, ассоциациях и выводах.

Имя не является identity key. Каноническая идентичность строится из структуры, контекста и уже известных связей.

## Как выглядит один факт

Пусть агент получает:

```text
Иван передал книгу Марии.
```

Упрощённое представление может выглядеть так:

```text
m_IVAN
m_BOOK
m_MARIA

T_TRANSFER
├── SUBJECT
├── OBJECT
└── RECIPIENT

N_TRANSFER
├── T*        → T_TRANSFER
├── SUBJECT  → m_IVAN
├── OBJECT   → m_BOOK
└── RECIPIENT→ m_MARIA
```

`T` описывает **тип ситуации**, а `N` — **конкретное произошедшее**.

Если содержание имеет логическую форму, над пропозициями строится `g`:

```text
Иван не пришёл.

g_NOT
└── N_ARRIVE
    └── SUBJECT → m_IVAN
```

Поэтому логика хранится не как приписка к строке текста, а как часть канонической структуры.

## Когнитивный цикл

Высокоуровневый поток одного хода агента:

```text
внешний текст
    ↓
формализация и разрешение смысла
    ↓
атомарная запись подтверждённой структуры в AH
    ↓
seed / reactivation
    ↓
Ignition: распространение активации
    ↓
Workspace: текущий активный подграф
    ↓
Recall + Symbolic Inference
    ↓
детерминированная проекция в AgentContext
    ↓
LLM Agent
    ↓
ответ / решение / действие
    ↓
запись пережитого опыта в H
```

Каноническая память и runtime-состояние разделены: возбуждение, текущий Workspace и временный контекст могут пересчитываться, не меняя сам факт.

## Формализатор V7

Формализатор — граница между естественным языком и канонической памятью.

Его задача — не «угадать наиболее похожий смысл», а построить типизированные кандидаты, проверить их основания, сохранить неоднозначность там, где она действительно есть, и допустить запись только после прохождения явных контрактов.

Полный нормативный путь:

```text
RawInput
  → T0
  → SRL
  → T1
  → TD
  → T2
  → TP
  → structural_seal
  → T3
  → T4
  → assemble_candidate_ir
  → C
  → T5
  → T6

T6b → новая версия интерпретации / отзыв опор
```

### Стадии по смыслу

| Контур | Что происходит |
|---|---|
| `T0` | вход валидируется, исходные символы и диапазоны фиксируются без потерь |
| `SRL → T1 → TD` | строятся лексические, морфологические, синтаксические, coreference- и scope-кандидаты |
| `T2` | формируются предикативные рамки и типизированные аргументы |
| `TP` | при структурном разрыве допускается ограниченная локальная гипотеза |
| `structural_seal` | структура версии фиксируется и больше не может незаметно измениться |
| `T3` | разрешаются значения уже существующих структурных слотов |
| `T4` | совместимые кандидаты собираются в обоснованное решение либо явную неопределённость |
| `assemble_candidate_ir` | создаётся неизменяемый `FormalizerCandidateIR` |
| `C` | выполняются identity/dedup и строится план канонической привязки |
| `T5` | план и решения фиксируются в durable-журнале |
| `T6` | допустимый план атомарно применяется к AH |
| `T6b` | изменение контекста, ресурса или наблюдения создаёт новую версию и отзывает устаревшие опоры |

### Что может и чего не может модель

LLM используется как **ограниченный источник предложения**, а не как владелец памяти.

Модель может:

- предложить локальную структурную гипотезу;
- выбрать один из явно разрешённых идентификаторов;
- помочь разрешить локальную неоднозначность;
- работать только через объявленный контекст и журналируемый вызов.

Модель не может:

- назначать канонические UID;
- создавать неизвестный машинный оператор;
- объявлять содержание истинным;
- писать напрямую в AH;
- молча объединять новый смысл с существующим;
- обходить типы ролей, валентность и границы `structural_seal`.

Это сохраняет полезность LLM там, где язык неоднозначен, не отдавая ей право переписывать семантическую память.

## Основания и граница истины

Каждое решение хранит provenance и типизированные основания.

Они разделены на два класса.

### Truth grounds

Эти основания могут поддерживать утверждённый факт:

| Ground | Источник |
|---|---|
| `O` | само утверждающее наблюдение и его исходный span |
| `C` | явно переданное контекстное утверждение |
| `W` | версионированное фоновое знание с собственным provenance |

### Interpretation grounds

Они объясняют, **почему структура была распознана именно так**, но не делают содержание истинным:

| Ground | Источник |
|---|---|
| `R` | морфология, валентность, словарь смыслов и другие ресурсы |
| `D` | сработавшее проверяемое правило |
| `M` | валидированное предложение модели |
| `A` | явно объявленная внешняя гипотеза |
| `P` | предшествующее наблюдение, используемое для разрешения ссылки |

Ключевой инвариант:

```text
R / D / M / A / P
не являются самостоятельным подтверждением факта.

Материализация утверждённого содержания
требует O / C / W.
```

Поэтому удачная интерпретация и истинность утверждения — разные вещи.

## Новая лексика без угадывания

Словарь не считается закрытым.

Если структура предложения понятна, но для предиката нет подтверждённого канонического смысла, формализатор может сохранить **occurrence-local open predicate**:

```text
новая лексема
    ↓
OpenPredicateCandidate
    ↓
проверенные роли и source spans
    ↓
изолированный T
semantic_status = UNLINKED
```

Такой `T` позволяет помнить само утверждённое содержание, но не получает чужую семантику «по похожести».

Пока связь с известным смыслом не подтверждена:

- не выполняются правила вывода, требующие канонического sense;
- не создаётся скрытая синонимия;
- не происходит cross-source alias;
- последующее связывание выполняется явно и версионно.

Это позволяет расширять язык памяти без обработчика под каждую новую фразу и без тихой подмены смысла.

## Логика, кванторы и время

Логическая композиция представлена отдельными `g`-узлами с зарегистрированной машинной семантикой.

В архитектуре предусмотрены:

```text
AND
OR
XOR
NOT
IMPLIES
FORALL
EXISTS
POSSIBLE
NECESSARY
COUNTERFACTUAL
BEFORE
AFTER
DURING
ASSOCIATION
```

Для каждого оператора `FunctionRegistry` задаёт допустимую сигнатуру, каноническое представление и разрешённые правила вывода.

### Кванторы

Квантор хранит связанную переменную, restriction и body. Область действия является частью структуры, поэтому:

```text
EVERY(x, R, B)
```

не сводится к строковому маркеру «каждый».

Инстанциация универсального утверждения выполняется по конкретной цели и только при наличии необходимых живых premise-supports. Производный факт получает собственный путь доказательства.

### Open-world семантика

Отсутствие записи не считается отрицательным свидетельством.

Если для вывода недостаточно оснований, результат остаётся неизвестным. Для утверждений, которым нужна полнота области — например, точного количества объектов, — требуется явно объявленная замкнутая область.

### Время

Временное содержание хранится отдельно от текстовой метки события.

`TemporalLedger` связывает временное свидетельство с конкретной `SupportRecord`. Поэтому два независимых утверждения одного и того же события могут иметь разные временные основания, а отзыв одного пути не обязан уничтожать другой.

## Версии, опоры и отзыв

AG Memory не должна исправлять прошлое переписыванием старого факта.

Для этого используются:

```text
observation_id
interpretation_version
SupportRecord
IdentityBinding
UsageLink
NodeLifecycleEvent
```

Один и тот же фрагмент источника имеет устойчивый `observation_id`. Изменение текста, контекста или используемого ресурсного снимка создаёт новую версию интерпретации.

Факт может иметь несколько независимых `SupportRecord`:

```text
N_X
├── support from O1
├── support from O2
└── derived support from rule R
```

Отзыв наблюдения переводит именно зависимые от него опоры в неактивное состояние. Канонический узел не удаляется физически и может оставаться доступным через другой живой путь.

Если последний путь исчезает, узел становится недоступным. Если позднее появляется новая независимая опора, тот же канонический узел может снова стать доступным — без уничтожения истории его предыдущего состояния.

## Ассоциативная активация и Workspace

После записи память работает не только как хранилище.

У элементов есть текущий уровень возбуждения `x`. Входной стимул активирует связанные структуры, после чего Ignition Engine распространяет возбуждение по графу.

```text
seed
  ↓
activation propagation
  ↓
x(node)
  ↓
Workspace = релевантный активный подграф
```

Workspace определяет, какая часть памяти сейчас попадает в фокус агента.

Важно:

```text
activation ≠ truth
association ≠ entailment
recall ≠ inference
```

Ассоциативная динамика отвечает за доступность и релевантность, а символический контур — за допустимость вывода.

## Быстрый старт

### Требования

- Python `>= 3.12`
- `uv`
- локальный LLM backend: Ollama, LM Studio или встроенный Hugging Face/PyTorch worker

### Установка

```bash
git clone --branch temp https://github.com/MaxSquizie/AG_Memory.git
cd AG_Memory

uv venv
```

Активация окружения:

```bash
# Windows
.venv\Scripts\activate

# Linux / macOS
source .venv/bin/activate
```

Для GUI с внешним backend:

```bash
uv pip install -e ".[gui]"
```

Для встроенного Hugging Face/PyTorch worker:

```bash
uv pip install -e ".[gui,llm]"
```

### Рекомендуемый первый запуск: Ollama

```bash
ollama serve
ollama pull qwen2.5:7b
```

Запуск V7-контура:

```powershell
# Windows PowerShell
$env:AH_FORMALIZER="1"
ah-gui --config config/ollama.toml
```

```bash
# Linux / macOS
AH_FORMALIZER=1 ah-gui --config config/ollama.toml
```

Для LM Studio используется профиль:

```text
config/lmstudio.toml
```

Для встроенного worker:

```text
config/default.toml
```

В корне также есть готовые launch-скрипты для Windows и Unix-подобных систем.

## CLI и встраивание

После установки доступны две точки входа:

```text
ah-gui    графический интерфейс
ah-agent  CLI
```

Примеры:

```bash
ah-agent --config config/ollama.toml summary
ah-agent --config config/ollama.toml dump-json
ah-agent --config config/ollama.toml dump-dot
ah-agent --config config/ollama.toml import-corpus data/corpus/example.json
ah-agent --config config/ollama.toml import-text notes.txt
ah-agent --config config/ollama.toml import-memory snapshot.json
ah-agent --config config/ollama.toml reset-memory
```

Для V7-пути установите `AH_FORMALIZER=1` в окружении процесса.

### Встраивание runtime в Python

```python
from ah.config import AppConfig
from ah.bootstrap import RuntimeServices

config = AppConfig.from_toml("config/ollama.toml")
services = RuntimeServices.build(config)

result = services.agent.handle_user_text(
    "Иван передал книгу Марии."
)
```

`RuntimeServices` собирает основные подсистемы в единый runtime: память, формализацию, интеграцию, ассоциативную динамику, вывод, проекцию контекста, LLM-backend и персистентность.

## Архитектурные инварианты

Если нужно понять проект в нескольких правилах, достаточно этих:

1. **Кандидат не является фактом.** Между распознаванием текста и записью в память существует явная проверяемая граница.
2. **Модель не владеет канонической памятью.** Она предлагает локальные гипотезы, а не назначает truth или UID.
3. **Неизвестное остаётся неизвестным.** Отсутствие знания не заменяется ближайшим смыслом или отрицанием.
4. **Identity отделена от имени.** Сущность определяется канонической структурой и доказанными связями.
5. **Логика хранится как структура.** Scope, кванторы, модальность и отрицание не сводятся к текстовым тегам.
6. **Каждый факт имеет путь поддержки.** Вывод можно проследить до наблюдения, контекста, фонового знания или производного правила.
7. **Отзыв не стирает историю.** Умирает конкретная опора; канонический объект сохраняется и может оставаться доступным через другие пути.
8. **Активация не равна истинности.** Ignition определяет релевантность, symbolic inference — допустимый вывод.
9. **Запись атомарна.** Канонические изменения проходят через контролируемый writer и журнал.
10. **Расширение языка безопасно.** Новый предикат можно представить, не притворяясь, что его смысл уже известен.

AG Memory строится вокруг идеи, что долговременная память агента должна быть одновременно **структурной, объяснимой, ассоциативной, версионной и пригодной для формального рассуждения**.
