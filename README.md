# AG Memory

**Ассоциативно-гетерархическая долговременная память для агентов на основе больших языковых моделей.**

AG Memory — это архитектура и рабочее ядро когнитивной памяти, в которой языковой опыт превращается в **типизированную семантическую структуру**, связывается с уже известными сущностями и событиями, получает явные основания и затем участвует в ассоциативном вспоминании и символическом выводе.

Проект ориентирован на текстового агента и локальную среду выполнения. Формализатор принимает русский текст, строит проверяемое представление смысла и отделяет **интерпретацию** от **утверждения факта**. Внутри формализатора модель-парсер может предложить локальную гипотезу, но не может сама назначить каноническую идентичность, объявить содержание истинным или записать его в память.

## Идея проекта

АГ-память рассматривается как долговременное состояние агента, а не как архив сообщений.

Она должна уметь одновременно:

- сохранять новый опыт;
- поддерживать устойчивые идентичности сущностей;
- представлять события и отношения через роли;
- хранить отрицание, дизъюнкцию, импликацию, модальность и кванторы как структуру;
- учитывать время и область действия утверждений;
- сохранять несколько независимых оснований одного и того же содержания;
- отзывать устаревшую опору без уничтожения истории;
- распространять активацию по ассоциациям;
- формировать текущий фокус внимания;
- строить символические выводы с отслеживаемым происхождением;
- передавать только релевантную часть памяти в контекст языковой модели агента.

Два механизма принципиально разделены:

```text
Вспоминание = что сейчас релевантно?
Вывод       = что следует из уже формализованных знаний?
```

Высокая активация делает узел заметным для агента, но не делает его истинным. Истинность и доступность факта определяются его структурой и живыми путями поддержки.

## Модель памяти

Внутреннее состояние описывается как:

```text
AH = <S, C, P, H, L>
```

| Компонент | Назначение |
|---|---|
| `S` | устойчивые языковые символы и распознаваемые словоформы |
| `C` | канонические знания и устойчивые семантические структуры |
| `P` | пропозициональный контур рассуждений и производных результатов |
| `H` | пережитый опыт: диалог, события, эпизоды, собственная история агента |
| `L` | типизированные направленные связи между элементами памяти |

Внутри семантических доменов используется несколько базовых типов:

| Тип | Смысл |
|---|---|
| `s` | языковой символ: лексическая единица и её формы |
| `m` | самостоятельно адресуемая сущность или понятие |
| `T` | шаблон предиката: какие роли допускает отношение |
| `N` | конкретная реализация предиката — пропозиция или событие |
| `g` | функциональная конструкция с машинной семантикой |
| `k` | адресуемая группировка, эпизод или набор альтернатив |
| `L` | направленная типизированная ассоциация |

## Как выглядит один факт

Пусть агент получает:

```text
Иван передал книгу Марии.
```

Упрощённое представление может выглядеть так:

```text
m_IVAN
m_BOOK
m_MARIA

T_TRANSFER
├── SUBJECT
├── OBJECT
└── RECIPIENT

N_TRANSFER
├── T*        → T_TRANSFER
├── SUBJECT  → m_IVAN
├── OBJECT   → m_BOOK
└── RECIPIENT→ m_MARIA
```

`T` описывает **тип ситуации**, а `N` — **конкретное произошедшее**.

Если содержание имеет логическую форму, над пропозициями строится `g`:

```text
Иван не пришёл.

g_NOT
└── N_ARRIVE
    └── SUBJECT → m_IVAN
```

Поэтому логика хранится не как приписка к строке текста, а как часть канонической структуры.

## Когнитивный цикл

Высокоуровневый поток одного хода агента:

```text
внешний текст
    ↓
формализация и разрешение смысла
    ↓
атомарная запись подтверждённой структуры в AH
    ↓
начальная / повторная активация
    ↓
распространение активации по графу
    ↓
рабочее пространство: текущий активный подграф
    ↓
вспоминание + символический вывод
    ↓
детерминированное построение контекста агента
    ↓
агентская LLM
    ↓
ответ / решение / действие
    ↓
запись пережитого опыта в H
```

Каноническая память и состояние среды выполнения разделены: возбуждение, текущее рабочее пространство и временный контекст могут пересчитываться, не меняя сам факт.

Здесь важно различать две роли языковой модели. **LLM-парсер** участвует в восприятии и формализации входного текста. **Агентская LLM** работает позже: получает уже собранный контекст агента и формирует ответ, решение или действие. Физически эти роли может обслуживать одна и та же модель, но архитектурно это разные компоненты с разными входами и полномочиями.

## Формализатор V7

Формализатор — граница между естественным языком и канонической памятью.

Его задача — не «угадать наиболее похожий смысл», а построить типизированные кандидаты, проверить их основания, сохранить неоднозначность там, где она действительно есть, и допустить запись только после прохождения явных контрактов.

Полный нормативный путь:

```text
RawInput
  → T0
  → SRL
  → T1
  → TD
  → T2
  → TP
  → structural_seal
  → T3
  → T4
  → assemble_candidate_ir
  → C
  → T5
  → T6

T6b → новая версия интерпретации / отзыв опор
```

Имена стадий и типов в этом блоке сохранены в том виде, в котором они существуют в коде и нормативной архитектуре.

### Стадии по смыслу

| Контур | Что происходит |
|---|---|
| `T0` | вход проверяется, исходные символы и диапазоны фиксируются без потерь |
| `SRL → T1 → TD` | строятся лексические, морфологические и синтаксические кандидаты, кандидаты кореференции и области действия |
| `T2` | формируются предикативные рамки и типизированные аргументы |
| `TP` | при структурном разрыве допускается ограниченная локальная гипотеза |
| `structural_seal` | структура версии фиксируется и больше не может незаметно измениться |
| `T3` | разрешаются значения уже существующих структурных позиций |
| `T4` | совместимые кандидаты собираются в обоснованное решение либо явную неопределённость |
| `assemble_candidate_ir` | создаётся неизменяемое промежуточное представление `FormalizerCandidateIR` |
| `C` | устанавливается каноническая идентичность, устраняются дубликаты и строится план привязки |
| `T5` | план и решения фиксируются в устойчивом журнале |
| `T6` | допустимый план атомарно применяется к AH |
| `T6b` | изменение контекста, ресурса или наблюдения создаёт новую версию и отзывает устаревшие опоры |

### Роль LLM-парсера

В этом разделе речь идёт именно о **LLM-парсере внутри формализатора**, а не об агентской LLM.

LLM-парсер помогает разобрать естественный язык в тех местах, где одних детерминированных правил и ресурсов недостаточно. Его результат всегда остаётся локальным предложением для последующей проверки. Даже если для разбора текста и генерации ответа используется одна физическая модель, эти вызовы относятся к разным архитектурным ролям и не смешиваются.

LLM-парсер может:

- предложить локальную структурную гипотезу;
- выбрать один из явно разрешённых идентификаторов;
- помочь разрешить локальную неоднозначность;
- использовать только объявленный контекст;
- возвращать результат через контролируемый и журналируемый вызов.

LLM-парсер не может:

- назначать канонические UID;
- создавать неизвестный машинный оператор;
- объявлять содержание истинным;
- писать напрямую в AH;
- неявно объединять новый смысл с существующим;
- обходить типы ролей, валентность и границу `structural_seal`.

Агентская LLM находится за пределами этого контура: она получает подготовленный контекст агента и формирует ответ. Её ответ, если он должен стать частью памяти, проходит собственный путь интеграции и не получает права непосредственной записи в каноническую память только потому, что был сгенерирован моделью.

## Основания и граница истины

Каждое решение хранит происхождение и типизированные основания.

Они разделены на два класса.

### Основания факта

Эти основания могут поддерживать утверждённый факт:

| Тип | Источник |
|---|---|
| `O` | само утверждающее наблюдение и соответствующий диапазон исходного текста |
| `C` | явно переданное контекстное утверждение |
| `W` | версионированное фоновое знание с собственным происхождением |

### Основания интерпретации

Они объясняют, **почему структура была распознана именно так**, но не делают содержание истинным:

| Тип | Источник |
|---|---|
| `R` | морфология, валентность, словарь смыслов и другие ресурсы |
| `D` | сработавшее проверяемое правило |
| `M` | проверенное предложение LLM-парсера |
| `A` | явно объявленная внешняя гипотеза |
| `P` | предшествующее наблюдение, используемое для разрешения ссылки |

```text
R / D / M / A / P
не являются самостоятельным подтверждением факта.

Материализация утверждённого содержания
требует O / C / W.
```

Поэтому удачная интерпретация и истинность утверждения — разные вещи.

## Новая лексика без угадывания

Словарь не считается закрытым.

Если структура предложения понятна, но для предиката нет подтверждённого канонического смысла, формализатор может сохранить **открытый предикат, локальный для конкретного употребления**:

```text
новая лексема
    ↓
OpenPredicateCandidate
    ↓
проверенные роли и диапазоны исходного текста
    ↓
изолированный T
semantic_status = UNLINKED
```

Такой `T` позволяет помнить само утверждённое содержание, но не получает чужую семантику «по похожести».

Пока связь с известным смыслом не подтверждена:

- не выполняются правила вывода, требующие известного канонического смысла;
- не создаётся скрытая синонимия;
- не происходит неявного отождествления между разными источниками;
- последующее связывание выполняется явно и версионно.

Это позволяет расширять язык памяти без обработчика под каждую новую фразу и без тихой подмены смысла.

## Логика, кванторы и время

Логическая композиция представлена отдельными `g`-узлами с зарегистрированной машинной семантикой.

В архитектуре предусмотрены:

```text
AND
OR
XOR
NOT
IMPLIES
FORALL
EXISTS
POSSIBLE
NECESSARY
COUNTERFACTUAL
BEFORE
AFTER
DURING
ASSOCIATION
```

Это машинные идентификаторы операторов, поэтому в документации они сохраняются без перевода. Для каждого оператора `FunctionRegistry` задаёт допустимую сигнатуру, каноническое представление и разрешённые правила вывода.

### Кванторы

Квантор хранит связанную переменную, ограничение и тело выражения. Область действия является частью структуры, поэтому:

```text
EVERY(x, R, B)
```

не сводится к строковому маркеру «каждый».

Подстановка в универсальное утверждение выполняется по конкретной цели и только при наличии необходимых живых опор посылок. Производный факт получает собственный путь доказательства.

### Семантика открытого мира

Отсутствие записи не считается отрицательным свидетельством.

Если для вывода недостаточно оснований, результат остаётся неизвестным. Для утверждений, которым нужна полнота области — например, точного количества объектов, — требуется явно объявленная замкнутая область.

### Время

Временное содержание хранится отдельно от текстовой метки события.

`TemporalLedger` связывает временное свидетельство с конкретной записью поддержки `SupportRecord`. Поэтому два независимых утверждения одного и того же события могут иметь разные временные основания, а отзыв одного пути не обязан уничтожать другой.

## Версии, опоры и отзыв

AG Memory не должна исправлять прошлое переписыванием старого факта.

Для этого используются:

```text
observation_id
interpretation_version
SupportRecord
IdentityBinding
UsageLink
NodeLifecycleEvent
```

Это реальные имена структур и полей архитектуры, поэтому они сохранены в исходном виде.

Один и тот же фрагмент источника имеет устойчивый `observation_id`. Изменение текста, контекста или используемого снимка ресурсов создаёт новую версию интерпретации.

Факт может иметь несколько независимых записей поддержки `SupportRecord`:

```text
N_X
├── опора O1
├── опора O2
└── производная опора по правилу R
```

Отзыв наблюдения переводит именно зависимые от него опоры в неактивное состояние. Канонический узел не удаляется физически и может оставаться доступным через другой живой путь.

Если последний путь исчезает, узел становится недоступным. Если позднее появляется новая независимая опора, тот же канонический узел может снова стать доступным — без уничтожения истории его предыдущего состояния.

## Ассоциативная активация и рабочее пространство

После записи память работает не только как хранилище.

У элементов есть текущий уровень возбуждения `x`. Входной стимул активирует связанные структуры, после чего механизм активации распространяет возбуждение по графу.

```text
начальная активация
  ↓
распространение возбуждения
  ↓
x(узел)
  ↓
рабочее пространство = релевантный активный подграф
```

Рабочее пространство определяет, какая часть памяти сейчас попадает в фокус агента.

Важно различать:

```text
активация ≠ истинность
ассоциация ≠ логическое следование
вспоминание ≠ вывод
```

Ассоциативная динамика отвечает за доступность и релевантность, а символический контур — за допустимость вывода.

## Быстрый запуск

### Требования

- Python `>= 3.12`
- `uv`
- локальная среда доступа к языковой модели: Ollama, LM Studio или встроенный процесс Hugging Face/PyTorch

### Установка

```bash
git clone --branch temp https://github.com/MaxSquizie/AG_Memory.git
cd AG_Memory

uv venv
```

Активация окружения:

```bash
# Windows
.venv\Scripts\activate

# Linux / macOS
source .venv/bin/activate
```

Для графического интерфейса с внешней средой модели:

```bash
uv pip install -e ".[gui]"
```

Для встроенного процесса Hugging Face/PyTorch:

```bash
uv pip install -e ".[gui,llm]"
```

### Рекомендуемый первый запуск: Ollama

```bash
ollama serve
ollama pull qwen2.5:7b
```

Запуск контура V7:

```powershell
# Windows PowerShell
$env:AH_FORMALIZER="1"
ah-gui --config config/ollama.toml
```

```bash
# Linux / macOS
AH_FORMALIZER=1 ah-gui --config config/ollama.toml
```

Для LM Studio используется профиль:

```text
config/lmstudio.toml
```

Для встроенного процесса:

```text
config/default.toml
```

В корне также есть готовые скрипты запуска для Windows и Unix-подобных систем.

## Командная строка и встраивание

После установки доступны две точки входа:

```text
ah-gui    графический интерфейс
ah-agent  интерфейс командной строки
```

Примеры:

```bash
ah-agent --config config/ollama.toml summary
ah-agent --config config/ollama.toml dump-json
ah-agent --config config/ollama.toml dump-dot
ah-agent --config config/ollama.toml import-corpus data/corpus/example.json
ah-agent --config config/ollama.toml import-text notes.txt
ah-agent --config config/ollama.toml import-memory snapshot.json
ah-agent --config config/ollama.toml reset-memory
```

Для пути V7 установите `AH_FORMALIZER=1` в окружении процесса.

### Встраивание среды выполнения в Python

```python
from ah.config import AppConfig
from ah.bootstrap import RuntimeServices

config = AppConfig.from_toml("config/ollama.toml")
services = RuntimeServices.build(config)

result = services.agent.handle_user_text(
    "Иван передал книгу Марии."
)
```

`RuntimeServices` собирает основные подсистемы в единую среду выполнения: память, формализацию, интеграцию, ассоциативную динамику, вывод, построение контекста, доступ к языковой модели и долговременное сохранение состояния.
