# AG Memory

**Ассоциативно-гетерархическая долговременная память для языковых агентов.**

AG Memory хранит типизированные сущности, отношения, события, логические конструкции и основания утверждений. Формализатор преобразует естественный язык в кандидаты структуры; каноническая память связывает их с существующими элементами; механизм активации выбирает актуальный фрагмент для агента.

В этом README **одно предложение проходит полный путь от входной строки до гиперграфа**. Показаны структуры данных на границах стадий, условия записи и работа памяти после сохранения.

**Пример условный.** Промежуточные структуры иллюстрируют нормативный контракт V7, а не результат конкретного запуска. Для полного канонического пути необходимы совместимые утверждённые ресурсы и действующие отображения на шаблоны памяти.

## Исходное предложение

> Вчера диспетчер Ирина не разрешила роботу Кай-7 открыть повреждённый шлюз станции «Орион».

В предложении присутствуют:

- **два предикативных центра:** «разрешила» и «открыть»;
- **отрицание:** «не» относится к разрешению;
- **несколько участников:** Ирина, Кай-7 и шлюз;
- **атрибут:** «повреждённый»;
- **вложенная структура:** открытие шлюза является содержанием разрешения;
- **относительное время:** «вчера» требует временного якоря.

Ожидаемая семантическая основа: **отрицается факт предоставления разрешения**. Из предложения не следует, что шлюз был открыт, что робот пытался его открыть или что Ирина прямо запретила открытие.

Для определённости зададим дату сообщения и известный языковой контекст. Сами сущности могут существовать в памяти заранее; совпадение имён ещё требует канонической привязки.

~~~json
{
  "source_id": "station-log:042",
  "source_revision": 1,
  "text": "Вчера диспетчер Ирина не разрешила роботу Кай-7 открыть повреждённый шлюз станции «Орион».",
  "language": "ru",
  "source_timestamp": "2026-10-09T12:00:00+03:00",
  "batch_kind": "MESSAGE",
  "request_kind": "ASSERTION"
}
~~~

Перед началом обработки фиксируется `ResourceSnapshot` — версии морфологических, синтаксических, семантических ресурсов и политик. Запуск одной версии наблюдения привязан к конкретным входным данным и журналируемым обращениям к модели.

## Разбор исходного предложения

### T0 — фиксация символов и токенов

**Вход:** `RawInput`. **Выход:** `TokenSpan[]` и `SentenceUnit[]`.

T0 сохраняет исходную строку без исправлений. Каждый символ учитывается как часть токена, пунктуации или пробельного диапазона. Границы указываются как `[начало, конец)` в исходной строке.

| Фрагмент | Диапазон | Назначение |
|---|---|---|
| `Вчера` | `[0, 5)` | временное выражение |
| `не` | `[22, 24)` | возможный показатель отрицания |
| `разрешила` | `[25, 34)` | конечный глагол |
| `Кай-7` | `[42, 47)` | фрагмент имени; токенизация дефиса зависит от правил |
| `открыть` | `[48, 55)` | инфинитив |
| `шлюз` | `[69, 73)` | существительное |
| `«Орион»` | `[82, 89)` | фрагмент наименования с кавычками |

Остальные фрагменты и пробелы также сохраняются. Диапазоны из таблицы обозначают участки исходной строки; один участок не обязан соответствовать ровно одному внутреннему токену.

**Результат:** неизменяемая привязка последующих кандидатов к символам наблюдения. На T0 ещё нет сущностей памяти и утверждённых отношений.

### SRL — лексические и структурные гипотезы

**Вход:** токены T0, гипотезы R1 и объявленные синтаксические правила. **Выход:** `TokenHypothesis`, `BoundaryCandidate`, `ClauseCandidate`, при необходимости `EllipsisCandidate`.

На этом этапе:

- сохраняются исходные формы через `KEEP_AS_IS`;
- предлагаются варианты лексического разбора;
- определяются возможные границы частей предложения;
- отдельно учитываются конечный глагол «разрешила» и инфинитив «открыть».

Например, `Кай-7` не исправляется автоматически на знакомое слово. Неизвестная форма может остаться именем-кандидатом без готового словарного значения.

**Результат:** множество структурных вариантов, ещё не распределённых по каноническим объектам.

### T1 — морфология и упоминания

**Вход:** кандидаты SRL и морфологический ресурс R1. **Выход:** `MentionCandidate`, `SurfaceOperatorCandidate`, `LexDecision`.

| Форма | Возможные признаки, существенные для примера |
|---|---|
| `диспетчер` | существительное, именительный падеж |
| `Ирина` | имя, именительный падеж, женский род |
| `разрешила` | лемма «разрешить»; прошедшее время, ед. число, женский род |
| `роботу` | лемма «робот»; дательный падеж |
| `открыть` | инфинитив |
| `повреждённый` | согласуемый признак существительного |
| `шлюз` | существительное; возможны совпадающие формы именительного и винительного падежей |
| `станции` | существительное; возможен родительный падеж |
| `не` | кандидат оператора `NOT` |
| `вчера` | кандидат относительного временного выражения |

Морфологические варианты не объединяются в произвольную «среднюю» форму. Для неоднозначного падежа или присоединения сохраняются отдельные кандидаты.

**Результат:** описания упоминаний с леммами, грамматическими признаками и исходными диапазонами.

![Диапазоны входной строки, морфологические варианты и начало структурного связывания](docs/assets/formalization-roles.svg)

### TD — зависимости, ссылки и область действия

**Вход:** упоминания и операторы T1. **Выход:** `DependencyCandidate`, `ReferenceCandidate`, `ScopeTreeCandidate`.

Для нашего предложения проверяются связи:

~~~text
разрешила
├── кто?        → диспетчер Ирина
├── кому?       → роботу Кай-7
└── содержание  → открыть
                   ├── кто?   → Кай-7  [кандидат управления]
                   └── что?   → повреждённый шлюз
                                 └── чей? → станции «Орион»
~~~

Привязка исполнителя инфинитива к Кай-7 требует допустимого правила управления или собственного основания. При конкурирующих вариантах они остаются отдельными `LinkedAlternative`.

Отдельно строится дерево области действия:

~~~text
NOT
└── разрешить
    └── открыть
~~~

Отрицание относится к предикату разрешения. Оно не утверждает `NOT(открыть)`.

Уточнения ссылок могут использовать объявленное окно предшествующего контекста с политикой `CorefPolicy`. В этом предложении нет местоимения, которое требовало бы обязательной кореференции; сопоставление имён с уже существующими сущностями окончательно выполняется позднее.

**Результат:** граф зависимостей и кандидаты области действия. Они всё ещё локальны для наблюдения.

### T2 — предикативные рамки и валентности

**Вход:** структуры TD, ресурс валентностей `R-V`, синтаксические правила. **Выход:** `PredicateAnchor`, `FrameCandidate`, `MissingArgumentCandidate`.

Т2 связывает грамматические аргументы с разрешёнными ролями предиката. Упрощённая структура:

~~~text
Frame A: разрешить
  SUBJECT        = Ирина
  RECIPIENT      = Кай-7
  PROPOSITION    = Frame B

Frame B: открыть
  AGENT          = Кай-7         [если управление подтверждено]
  OBJECT         = шлюз

ATTRIBUTE(шлюз) = повреждённый
ENTITY_CONTEXT   = станция «Орион»
SCOPE             = NOT(Frame A)
TIME_EXPR         = вчера
~~~

Названия ролей в этом блоке демонстрационные; реальные допустимые роли и типы определяются `RoleRegistry` и валентностями. Для инфинитивного дополнения общий путь может потребовать структурной гипотезы `TP`. Отсутствие записи валентности фиксируется как неизвестное ограничение, а не как разрешение любой роли.

**Результат:** рамки с типизированными аргументами, неполными позициями и связями с областью действия.

### TP → structural_seal — закрытие структуры

`TP` применяется при непокрытых диапазонах, отсутствующей связи между предикатами или неразрешённой области действия. Он допускает ограниченное предложение **LLM-парсера** либо другой локальный структурный вариант.

Для примера возможна гипотеза: инфинитив «открыть» — содержательный аргумент «разрешить»; его исполнитель — получатель разрешения Кай-7. Валидатор проверяет исходные диапазоны, допустимые типы узлов, роли, ограничения и происхождение каждой связи.

Если подтверждения связи нет, структура остаётся неоднозначной или неполной. **TP не вправе назначить канонические UID и записать факт.**

`structural_seal` фиксирует граф рамок, упоминаний, зависимостей и операторов для текущей версии. После него T3 и T4 **не добавляют новых структурных рёбер**.

**Результат:** зафиксированная структура, в которой остаётся определить смысловые значения.

## Разрешение значений и неоднозначности

### T3 — выбор семантических значений

**Вход:** запечатанные рамки, `R-S`, `PredicateSchema`, политики ресурсов, объявленный контекст. **Выход:** кандидаты смыслов, предварительные решения и `CandidateSourceTrace`.

Для каждого смыслового слота T3 проверяет пять источников:

| Источник | Назначение |
|---|---|
| `1` | значения схемы предиката и объявленные расширения |
| `2` | словарь смыслов `R-S` |
| `3` | совместимые сохранённые варианты `R-X3` |
| `4` | объявленные контекстные и фоновые утверждения `C/W` |
| `5` | локальный открытый смысл `OPEN_LEXICAL`, когда известного не найдено |

Для «разрешить» и «открыть» должны быть подтверждены конкретные смысловые значения и их роли. Для нового слова может использоваться `OpenPredicateCandidate` со статусом `UNLINKED`. Такой предикат изолирован от неподтверждённых синонимий и правил вывода.

Каждый источник получает состояние `FOUND`, `CHECKED_EMPTY`, `NOT_APPLICABLE` или `BLOCKED`. Отсутствие записи в корректном словаре отличается от недоступности самого словаря.

**Результат:** значения, привязанные к уже существующим рамкам, с проверяемым происхождением каждого кандидата.

### T4 — согласование всех кандидатов

**Вход:** смысловые кандидаты T3 и ограничения T0–TP. **Выход:** итоговое решение и причины отклонения альтернатив.

T4 исключает несовместимые сочетания морфологии, валентностей, ролей, областей действия и смысловых значений. Затем проверяет оставшиеся совместимые комбинации.

| Исход | Значение |
|---|---|
| `RESOLVED` | установлен допустимый вариант с необходимыми основаниями |
| `AMBIGUOUS` | остаются несколько обоснованных вариантов |
| `INSUFFICIENT_CONTEXT` | не хватает объявленного контекста |
| `NO_CANDIDATE` | полный допустимый поиск не дал варианта |
| `UNRESOLVED` | решение не получено; причина сохраняется |

Для продолжения нашего примера предполагаем `RESOLVED`: структурные связи и смысловые значения подтверждены ресурсами. Это условие примера, не гарантированный исход для любого окружения.

**Результат:** согласованное локальное смысловое представление.

### assemble_candidate_ir — граница формализации

Все решения собираются в неизменяемый `FormalizerCandidateIR`:

~~~text
observation_id
interpretation_version
raw_spans
structural_candidates
semantic_graph_candidates
decision_ids
constraint_edges
coverage_status
grounds + provenance
diagnostics
~~~

В нём хранятся и выбранные варианты, и информация об отклонённых либо неполных участках. Привязка к канонической памяти ещё не выполнена.

## Каноническая привязка и запись

### C — сопоставление с АГ-памятью

`C` читает `FormalizerCandidateIR` и текущий снимок АГ-памяти. Он определяет:

1. Существуют ли уже сущности «Ирина», «Кай-7», «шлюз», «Орион» и какие привязки подтверждены.
2. Каким каноническим шаблонам `T` соответствуют выбранные предикаты.
3. Какие отношения и структуры уже присутствуют; какие требуется создать.
4. Какие узлы служат утверждённым корнем, а какие — его структурными операндами.

В примере ожидаемая **логическая форма содержания**:

~~~text
G_NOT(
    N_PERMISSION(
        subject = M_Ирина,
        recipient = M_Кай-7,
        content = N_OPEN(
            agent = M_Кай-7,
            object = M_шлюз
        )
    )
)
~~~

Обозначения `N_PERMISSION` и `N_OPEN` здесь условные метки для чтения схемы; реальные идентификаторы назначаются каноническими механизмами. Признак «повреждённый», принадлежность станции и временная привязка входят в соответствующие типизированные связи и данные наблюдения.

**C формирует план изменений и не пишет в AH.** Для известного смысла требуется действительная запись `TemplateMap`. Если она отсутствует, нельзя заменить её произвольным «похожим» шаблоном.

### T5 — журнал и допуск записи

`T5` получает план C и проверяет завершённость решений, актуальность объявленных данных, целостность структуры и основания утверждаемого содержания.

Основания имеют разные права:

- **`O / C / W`** — поддержка утверждения: исходное наблюдение, явно заданный контекст, фоновое знание;
- **`R / D / M / A / P`** — поддержка интерпретации: ресурс, правило, проверенное предложение парсера, гипотеза, предшествующее наблюдение.

Результат `RESOLVED` ещё не означает, что запись совершена. T5 фиксирует допустимый пакет и решение в устойчивом журнале. Неопределённые или незавершённые участки не превращаются в утверждённые факты.

### T6 — атомарная запись гиперграфа

**T6 — единственный писатель утверждённых канонических фактов.** Из допущенного плана создаются или используются:

- языковые символы `S` и сущности `M`;
- шаблоны отношений `T` и конкретные конструкции `N`;
- функциональный узел `G(NOT, P)`;
- связи аргументов, операторов и вложенного содержания;
- `SupportRecord`, при необходимости `IdentityBinding`, а также журналируемый маркер записи.

Для нашего предложения существенно разделение видимости:

| Элемент | Статус после записи |
|---|---|
| `G(NOT, N_PERMISSION)` | утверждён; получает прямую опору `O` |
| `N_PERMISSION` | структурный операнд отрицания; сам по себе не утверждён |
| `N_OPEN` | вложенное содержание; факт открытия не утверждён |
| `M_Ирина`, `M_Кай-7`, `M_шлюз` | канонические сущности или проверенные привязки |
| «вчера» | относительное выражение; при заданном временном якоре соответствует 8 октября 2026 года |

Связь операнда с родительской структурой создаётся через предусмотренный механизм `UsageLink`. Структурная доступность вложенного узла не даёт ему фактической поддержки. Коммит узлов, оснований и маркера выполняется атомарно.

## Гиперграф и активация

После записи АГ-память содержит связанный гиперграф. Новые `G/N`-структуры соединены с `M`-сущностями. Если «Кай-7» или «Орион» уже были представлены в памяти, новые конструкции используют проверенные канонические привязки. При неизвестной идентичности решение принимается по правилам C.

При обращении к памяти:

1. Из запроса образуются начальные очаги активации.
2. Возбуждение распространяется по типизированным ассоциативным связям.
3. У узлов изменяется текущий уровень возбуждения.
4. Формируется **рабочее пространство** — актуальный фрагмент графа.
5. Вспоминание предоставляет релевантные структуры; символический вывод отдельно проверяет допустимость заключений.
6. Подготовленный контекст передаётся **агентской LLM** для ответа.

Активация влияет на доступность и внимание. **Она не меняет истинность узлов и не заменяет проверку опор.** Вложенный `N_OPEN` может быть активен как часть связи с запросом, оставаясь неутверждённым действием.

![Гиперграф АГ-памяти: существующие и новые узлы, уровни возбуждения и распространение импульса](docs/assets/hypergraph-activation.svg)

*Схема показывает относительную активацию, структуру связей и включение нового фрагмента в память. Она не отображает численные значения реального запуска.*

## GOAL-запросы

Запросы выполняются **после** записи соответствующих знаний. Исполнение цели не является стадией T0–T6.

Например:

> Ирина вчера разрешила Кай-7 открыть повреждённый шлюз станции «Орион»?

1. Формализатор обрабатывает вопрос с `request_kind=QUERY`.
2. `GoalCompiler` создаёт цель проверки утверждения `P = PERMISSION(...)`.
3. Механизм вывода ищет доступные основания `P` и `NOT(P)` с подходящей областью действия.
4. При наличии сохранённой прямой опоры отрицания выводится **«Нет»** с указанием наблюдения-источника.

Другой запрос:

> Кай-7 открыл шлюз?

Результат — **«Неизвестно»**, если иных оснований нет. Вложенный `N_OPEN` не является свидетельством совершённого открытия.

GOAL работает с уже подготовленным состоянием памяти и собственными правилами доказательства. Запрос сам по себе не записывается как утверждение о мире. Запись производного результата, если она допустима, проходит отдельную границу исполнения целей.

## Пересмотр и отзыв — T6b

Если источник `station-log:042` исправляет сообщение, создаётся новая ревизия входа и версия интерпретации. `T6b` адресно пересчитывает зависимые решения и отзывает соответствующие опоры.

Когда последняя действующая опора `G(NOT, P)` исчезает, отрицание перестаёт быть фактически видимым. Структурные узлы и история остаются в каноническом хранилище; новая независимая опора может снова сделать ту же конструкцию доступной.

Это поддерживается `SupportRecord`, событиями жизненного цикла и журналом изменений. Повтор идентичного входа не создаёт новую версию без объявленного изменения.

## Архитектура и исходный код

Нормативная последовательность формализатора:

~~~text
RawInput → T0 → SRL → T1 → TD → T2 → TP
         → structural_seal → T3 → T4
         → assemble_candidate_ir → C → T5 → T6

T6b → новая версия и пересчёт по этому пути
~~~

Контуры АГ-памяти обозначаются `AH = <S, C, P, H, L>`: языковые символы, канонические знания, пропозициональные структуры, опыт агента и типизированные связи.

Основные каталоги: `src/ah/formalizer/` — формализатор; `src/ah/core/` — память; `src/ah/ignition/` — активация; `src/ah/inference/` — вывод; `src/ah/projection/` — контекст; `src/ah/agent/` — цикл агента.

Документация:

- [Нормативная архитектура формализатора V7](docs/FORMALIZER_ARCHITECTURE_V7.md) — полные контракты стадий, ресурсов, логики, записи и отзыва.
- [Карта реализации V7](docs/IMPLEMENTATION_MAP_V7.md) — расположение компонентов в исходном коде.
- [Архитектура АГ-памяти](docs/reference/Архитектура_v3.md) — организация памяти и когнитивного цикла.
- [Настройка и эксплуатация](docs/RUN.md) — параметры окружения.

## Установка и встраивание

### Окружение

Необходимы **Python 3.12+**, `uv` и языковая модель через Ollama, LM Studio или Hugging Face/PyTorch.

~~~bash
git clone --branch temp https://github.com/MaxSquizie/AG_Memory.git
cd AG_Memory
uv venv
~~~

~~~powershell
# Windows
.venv\Scripts\activate
~~~

~~~bash
# Linux / macOS
source .venv/bin/activate
~~~

~~~bash
uv pip install -e ".[gui]"
~~~

Для встроенной модели вместо последней команды: `uv pip install -e ".[gui,llm]"`.

### Модель и ресурсы

Пример Ollama:

~~~bash
ollama pull qwen2.5:7b
ollama serve
~~~

Профили: `config/ollama.toml`, `config/lmstudio.toml`, `config/default.toml`.

**Для V7 требуется утверждённый ресурсный релиз**, внешняя проверка подписи, действительные `TemplateMap` и шаблоны `T` в снимке АГ-памяти. Эти данные должны быть подготовлены для конкретного окружения; отсутствие ресурсов блокирует запуск, а не заменяется демонстрационным словарём.

После настройки путей:

~~~bash
python -m ah.formalizer.resources.release_cli check data/formalizer_release.json --trusted-reviews data/formalizer_reviews.json --ah-snapshot data/memory.json
ah-gui --config config/ollama.toml
~~~

### Командная строка

~~~bash
ah-agent --config config/ollama.toml summary
ah-agent --config config/ollama.toml dump-json
ah-agent --config config/ollama.toml dump-dot
ah-agent --config config/ollama.toml import-text notes.txt
ah-agent --config config/ollama.toml native-sources
ah-agent --config config/ollama.toml native-clarifications
~~~

Для пересмотра предусмотрены адресные операции `retract-observation`, `retract-support`, `retract-time-assertion`, `reinterpret-observation` и операции переноса. Полные аргументы приведены в [RUN.md](docs/RUN.md). Снимок АГ-памяти и журнал `formalizer_journal.log` должны оставаться согласованными.

### Встраивание в Python

~~~python
from ah.config import AppConfig
from ah.bootstrap import RuntimeServices

config = AppConfig.from_toml("config/ollama.toml")
services = RuntimeServices.build(config)

result = services.agent.handle_user_text(
    "Вчера диспетчер Ирина не разрешила роботу Кай-7 открыть повреждённый шлюз станции «Орион»."
)
~~~

Код показывает точку вызова агента. Для прохождения описанного канонического пути требуются ресурсы и конфигурация, соответствующие контексту примера.
