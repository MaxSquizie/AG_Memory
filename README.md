# AH Agent MVP

**Ассоциативно-иерархическое (AH) ядро памяти для текстового LLM-агента.**

`ah-agent-mvp` — это не «RAG поверх векторной БД», а полноценная когнитивная память:
канонический гиперграф знаний, детерминированный символьный вывод и движок
распространения активации (spreading activation), в которые локальная LLM лишь
*подсказывает* семантику текста. Все канонические решения — кто есть кто, какие
домены, какие сущности — принимает детерминированный код, а не модель.

---

## Что это за проект

Ядро представляет память как **типизированный гиперграф** из семи классов узлов:

| Узел | Роль |
|------|------|
| `S`  | устойчивая лексическая единица / парадигма (слово, предикат) |
| `m`  | сущность-манифестация (конкретный объект/персона) |
| `g`  | логический оператор (AND/OR/NOT/EXISTS/кванторы) |
| `k`  | множество / неопределённая ссылка (`AMBIGUOUS`) |
| `T`  | типизированное утверждение-шаблон (предикат + валентность) |
| `N`  | пропозиция — конкретный факт с актантами |
| `L`  | ассоциативная связь между узлами (`IS-A`, `FOLLOW`, `CAUSE`, …) |

Каждый узел живёт в одном из трёх **доменов**:

- **C** — *canonical* (стабильные факты/знания);
- **P** — *propositional* (текущие рассуждения, выводы);
- **H** — *experiential* (пережитый опыт: диалог, события, следы внимания).

Поверх канонического хранилища лежат производные индексы (полностью
перестраиваемые из `AH`), движок активации и проекция в контекст агента.

## Для чего предназначен

- **Память для LLM-агента**, которая *помнит, рассуждает и объясняет*, а не просто
  возвращает похожие куски текста: агент получает связанный фрагмент графа знаний
  (`AgentContext`), а не топ-k отрывков.
- **Понятная семантика**: факты хранятся как пропозиции с актантами и логической
  структурой, поэтому над ними работают транзитивность `IS-A`/`FOLLOW`, модус
  причинности, кванторы (`EXISTS`/универсальные правила), временные интервалы и
  явное опровержение (`FALSE(N)`).
- **Локальный, self-hosted контур**: работает с локальными бэкендами (Ollama,
  LM Studio, HuggingFace в отдельном процессе) и имеет мост на Android NPU. Ядро
  не зависит от `torch`/`transformers`/облака.
- **Прозрачность**: весь граф виден в GPU-GUI как 2.5D/3D-сцена, есть read-only
  диагностика, DSL для запросов и полный provenance/trace каждого вывода.

## Ключевые преимущества

1. **Детерминированное ядро + ограниченная LLM.** Модель отвечает на короткие
   stateless-пробы (тип действия, прол предиката, роль актанта…), а не сериализует
   JSON/AST целиком. Канонические UID, домены и сущности модель *не* выдаёт — их
   строит код. Ошибка модели не может «записать мусор» в память: семантический
   perception имеет ровно два исхода — валидный результат или явная ошибка.
2. **Символьный вывод вместо только векторного поиска.** Над графом работают
   логические правила (транзитивность, MP-подобный вывод по `CAUSE`, кванторы,
   временные модусы). Есть бенчмарк **M4: AH vs Vanilla RAG** на документальном
   корпусе.
3. **Атомарная, управляемая память.** Copy-on-write транзакции, lifecycle
   (`NEW → REINFORCED → CONSOLIDATED`), GC, который не удаляет консолидированные и
   исторически значимые факты, явная семантическая коррекция через `FALSE(N)`.
4. **Ассоциативная динамика.** Движок Ignition считает возбуждение `x`, импульсы
   и веса связей; Workspace определяется порогом `x > t` — без второго «когнитивного
   top-k/reranker» после порога.
5. **Локальность и автономность.** Всё работает на машине пользователя: локальная
   LLM, локальное хранилище (атомарный JSON), опциональный Android NPU.
6. **Измеряемое качество.** Метрика-контур M1–M5, adversarial-корпуса и поведенческие
   инварианты фиксируют регрессии; acceptance-прогоны идут через тот же локальный
   пайплайн, что и живой агент.

## Как пользоваться

### Установка

Требуется **Python ≥ 3.12**. Базовое ядро тянет только `pymorphy3`; остальное —
опциональные extras:

```bash
# ядро + тесты
pip install -e ".[test]"

# GUI (PySide6 + VisPy) и локальная LLM (torch/transformers)
pip install -e ".[gui,llm]"

# отдельные бэкенды / возможности
pip install -e ".[llm-lora]"     # LoRA-адаптеры
pip install -e ".[llm-vision]"   # мультимодальность
```

Точка входа — две console-скрипта: `ah-agent` (CLI) и `ah-gui` (GUI).

### GUI (основной способ работы)

```bash
# Windows
run_gui.bat                 # config/default.toml
run_gui_ollama.bat         # бэкенд Ollama
run_gui_lmstudio.bat       # бэкенд LM Studio

# Linux/macOS
./run_gui.sh
# или напрямую:
ah-gui --config config/default.toml
```

GUI строит AH как GPU-сцену (цвет = домен, «жар»/размер узла = возбуждение `x`,
белая вспышка = активация, голубая обводка = Workspace), содержит диалог, полный
TOML-редактор конфига с picker'ом пути к модели и инспектор узлов. Все параметры
можно менять из GUI; поля помечены `LIVE / NEXT_TURN / RESTART_LLM / RESTART_RUNTIME`.

Путь к локальной модели задаётся **только** в конфиге:

```toml
[paths]
llm_model_dir = "C:/Models/Qwen"
```

### CLI (диагностика и загрузка данных)

```bash
ah-agent --config config/default.toml <команда>
```

| Команда | Назначение |
|---------|-----------|
| `summary` | сводка по runtime |
| `dsl "<выражение>"` | выполнить одну DSL-команду/пайплайн |
| `dump-json` / `dump-dot` | дамп канонического/runtime-графа (JSON / Graphviz) |
| `tick [n]` | вручную продвинуть Ignition на n тиков |
| `refute <uid> [--tick]` | создать/повторить `FALSE(N)` и запланировать опровержение |
| `import-corpus <path>` | холодная загрузка структурированного JSON/.ahm/.prj в AH |
| `import-text <path>` | загрузить сырой текст как опыт USER (по умолчанию строгий семантический парсинг) |
| `import-dialogue <path>` | загрузить диалог `ah_dialogue_v1` |
| `import-memory <path>` | заменить живой AH снапшотом персистентности |
| `reset-memory` | очистить AH/runtime/context и заново создать SELF/USER |
| `semantic-acceptance`, `quantifier-acceptance`, `temporal-mode-acceptance` | acceptance-прогоны через локальный пайплайн |
| `m1-score <run_dir>`, `m2/m3/m4-acceptance`, `tick-benchmark` | метрики M1–M5 и бенчмарки |

Пример DSL:

```bash
ah-agent dsl "findRoles role=LOCATION value=@M_1 domain=H | findLists domain=H | where meta.TYPE=Episode"
```

### Конфигурация

Главный файл — `config/default.toml`; рядом лежат готовые пресеты под бэкенды:
`ollama.toml`, `lmstudio.toml`, `android.toml`. Конфиг управляет: путями и
параметрами LLM, начальными весами интеграции, функциями активации `f/g/h/t/ν`,
сильой семантических/сенсорных seed'ов, lifecycle/GC, глубиной и бюджетом вывода,
порогом Workspace, бюджетом AgentContext, политикой персистентности, identity
агента/пользователя и числом тиков оркестратора.

## Архитектура (обзор)

Полный когнитивный turn-цикл:

```text
внешний текст
→ Text Sensory (распознавание S, сенсорные seed'ы — без семантики)
→ LLM Perception (последовательность коротких stateless-проб)
→ Deterministic Integration (валидация, разрешение T/актантов/деиксиса, C/P/H routing)
→ атомарный commit в AH + локальный dedup
→ Ignition ticks (распространение активации)
→ Workspace = узлы с x > t
→ Symbolic Inference (транзитивность, кванторы, вывод)
→ опциональная материализация вывода (C < P < H)
→ проекция ACTIVE/DEPENDENCY → AgentContext
→ ответ LLM-агента
→ интеграция ответа (H-only путь) + FOLLOW/episodic history
→ персистентность
```

Подсистемы (подробности — в `docs/IMPLEMENTATION_MAP.md` и `docs/reference/Архитектура_v3.md`):

1. **AH Core** — каноническое хранилище, типизированные ссылки, глобальные UID, атомарные транзакции, производные индексы.
2. **Text Sensory** — сенсорный слой до LLM: токены → `S.R_text`, без создания семантики.
3. **LLM Perception** — адаптивный multi-call по коротким пробам; два исхода (валидный результат / явная ошибка).
4. **Deterministic Integration** — валидация, разрешение сущностей/кореференции/деиксиса, маршрутизация C/P/H, атомарный commit.
5. **Ignition Engine** — синхронные тики, `f(x,z)`, затухание, pacemaker `ν`.
6. **Lifecycle + GC** — `NEW→REINFORCED→CONSOLIDATED`, безопасное удаление orphan'ов.
7. **Workspace → AgentContext** — проекция ACTIVE/DEPENDENCY без второго reranker.
8. **Symbolic Inference** — role-fill, транзитивность, MP-подобный вывод, кванторы; read-only search.
9. **DSL / canonical API** — высокоуровневые запросы поверх канонической границы записи.
10. **Explicit FALSE / коррекция** — опровержение как `FALSE(N_old)`, вес корректируется через `h_N`.
11. **ν pacemaker + часы** — внутренние импульсы и опциональный wall-clock драйв.
12. **Diagnostics** — read-only инспектор, трассировка, CLI-дамп.
13. **Persistence** — атомарный JSON (temp → `os.replace`), перестройка индексов после load.
14. **Full Turn Orchestrator** — связывает всё выше в один цикл (`AgentOrchestrator`).
15. **Local LLM process boundary** — локальная модель в отдельном процессе (JSONL), ядро не зависит от torch/CUDA.
16. **GPU GUI** — PySide6 + VisPy, 2.5D/3D-сцена графа, редактор конфига, инспектор узлов.

## Структура проекта

```text
config/            # default.toml + пресеты (ollama/lmstudio/android)
prompts/          # agent.txt, system.txt, perception/*.txt (короткие пробы)
schemas/          # JSON-схемы протоколов
docs/             # архитектура, implementation map, acceptance, archive/slices/
src/ah/           # ядро: model, core, perception, integration, ignition,
                  #   inference, projection, llm, agent, gui, dsl, corpus, ...
tests/            # unittest-свит + acceptance-фикстуры
android/          # Android NPU bridge (Kotlin)
```

## Тесты и acceptance

```bash
# полный свит
PYTHONPATH=src python -m unittest discover -s tests -v
# или через pytest
python -m pytest -q            # run_all_tests.bat
```

Поведенческие инварианты и метрики M1–M5 прогоняются отдельными acceptance-командами
CLI (см. таблицу выше) через тот же локальный пайплайн, что и живой агент.
