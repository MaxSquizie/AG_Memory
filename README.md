# AH Agent MVP

**Ассоциативно-иерархическое (AH) ядро памяти для текстового LLM-агента.**

`ah-agent-mvp` — когнитивная память: канонический гиперграф знаний, детерминированный
символьный вывод и движок распространения активации. Локальная LLM подсказывает семантику
текста; все канонические решения (кто есть кто, какие домены, какие сущности) принимает
детерминированный код, а не модель.

---

## Что это за проект

Ядро представляет память как **типизированный гиперграф** из семи классов узлов:

| Узел | Роль |
|------|------|
| `S`  | устойчивая лексическая единица / парадигма (слово, предикат) |
| `m`  | сущность-манифестация (конкретный объект/персона) |
| `g`  | логический оператор (AND/OR/NOT/EXISTS/кванторы) |
| `k`  | множество / неопределённая ссылка (`AMBIGUOUS`) |
| `T`  | типизированное утверждение-шаблон (предикат + валентность) |
| `N`  | пропозиция — конкретный факт с актантами |
| `L`  | ассоциативная связь между узлами (`IS-A`, `FOLLOW`, `CAUSE`, …) |

Каждый узел живёт в одном из трёх **доменов**:

- **C** — *canonical* (стабильные факты/знания);
- **P** — *propositional* (текущие рассуждения, выводы);
- **H** — *experiential* (пережитый опыт: диалог, события, следы внимания).

Поверх канонического хранилища лежат производные индексы (полностью перестраиваемые из `AH`),
движок активации и проекция в контекст агента.

## Формализатор: как устроен

Формализатор — детерминированный конвейер, который превращает русский текст в типизированные
кандидаты и после проверки записывает их в граф. Он включается переменной окружения
`AH_FORMALIZER=1`; без неё используется встроенный адаптивный парсер (по умолчанию).

### Полный цикл обработки одного наблюдения

```text
RawInput → T0 → SRL → T1 → TD → T2 → TP → structural_seal
         → T3 → T4 → assemble_candidate_ir → C → T5 → T6  (+ T6b — ревизия/отзыв)
```

Каждая стадия работает в своей колонке: у неё зафиксированы вход, выход, разрешённые чтения и
отказы; выйти за свою колонку стадия не может.

1. **T0.** Каждый символ исходной строки помечается как токен, пунктуация или пробел — ни одна
   буква не теряется; фиксируется снимок ресурсов.
2. **SRL (структурная разбивка).** Кандидаты границ предложений/клауз и эллипсиса. Гипотеза токена
   всегда включает вариант «оставить как есть»: расстояние до известного слова лишь ранжирует, а не
   доказывает опечатку.
3. **T1 (морфология и лексика).** Для каждого слова — лемма, часть речи, падеж/число/род; двусмысленные
   варианты сохраняются отдельными кандидатами. Незнакомое слово остаётся как есть, пока нет основания
   считать его опечаткой.
4. **TD (зависимости и кореференция).** Кандидаты зависимостей и разрешения местоимений по четырём каналам
   доказательств (морфология / синтаксис / дискурс / память). Несовместимые по известным признакам кандидаты
   отклоняются, а не угадываются. Строится дерево областей действия для кванторов, отрицания, модальности и времени.
5. **T2 (рамки).** Из слов собираются предикативные рамки по объявленным операциям и ресурсу валентности;
   недостающие участники фиксируются как кандидаты, а не выдумываются. Непокрытые связи честно помечаются.
6. **TP (локальные гипотезы модели).** Когда детерминированных кандидатов недостаточно, модель предлагает
   ограниченную локальную структуру — только из объявленных типов узлов и рёбер, без канонических идентификаторов
   и без утверждения об истинности; предложение детерминированно проверяется.
7. **structural_seal.** Структура фиксируется для этой версии интерпретации: дальнейшее изменение запрещено,
   поэтому вместо скрытой перегенерации выдаётся честная неполнота.
8. **T3 (семантическое разрешение).** Для каждого слота — ограниченный выбор значения из заранее объявленного
   набора; каждое решение остаётся предварительным и несёт основания.
9. **T4 (поиск и исход).** Итог: `RESOLVED` / `AMBIGUOUS` / `INSUFFICIENT_CONTEXT` / `NO_CANDIDATE` /
   `UNRESOLVED`; каждый не-`RESOLVED` несёт явную причину. Однозначное решение требует одновременного выполнения
   трёх условий, а не просто наличия единственного кандидата.
10. **assemble_candidate_ir.** Все выходы собираются в неизменяемый IR — единственный результат формализации.
11. **C (консолидация).** Планы объединения идентичных сущностей, дедупликация и каноническая привязка; либо
    изолированный открытый шаблон для нового слова. Записей в граф ещё нет.
12. **T5 (журнал).** Формируется батч и запись журнала; факт попадает в журнал только при исходе `RESOLVED`.
13. **T6 (единственный писатель).** Утверждённые факты записываются в граф одной атомарной транзакцией с
    идемпотентными маркерами; после сбоя состояние восстанавливается детерминированно до того же результата.
14. **T6b (ревизия и отзыв).** Новые данные создают новую версию интерпретации того же наблюдения; отзыв
    наблюдения каскадно инвалидирует его основания и закрывает открытые конфликты.

### Типы оснований: O C W R D M A P

Каждое решение опирается на типизированные основания двух классов с разными правами.

**Truth-grounds — утверждают, что содержание является фактом:**
- **O** — само наблюдение: исходный фрагмент текста дословно;
- **C** — объявленное контекстное утверждение (дословная цитата); может подтверждать другие наблюдения, но само не записывается как факт;
- **W** — версионированная фоновая запись с собственным происхождением и интервалом действия.

**Interpretation grounds — помогают распознать значение/структуру, но сами по себе не утверждают факта:**
- **R** — запись ресурса (морфология, валентность, смыслы);
- **D** — сработавшее проверяемое правило и зафиксированные признаки;
- **M** — валидированный выбор модели или локальная гипотеза (сохранены запрос и ответ); повтор идентичного M ничего не добавляет;
- **A** — явно объявленная внешняя гипотеза; никогда не записывается как факт;
- **P** — свидетельство предшествующего наблюдения из контекста; используется только для разрешения местоимений.

Следствие: факт материализуется только при наличии O/C/W-основания. R/D/M/A/P обосновывают выбор интерпретации
и структуру, но ни один из них в одиночку не подтверждает истинность содержания.

### Честная неполнота вместо угадывания

Покрытие структуры отчитывается отдельным статусом — `FULL_CANONICAL` / `OPEN_LEXICAL` / `PARTIAL` / `NONE` —
независимо от семантического исхода. Отсутствие записи в ресурсе даёт явный диагноз (например, неизвестная
валентность), а не молчаливое допущение; незанятый слот и непокрытая связь сохраняются как кандидаты с причиной.

### Два независимых состояния решения

Жизненный цикл решения (`OPEN → PROVISIONAL → … → COMMITTED / SUPERSEDED / FROZEN`) отделён от семантического
исхода (`RESOLVED` / `AMBIGUOUS` / `INSUFFICIENT_CONTEXT` / `NO_CANDIDATE` / `UNRESOLVED`). `RESOLVED` выдаёт T4;
`COMMITTED` — только после условий коммита и маркера.

### Коммит и ревизия

T5 пишет журнал, T6 — единственный писатель утверждённых фактов: одна атомарная транзакция, идемпотентные
маркеры, детерминированное восстановление после сбоя до того же конечного состояния. T6b создаёт новую версию
интерпретации при новых данных; отзыв наблюдения каскадно снимает его основания и закрывает открытые конфликты —
отозванный кандидат не становится фактом (открытый мир).

### Конфликты без молчаливого удаления

Кандидат, противоречащий закоммиченному факту или другому фрагменту того же батча, исключается из коммита, но
остаётся видимым как открытый отчёт `CONFLICTING_EVIDENCE` с причиной и стабильным детерминированным идентификатором.
Отчёт закрывается только явным актом (отзыв / замена / разъяснение говорящего); молчаливого исчезновения альтернативы нет.

### Логика, кванторы и время

Над графом работают логические операторы (`AND`/`OR`/`XOR`/`NOT`) и кванторы (`EXISTS`/`FORALL`) в канонической
форме; элиминация дизъюнкта требует явной временной лицензии. Отрицание несёт область действия как интервал.
Временные утверждения прикрепляются к фактам с интервалом и семантикой `CONTINUOUS`/`EXISTENTIAL`; противоречие
проверяется по гарантированной одновременности, а не по совпадению строк.

### Вывод по закоммиченному состоянию

Запросы-цели выполняются read-only поверх утверждённых фактов; производные выводы дописываются (append-only),
не переписывая существующие записи, версии и маркеры.

### Адаптивный опыт (R-X)

Кэш хранит опыт, а не истину: он влияет на приоритет кандидатов, но не имеет права запрещать новую интерпретацию;
текущее предложение всегда разбирается заново. Чтение разделено по стадиям (морфологическое / структурное /
семантическое), повторное использование записи не создаёт нового основания.

### Детерминизм и версионирование

Один вход и один снимок ресурсов дают одинаковый результат на каждой стадии; изменение объявленного источника
вызывает пересчёт, но не обязано менять исход. Каждая интерпретация версионируется; ревизия создаёт новую версию,
а не переписывает историю.

## Что умеет ядро

- **Понятная семантика.** Факты хранятся как пропозиции с актантами и логической структурой, поэтому над ними
  работают транзитивность `IS-A`/`FOLLOW`, модус причинности, кванторы (`EXISTS`/универсальные правила), временные
  интервалы и явное опровержение (`FALSE(N)`).
- **Символьный вывод.** Над графом работают логические правила (транзитивность, MP-подобный вывод по `CAUSE`, кванторы,
  временные модусы) — read-only поиск поверх канонического хранилища.
- **Атомарная управляемая память.** Copy-on-write транзакции, lifecycle (`NEW → REINFORCED → CONSOLIDATED`), GC, который
  не удаляет консолидированные и исторически значимые факты, явная семантическая коррекция через `FALSE(N)`.
- **Ассоциативная динамика.** Движок Ignition считает возбуждение `x`, импульсы и веса связей; Workspace определяется
  порогом `x > t`.
- **Локальный self-hosted контур.** Работает с локальными бэкендами (Ollama, LM Studio, HuggingFace в отдельном процессе)
  и имеет мост на Android NPU. Ядро не зависит от `torch`/`transformers`/облака.
- **Прозрачность.** Весь граф виден в GPU-GUI как 2.5D/3D-сцена; есть read-only диагностика, DSL для запросов и полный
  provenance/trace каждого вывода.

## Как пользоваться

### Установка

Требуется **Python ≥ 3.12**. Базовое ядро тянет только `pymorphy3`; остальное — опциональные extras:

```bash
# ядро + тесты
pip install -e ".[test]"

# GUI (PySide6 + VisPy) и локальная LLM (torch/transformers)
pip install -e ".[gui,llm]"

# отдельные бэкенды / возможности
pip install -e ".[llm-lora]"     # LoRA-адаптеры
pip install -e ".[llm-vision]"   # мультимодальность
```

Точка входа — два console-скрипта: `ah-agent` (CLI) и `ah-gui` (GUI).

### GUI (основной способ работы)

```bash
# Windows
run_gui.bat                 # config/default.toml
run_gui_ollama.bat         # бэкенд Ollama
run_gui_lmstudio.bat       # бэкенд LM Studio

# Linux/macOS
./run_gui.sh
# или напрямую:
ah-gui --config config/default.toml
```

GUI строит AH как GPU-сцену (цвет = домен, «жар»/размер узла = возбуждение `x`, белая вспышка = активация, голубая
обводка = Workspace), содержит диалог, полный TOML-редактор конфига с picker'ом пути к модели и инспектор узлов. Все
параметры можно менять из GUI; поля помечены `LIVE / NEXT_TURN / RESTART_LLM / RESTART_RUNTIME`.

Путь к локальной модели задаётся **только** в конфиге:

```toml
[paths]
llm_model_dir = "C:/Models/Qwen"
```

### Включение детерминированного формализатора

По умолчанию восприятие обрабатывает встроенный адаптивный парсер. Чтобы включить детерминированный формализатор,
задайте переменную окружения перед запуском:

```bash
AH_FORMALIZER=1 ah-gui --config config/default.toml
# или для CLI:
AH_FORMALIZER=1 ah-agent --config config/default.toml <команда>
```

Без этой переменной формализатор не подключается, и используется встроенный парсер.

### CLI (диагностика и загрузка данных)

```bash
ah-agent --config config/default.toml <команда>
```

| Команда | Назначение |
|---------|-----------|
| `summary` | сводка по runtime |
| `dsl "<выражение>"` | выполнить одну DSL-команду/пайплайн |
| `dump-json` / `dump-dot` | дамп канонического/runtime-графа (JSON / Graphviz) |
| `tick [n]` | вручную продвинуть Ignition на n тиков |
| `refute <uid> [--tick]` | создать/повторить `FALSE(N)` и запланировать опровержение |
| `import-corpus <path>` | холодная загрузка структурированного JSON/.ahm/.prj в AH |
| `import-text <path>` | загрузить сырой текст как опыт USER (по умолчанию строгий семантический парсинг) |
| `import-dialogue <path>` | загрузить диалог `ah_dialogue_v1` |
| `import-memory <path>` | заменить живой AH снапшотом персистентности |
| `reset-memory` | очистить AH/runtime/context и заново создать SELF/USER |

Пример DSL:

```bash
ah-agent dsl "findRoles role=LOCATION value=@M_1 domain=H | findLists domain=H | where meta.TYPE=Episode"
```

### Конфигурация

Главный файл — `config/default.toml`; рядом лежат готовые пресеты под бэкенды:
`ollama.toml`, `lmstudio.toml`, `android.toml`. Конфиг управляет: путями и параметрами LLM, начальными весами
интеграции, функциями активации `f/g/h/t/ν`, силой семантических/сенсорных seed'ов, lifecycle/GC, глубиной и бюджетом
вывода, порогом Workspace, бюджетом AgentContext, политикой персистентности, identity агента/пользователя и числом тиков
оркестратора.

## Архитектура (обзор)

Полный когнитивный turn-цикл:

```text
внешний текст
→ восприятие (встроенный адаптивный парсер ИЛИ детерминированный формализатор, AH_FORMALIZER=1)
   → T0–T6b: токенизация → структура → морфология/зависимости → рамки → seal → семантика → IR → консолидация → журнал → коммит
→ Ignition ticks (распространение активации)
→ Workspace = узлы с x > t
→ Symbolic Inference (транзитивность, кванторы, вывод)
→ опциональная материализация вывода (C < P < H)
→ проекция ACTIVE/DEPENDENCY → AgentContext
→ ответ LLM-агента
→ интеграция ответа (H-only путь) + FOLLOW/episodic history
→ персистентность
```

Подсистемы (подробности — в `docs/IMPLEMENTATION_MAP.md` и `docs/reference/Архитектура_v3.md`):

1. **AH Core** — каноническое хранилище, типизированные ссылки, глобальные UID, атомарные транзакции, производные индексы.
2. **Восприятие текста** — встроенный адаптивный парсер (по умолчанию) или детерминированный формализатор (`AH_FORMALIZER=1`); два исхода: валидный результат / явная ошибка.
3. **Deterministic Integration** — валидация, разрешение сущностей/кореференции/деиксиса, маршрутизация C/P/H, атомарный commit.
4. **Ignition Engine** — синхронные тики, `f(x,z)`, затухание, pacemaker `ν`.
5. **Lifecycle + GC** — `NEW→REINFORCED→CONSOLIDATED`, безопасное удаление orphan'ов.
6. **Workspace → AgentContext** — проекция ACTIVE/DEPENDENCY.
7. **Symbolic Inference** — role-fill, транзитивность, MP-подобный вывод, кванторы; read-only search.
8. **DSL / canonical API** — высокоуровневые запросы поверх канонической границы записи.
9. **Explicit FALSE / коррекция** — опровержение как `FALSE(N_old)`, вес корректируется через `h_N`.
10. **ν pacemaker + часы** — внутренние импульсы и опциональный wall-clock драйв.
11. **Diagnostics** — read-only инспектор, трассировка, CLI-дамп.
12. **Persistence** — атомарный JSON (temp → `os.replace`), перестройка индексов после load.
13. **Full Turn Orchestrator** — связывает всё выше в один цикл (`AgentOrchestrator`).
14. **Local LLM process boundary** — локальная модель в отдельном процессе (JSONL); ядро не зависит от torch/CUDA.
15. **GPU GUI** — PySide6 + VisPy, 2.5D/3D-сцена графа, редактор конфига, инспектор узлов.

## Структура проекта

```text
config/            # default.toml + пресеты (ollama/lmstudio/android)
prompts/          # agent.txt, system.txt, perception/*.txt (короткие пробы)
schemas/          # JSON-схемы протоколов
docs/             # архитектура, implementation map, reference/, archive/slices/
src/ah/           # ядро: model, core, perception, integration, ignition,
                  #   inference, projection, llm, agent, gui, dsl, corpus, ...
src/ah/formalizer/# детерминированный формализатор (включается AH_FORMALIZER=1)
tests/            # unittest-свит + acceptance-фикстуры
android/          # Android NPU bridge (Kotlin)
```
